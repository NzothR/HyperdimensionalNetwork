# 超维网络：分阶段实施与验收计划

本计划面向新模组重写，不承担旧 `DestroyStorage` 代码或旧存档兼容。每阶段形成一个可检查的提交和可运行构建；功能接入按当前目标游戏版本验证。

## 阶段 0：锁定目标版本和接入契约

**工作**

- 记录目标 7 Days to Die 版本、运行时/.NET/Mono 限制、Harmony 版本和打包方式。
- 用反编译/调试确认玩家背包、配方材料检查与扣除、工作站队列、维修、建筑升级、载具燃料/维修等真实调用链。
- 盘点常用第三方模组和它们对库存的访问方式，区分公共 API、Harmony 钩子和仅槽位数组访问。
- 建立最小兼容矩阵和 API 变化记录。

**验收**：每个核心消费入口有调用链图、查询/扣除时点和取消/失败语义；明确支持的首发游戏版本。未确认的入口标记为风险，不假定旧补丁仍有效。

## 阶段 1：领域模型、精确身份和交易协议

**工作**

- 定义 `ItemKey` 规范、序列化格式、相等性及品质/改装件/耐久/弹药等字段策略。
- 定义来源提供者、查询条件、精确材料需求、预留、提交、撤销、幂等交易 ID 和权限上下文。
- 明确背包/快捷栏/网络来源优先级及异步工作站生命周期。
- 加入调试配置模型、耗时计时器和适配器能力报告。

**验收**：六级材料只匹配六级；相同基础物品但改装件或弹药不同不会被误合并；失败和取消会释放预留；重复提交不会重复扣除。

## 阶段 2：存储引擎、索引和持久化

**工作**

- 建立精确变体主索引、基础 ID/分类/搜索辅助索引和预留计数。
- 实现按变更更新索引、并发交易保护、快照与追加日志、校验和、原子检查点和恢复诊断。
- 用可重复数据集测量加载、增删、查数、保存、恢复及内存开销。

**验收**：进程重启后数量和完整物品身份一致；损坏日志有可理解的恢复日志；普通增删只处理受影响条目，不重写整个存储文件；数据规模扩大时不会构造同量的常驻 `ItemStack` 对象。

## 阶段 3：存储界面和浏览投影

**工作**

- 实现打开/关闭、分页、分类、搜索、排序、精确数量、存入/取出和修订号缓存。
- 只为可见页面生成游戏 UI 项；搜索采用缓存文本/索引，输入防抖。
- 加入容量/权限/忙碌/保存错误反馈和诊断面板。

**验收**：拖动物品不会引发全库排序、全量保存和全量读取；翻页只投影当前页；筛选结果与存储计数一致。1 千、3 万、10 万变体均记录基线耗时。

## 阶段 4：单机核心消费适配器

按入口逐个落地，每个适配器需单独启停、记录能力和失败阶段：

1. 配方可用性、材料计数和制作消耗（先覆盖品质精确要求）。
2. 普通/高级工作站输入和异步队列预留。
3. 建筑方块升级、工具/装备维修和即时维修。
4. 载具燃料与载具维修。
5. 换弹、弹药银行及弹药类型规则。
6. 商人货币/购买和其他经过确认的库存入口。

**验收**：每项都有“可用数量正确、品质正确、恰好消耗一次、失败不丢失、取消释放、外部工作站可识别”用例；一个适配器失败不影响 UI 和其他适配器。

## 阶段 5：多人权威和共享网络

**工作**

- 服务端权威查询/交易、修订号、幂等请求、增量同步和快照恢复。
- 玩家/群组权限、邀请/接受/拒绝/退出流程及权限变更事件。
- 对延迟、重试、断线和重复 RPC 做交易一致性处理。

**验收**：两个客户端并发取最后一份材料时只有一个成功；重复包不会重复增减；断线重连后客户端最终与服务端修订一致；无权限操作明确拒绝并记诊断。

## 阶段 6：恢复附加功能和模组生态

**工作**

- 插件槽和插件效果：立即制作、立即拆解、立即维修、三核心插件、材料返还、自动补货、弹药银行、种植加速等。
- 分类规则、垃圾/过滤规则、快捷键、容器快捷存入、快捷访问、群组指令及多语言。
- 发布稳定的第三方适配 API、示例适配器和兼容矩阵。
- 评估是否恢复模组内说明页；开发期极限测试改为命令/测试夹具，正式内容无需暴露测试物品。

**验收**：插件通过相同交易接口工作，不直接改库存数组；插件和第三方适配器异常可隔离；逐版本生成兼容报告。

## 阶段 7：性能和发布验证

**工作**

- 对 1 千、3 万和 10 万精确变体执行标准基准，分析 P50/P95 和分配量。
- 在清洁单机、多人服务器及目标常见模组组合运行完整矩阵。
- 测试存档恢复、强制退出、日志开关、补丁缺失、异常物品数据和网络延迟。
- 生成只包含发布所需模组文件的部署/打包脚本；默认部署与发布打包分别执行。

**验收**：核心消费没有误匹配或重复扣除；适配状态可诊断；拖放/查询路径无全量 IO/重建；性能目标根据真实目标机基线确定并满足；发布包不含源码工作区、缓存和本地测试数据。

## 需要在阶段 0 确认的风险

- 当前游戏版本可能改变关键方法签名、库存结构或 Harmony 执行时机。
- 有些第三方模组直接读写槽位数组，无法只靠统一查询 API 自动兼容。
- 异步队列和多人模式的扣料时点必须与游戏服务器真实生命周期一致。
- `ItemValue` 的完整序列化/相等性语义以及模组自定义字段，需要用实际物品做往返验证。
- 游戏对象、物品定义和 UI 图标的线程安全规则需要验证；在此之前后台线程只处理纯数据。
