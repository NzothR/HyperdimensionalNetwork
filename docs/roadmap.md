# 超维网络：分阶段实施与待定细节

本文记录已确认的阶段安排、已验收范围、后续候选功能和仍需逐项讨论的规则。功能行为讨论完成后再补齐对应设计；本文不把尚未确认的候选行为当作已定需求。

## 当前状态

用户已确认阶段 1、2、3 验收完成。下一步进入多人开发第一阶段。其间所有新增功能从设计时考虑多人使用，避免功能完成后再补一轮多人架构。

多人开发第二阶段包含成员关系操作和最终多人验收。朋友参与的多人测试统一安排在其他功能完成后，减少反复占用朋友时间。

## 阶段 0：目标版本和接入契约

目标游戏版本、运行时/.NET/Mono 限制、Harmony/API 接口及首发模组兼容矩阵仍需在多人改造和新功能接入时持续核实。旧 `DestroyStorage` 只用于盘点功能与补丁入口，不作为新实现契约。

## 阶段 4：多人开发第一阶段——服务端基础、既有功能多人化和其他功能

### 网络与交易核心

- 每个网络具有持久、唯一、不会复用的 `NetworkId`；建议采用 GUID 或等价的全局唯一格式。所有库存操作明确指定网络 ID，不按显示名称或临时实体 ID 混用库存。
- 使用稳定玩家 ID 记录玩家当前所属网络。玩家首次进入存档时得到自己的独立网络，并作为该网络唯一管理员。
- 服务端拥有网络库存、成员关系和交易结果的最终权威。客户端请求查询/变更并显示服务端确认后的状态。
- 交易具备唯一 ID、网络修订号和可恢复的持久化语义，重复请求不能重复扣料或加料；多人同时消费时不能超额使用。
- 已验收阶段 1–3 的界面存取、制作、工作站、装备维修、建筑修复/升级、载具燃料/维修都接入服务端请求流程。操作要保留发起玩家上下文，区分共享材料与玩家个人收益/进度。
- 其他候选功能都在本阶段设计和开发；每项功能都明确操作者、共享库存影响、收益/进度归属及失败、取消、断线和重试语义。

### 服务器管理员控制台指令

服务器管理员权限与网络内“管理员/成员”角色是两种不同权限。以下维护指令只允许服务器管理员执行，并在服务端检查参数和权限：

1. 按源网络 ID 和目标网络 ID 迁移库存物品。此操作只搬库存，不改变网络成员关系或网络 ID；成功后源网络保留为空。
2. 按网络 ID 清空库存。网络 ID 和成员关系保留；建议要求显式确认参数。
3. 按玩家 ID 查询其当前网络 ID 和网络角色。共享网络中的玩家返回同一个网络 ID。
4. 列出当前存档中已知玩家的玩家 ID、显示名称、在线状态、当前网络 ID 和角色。
5. 按玩家 ID 设置网络管理员，不接收网络 ID 参数。服务端先查该玩家当前所属网络，将其设为管理员，并将同网络其他管理员降为成员；不影响其他网络。

库存迁移和玩家加入网络是不同操作：维护指令只迁移物品；成员加入会改变成员关系，并按第二阶段规则注销来源网络。

### 本阶段验收边界

开发期间构建并回归已验收的单机流程。最终的多人游玩验收延后到多人开发第二阶段，并等其他候选功能都完成后集中进行。

## 阶段 5：多人开发第二阶段——成员关系、UI/玩家指令与集中验收

### 邀请和成员规则

- 邀请即时发送，只能邀请当前在线玩家；不创建面向离线玩家的待处理邀请。
- 网络管理员和成员都能邀请别人；受邀玩家必须接受后才加入，加入者初始为成员。
- 一个玩家同一时刻只属于一个网络。成员要换网时先退出当前网络，再接受目标网络邀请。
- 成员可主动退出；网络管理员不能普通退出，也不能踢出自己。管理员可以踢出成员。
- 网络只有一个管理员。管理员可通过明确的“合并加入”操作加入别人网络，个人网络物品并入目标网络，原网络注销，玩家降为目标网络成员；个人网络还有其他成员时，先由他们离开或被移出。
- 成员退出或被踢后，立即失去原网络访问权并得到一个新的空网络，成为新网络管理员。此前的共享库存留在原网络，不按存入者返还。
- UI 和玩家指令共用服务端成员/权限服务。踢出、退出或加入完成后，旧界面和进行中的请求不能继续操作旧网络。

### 最终多人验收

朋友参与的多人验收等所有新增功能完成后集中进行，覆盖：

- 各玩家私人网络隔离；网络 ID 稳定且不同网络库存不串联。
- 管理员/成员邀请、接受、退出、踢出、网络管理员恢复和合并加入。
- 合并中断、服务器重启、重复请求和存档恢复不会重复加物品或丢物品。
- 多名玩家并发取出或消耗材料时，库存和修订保持一致。
- 阶段 1–3 及新增功能在多人下的发起者、受益玩家、库存扣除和失败回滚正确。
- 离线重连后成员关系与网络 ID 正确；已离线玩家不可接收新邀请。

多人测试的实际执行放在此阶段末尾，不要求朋友参与每个功能的开发迭代。

## 其他功能候选与待确定细节

以下内容来自现有架构规划和旧模组功能清单。它们计划放入多人开发第一阶段逐项讨论和实现；并非全部承诺实现。

### 弹药、换弹和弹药银行

- 哪些武器、弹匣和弹药类型可使用网络库存？是否只补充换弹，还是射击消耗也能从网络扣除？
- 品质、弹药类型、改装件和已装填弹匣如何匹配？网络取弹的数量、优先级和动画/声音沿用什么原版行为？
- “弹药银行”指储存、自动补货、自动换弹还是其他具体操作？

### 出售和商人交易

- 手动出售按游戏售价还是商人实际收购价？药水、技能等交易加成如何计算？售价由谁获得：发起者、网络，还是按别的规则分配？
- 自动出售由谁配置和拥有规则？入库时由存入者领取收益，还是收益归网络？如何避免同一物品重复出售？
- 商人商品集合按每个玩家已发现的商人分别计算，还是由网络共享？远程购买必须向哪个实际商人购买，货币从谁的库存扣除，物品送给谁或放在哪里？
- 每日刷新后自动购买的优先级、预算、失败重试和库存已满处理是什么？

### 自动读书和书籍处理

- “未读”必须按触发者个人进度判断；书籍从共享网络扣除后，学习效果归实际触发的玩家。
- 一键操作选择哪些书：设计图、杂志、技能书、可叠加阅读的书？“未满级”的判断和一键出售规则分别是什么？
- 入库触发自动读/售时，规则属于个人还是整个网络？由谁设置，书籍学习收益给存入者、当前在线玩家还是指定玩家？
- 玩家离线或没有明确触发者时，自动读书应暂停还是按网络管理员设置执行？无法明确收益归属前不实现后台代读。

### 远程箱子链接

- 可接入的箱子类型、距离/区域范围、是否要求领地或权限，以及箱子被拆除或区块卸载时的行为是什么？
- 链接存储与网络库存如何去重；同一物品同时在多个箱子或网络中时，查询、存入、取出和外部移动如何同步？
- 哪些网络成员可以添加、移除或配置链接？服务端如何限制跨区块扫描和性能开销？

### 自动化链式合成和补货

- 合成链在哪里启动，产物进入玩家背包、工作站还是网络？工作站类型、技能/解锁和配方选择如何限制？
- 多人共享材料时如何排队、预留与公平分配？发起者离线、取消、缺料或中途失败时，材料和产物分别退到哪里？
- 自动补货由谁配置、作用于哪个玩家/工作站、补充阈值和物品白名单如何定义？

### 旧模组附加功能

- 即时制作、即时拆解、即时维修分别绕过哪些原版时间或队列规则，材料和技能收益如何计算？
- 三核心插件各自效果、安装位置、叠加方式、取下/更换后的处理是什么？
- 拆解材料返还沿用什么原版或旧模组公式，是否受技能、品质和耐久影响？
- 种植加速影响哪些作物和区块，是否持续运行，玩家离线后是否生效？
- 模组内说明页首发需要覆盖哪些功能、语言和控制入口？

### 规则、界面和扩展 API

- 存储过滤/拾取规则由玩家还是网络管理员配置？规则在多人网络中共享吗？黑名单、入库即售/读/销毁的优先级是什么？
- 分类、排序、快捷操作、按键配置和状态页面有哪些首发要求？成员看到的所有者、网络标题和成员列表包含什么信息？
- 第三方 API 的稳定范围、版本兼容、权限调用和异步交易生命周期如何设计？

## 阶段 6：性能和发布验证

- 对 1 千、3 万和 10 万精确物品变体做基准，包含单变体超出 `int32.MaxValue` 的数量；记录 P50/P95 和内存分配。
- 完成单机、多人和目标常见模组组合的最终兼容矩阵。多人实测遵循阶段 5 的集中安排。
- 验证持久化恢复、强制退出、重复交易请求、日志开关、补丁缺失、异常物品数据及网络延迟。
- 发布包与开发工作区、缓存和本地测试数据分开。

**发布验收**：核心消费没有误匹配或重复扣除；各适配器能力可诊断；普通查询/拖放不触发全量磁盘读写或全量 `ItemStack` 构造；单条库存变更不向所有客户端广播完整快照。
