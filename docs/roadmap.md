# 超维网络：分阶段实施与验收计划

本计划面向新模组重写，不承担旧 `DestroyStorage` 代码或旧存档兼容。阶段按游戏内可独立测试的功能划分；每阶段形成一个可检查的提交、可运行构建和部署版本，不把只能验证能否启动的代码堆成一个测试阶段。

## 阶段 0：锁定目标版本和接入契约

**工作**

- 记录目标 7 Days to Die 版本、运行时/.NET/Mono 限制、Harmony 版本和打包方式。
- 用反编译/调试确认玩家背包、配方材料检查与扣除、工作站队列、维修、建筑升级、载具燃料/维修等真实调用链。
- 盘点常用第三方模组和它们对库存的访问方式，区分公共 API、Harmony 钩子和仅槽位数组访问。
- 建立首发兼容矩阵和 API 变化记录。

**验收**：每个核心消费入口有调用链、查询/扣除时点和取消/失败语义；明确首发游戏版本。未确认的入口标记为风险，不假定旧补丁仍有效。

## 阶段 1：最小可测试存储原型（已实现，待游戏内验证）

**功能**

- 导航栏最左侧书本图标直接打开超维网络，不需要解锁物品或 Buff。
- 从玩家背包拖放物品进网络、从网络取回；背包和战利品容器均提供一键存入。
- 参考旧模组窗口，包含分页、搜索和基础分类；弹药只属于独立弹药分类，不归入远程武器。
- 网络数量以 `long` 保存；任何对外数量或游戏 `ItemStack` 投影都限制到 `int32.MaxValue`。
- 两个压力测试物品：按运行时堆叠上限加入所有物品变体；可堆叠物品的每个变体加入 `int32.MaxValue`。品质物品遍历其可用等级。
- 日志配置代码默认关闭；本机开发部署配置开启，记录测试构造、事务持久化和网格投影耗时。

**验收**：新建单机存档可直接打开；拖放及一键存入/取出数量正确；重启后数据恢复；分类与品质变体显示正确；超过 int32 的网络数量仍以 int32 上限显示。压力测试前使用可丢弃存档，极限测试会产生很大的数量数据。

## 阶段 2：物品视同玩家携带（玩家库存、配方与工作方块；已接入，待游戏内验收）

按可单独游戏测试的小步完成，每一小步都先构建、部署，再验证后进入下一小步：

1. 玩家库存 `GetItemCount`、`HasItem`、`HasItems` 查询包含网络库存。
2. 任何消费判断得到的数量封顶为 `int32.MaxValue`，不得溢出到负数或假装超过游戏硬上限。
3. 按完整物品身份与品质匹配；六级材料要求不能由其他等级满足。
4. 增加统一来源优先级与材料预留/消费接口，避免只改变可用数量而未正确扣料。
5. 配方可用性、材料数量、最大可制作数、真实扣料、制作队列和失败/取消回滚。
6. 化学工作站、普通工作站/工作台、烹饪锅等输入格的材料检查与扣除。

**验收**：背包和网络的查询合并正确；超大数量对游戏端只暴露 int32 上限；品质、改装件等变体不会误匹配；配方与各类工作方块逐个测试；工作站要求实体输入槽时只通过窄适配器供料，不注入无限虚拟背包槽；材料消耗恰好一次；取消和失败时不丢料。每完成一个入口即可部署游戏内测试，不等整阶段全部完成。

**当前接入范围（待实测）**：玩家库存查询和批量扣料、配方可用性/最大可制作数、制作队列入队时扣料、普通工作方块输入格查询和扣料。当前游戏的篝火、工作台、化学工作站和水泥搅拌机制作从玩家库存扣料；熔炉使用独立的熔炼重量系统，尚未接入网络。队列取消沿用原版将材料返还到玩家物理库存的行为。极端写盘失败与多人并发场景仍需后续验证。

## 阶段 3：维修、建筑和载具

逐项完成并分别提供游戏用例：装备/工具维修、即时维修、建筑块升级与修复、载具燃料和载具维修。

**当前接入范围（待游戏内验收）**：装备/工具维修使用第二阶段玩家库存查询与扣料；Shift 点击维修操作执行即时维修。建筑块升级与修复使用独立材料事务；载具加油和载具维修接入网络材料。以上均已构建并部署到本机 `Mods`，需按 README 用例实际验证。

**验收**：每项按原版规则检查材料、品质、工具和耐久；成功只扣一次，失败/取消不扣；燃料数量、维修结果与背包材料行为一致。

## 阶段 4：其他核心物品入口

换弹、弹药银行，以及阶段 0 调查后确认属于核心携带体验的其他入口。商人购买/交易具有特殊语义，本阶段不包含，后续另行讨论。

**验收**：弹药类型、装填阶段及数量准确；每种适配器单独显示检测结果，缺少目标方法时清楚报告并禁用对应适配能力。

## 阶段 5：多人权威和共享网络

**工作**

- 服务端权威查询/交易、修订号、幂等请求、增量同步和快照恢复。
- 玩家/群组权限、邀请/接受/拒绝/退出及权限变更事件。
- 处理延迟、重试、断线和重复 RPC。

**验收**：两个客户端并发取最后一份材料时只有一个成功；重复包不重复增减；断线重连后客户端与服务端修订一致；无权限操作明确拒绝并记录诊断。

## 阶段 6：附加功能和模组生态

本阶段放置非核心功能，具体设计和实施顺序稍后再定，不阻塞核心存储与携带物品体验：

- **出售物品**：选择物品后按售价换成公爵币，并正确应用药水、技能等交易加成。
- **自动售出**：为指定物品设置规则，物品进入超维网络时自动售出。
- **商人交易集合与购买**：汇总玩家已发现/见过的商人可交易商品；购买时仍与实际商人发生交易，不凭空生成商品。
- **远程商人自动购买**：设置指定商品和数量，在每日商人商品刷新时从可交易的商人处购买。
- **自动读书**：一键阅读所有未读设计图和未满级杂志；已读/已满级书籍可一键出售。
- **入库自动读/售书**：书籍进入网络后按玩家设置的类别或“全部”规则自动阅读，或将已读/满级书籍售出。
- **远程链接**：以类似 AE2 存储总线的方式把箱子接入网络，并定义可访问范围、刷新和物品变更语义。
- **自动化链式合成**：按配方依赖链自动补齐材料、填入产物并处理队列与失败回滚。
- **旧模组附加项**：立即制作、立即拆解、立即维修、三核心插件、拆解材料返还、自动补货、弹药银行、种植加速和模组内说明页。
- 分类/过滤规则、快捷操作、多语言及第三方适配 API 持续完善。

**验收**：每个附加功能另立可游戏内验证的小阶段；交易功能使用游戏实际交易逻辑并遵守玩家加成，自动化功能具备可查看的执行结果和失败诊断；远程箱子受权限/范围规则约束；异常可隔离。

## 阶段 7：性能和发布验证

- 对 1 千、3 万和 10 万精确变体做基准，包含单变体超出 `int32.MaxValue` 并验证对外封顶；记录 P50/P95 和分配量。
- 在清洁单机、多人与目标常见模组组合下运行兼容矩阵。
- 验证持久化恢复、强制退出、日志开关、补丁缺失、异常物品数据及网络延迟。
- 部署脚本和发布打包脚本分开，发布包不带源码工作区、缓存和本地测试数据。

**验收**：核心消费无误匹配或重复扣除；适配状态可诊断；查询/拖放路径不触发完整磁盘读写或全量重建；性能目标在目标构建和目标机器上实测后确定。

## 功能覆盖

| 功能域 | 目标状态 | 阶段 |
|---|---|---|
| 大型随身库存、精确变体、存取、分类、分页和快速存入 | 核心原型 | 1 |
| 长整型存储、游戏外部数量 int32 封顶 | 核心约束 | 1–3 |

| 多人同步、群组权限 | 多人核心 | 5 |
| 买卖、自动交易、自动读书、远程链接、链式合成、旧插件 | 附加功能 | 6 |
| 极限性能测试和发布检查 | 维护 | 1、7 |

## 实施风险

- 当前游戏版本可能改变关键方法签名、库存结构或 Harmony 执行时机。
- 有些第三方模组直接读写槽位数组，无法只靠查询 API 自动兼容。
- 异步队列和多人模式的扣料时点必须匹配游戏服务器真实生命周期。
- `ItemValue` 的序列化/相等性语义和模组自定义字段须用真实物品往返验证。
- 游戏对象、物品定义和 UI 图标的线程规则需要验证；确认前后台线程只处理纯数据。
