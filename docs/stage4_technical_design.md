# 超维网络：阶段 4 核心架构与多人化技术设计

> 版本：2026-10-18 · 阶段 4 开工建议稿<br>
> 配套文档：[《超维网络：设计与实施计划》（阶段 4 修订版）](design_revised.md)<br>
> 本文侧重**尚未实现的服务端基础架构**与可执行的开发契约，不预设 7 Days to Die 的具体类型名、API 签名或 Harmony 补丁位置。阶段 1–3 现有代码的迁移只定义目标与检查方法，实际改造点以代码审查为准。

## 0. 约束、已确认决定与非目标

### 0.1 已确认的产品/阶段决定（按此实现）

1. **顺序**：多人核心 → 阶段 1–3 多人化 → 手动/自动补货 → 弹药银行 → 自动化链式合成 → 商人交易。
2. **环境**：单机、房主联机、专用服务器共用服务端权威逻辑；客户端只能请求查询/操作和显示服务端确认结果。房主不可绕过统一入口。
3. **身份**：`NetworkId` 持久唯一且不复用；每个玩家由稳定 `PlayerId` 关联且同时仅属一个网络；每网恰好一名网络管理员。成员管理的正式 UI/指令和共享网络综合验收属于阶段 5。
4. **开发数据**：阶段 1–3 测试存档可丢弃；不实现旧格式迁移。正常保存和正常关闭必须可靠；**不保障突然进程崩溃时最后的未保存变更或跨原版状态的一致性**。
5. **网络持久化**：正常运行时以内存为权威，周期性保存版本化快照；不要求每笔交易 WAL 同步刷盘或进程崩溃后事务回放。
6. **轻量客户端**：不维护完整库存镜像；按需读取查询视图，接收变化条目或视图失效通知；重连时重新校验必要缓存。
7. **插件系统**：阶段 4 完全暂缓插件槽、插件物品与解锁限制；普通成员/管理员权限依然生效。
8. **临时链式订单**：订单、订单空间和追踪状态仅在运行期存在；正常取消/离线尽力回收，服务器意外崩溃不恢复旧订单，接受少量损失，并尽量减少复制机会。
9. **测试安排**：阶段 4 只验证单机、多人架构与玩家独立网络（包括远程客户端基本流程）；真实共享网络及跨成员并发综合验收推迟到阶段 5，不为阶段 4 临时开发共享入口。
10. **现有功能**：阶段 1–3 的界面/行为继续沿用，改造成服务端权威实现；具体改哪些源码、补丁、原版方法须在看到代码后决定。

### 0.2 不在当前范围

- 不构建抽象到多个游戏版本的通用兼容层、独立公共插件 API、旧存档迁移系统。
- 不为进程崩溃实现跨玩家背包、工作方块与网络库存的两阶段磁盘提交或自动恢复。
- 不提前开发阶段 5 的玩家邀请、退出、踢出、合并交互，也不提前开发插件系统。
- 不把“网络物品视同携带”解释成把全部网络物品伪装成玩家背包 `ItemStack` 或无限虚拟槽。
- 不在没有源码验证的情况下声称任何具体原版入口能做到原子扣料、任务追踪或远程商人交易。

### 0.3 贯穿全阶段的必须满足项

- **正常执行严格正确**：扣料、加料、取消、失败、重复请求和并发不能造成无故物品复制、漏扣、负库存或错误权限访问。
- **网络与原版状态的边界可描述**：明确原版何时实际接收资源；对无法安全处理的接入点应关闭该能力并记录诊断，不假装成功。
- **按需工作**：日常查询/拖放不触发全量存盘、全库存 `ItemStack` 构造或面向所有客户端的完整快照广播。
- **同一网络所有库存变更必须复用同一套提交/入库管线**；自动化功能以后只增加生产者/消费者适配，不自行修改底层计数。

## 1. 总体结构和所有权

### 1.1 逻辑组件（名称为建议，可映射现有类）

| 组件 | 职责 | 明确不负责 |
|---|---|---|
| `PlayerNetworkDirectory` | `PlayerId → NetworkId`，网络管理员/成员关系，网络存在性和归属检查 | 物品匹配、实际扣料 |
| `StorageNetworkService` | 创建/注销网络、按 ID 取得网络状态、组织成员与库存生命周期 | UI 窗口逻辑、直接操作玩家背包 |
| `NetworkInventory` / `InventoryIndex` | 精确 `ItemKey` 的 `long` 数量、临时预留、搜索分类索引、查询投影 | 判断玩家是否有权操作、客户端通信 |
| `ItemCatalog` | 物品键规范化及轻量元数据（名称、类别、图标引用） | 对所有物品长期保留游戏堆栈对象 |
| `ItemQueryService` | 按真实需求合并发起玩家个人来源与所属网络的可用数量；保留品质/状态过滤 | 向客户端授予扣料权限 |
| `TransactionCoordinator` | 请求去重、校验、预留、提交、取消、网络库存变化和相关修订号 | 推测原版执行已经成功 |
| `GameIntegration` | 对接已验证的原版查询/实际接受物品时点；报告成功、拒绝和实际接收量 | 绕过事务协调器直接增减网络库存 |
| `NetworkSyncService` | 请求响应、视图订阅、修订号、增量或缓存失效通知 | 保存权威全库存到客户端 |
| `PersistenceService` | 正常游戏保存周期的版本化快照、加载、正常关闭保存、脏标记与错误诊断 | 突然崩溃下 WAL 回放、合成订单恢复 |
| `DiagnosticsService` | 统一开关的结构化日志、关键功能状态和耗时 | 默认逐帧/逐个物品打印 |
| `NetworkCommandService` | 服务端管理员维护指令、权限和参数校验、明确结果 | 将服务器管理员等同网络管理员 |

首期**按逻辑职责分层即可**，不要求拆成多个程序集。客户端可以有视图模型/本地查询缓存，但不能另有一份独立权威库存管理器。

### 1.2 权威状态

服务端维护：

```text
WorldNetworkState
  SaveFormatVersion
  Networks: NetworkId -> NetworkState
    AdminPlayerId
    Members: set<PlayerId>
    Inventory: ItemKey -> { Count: long }
    InventoryRevision: long
  PlayerDirectory: PlayerId -> NetworkId
  DirtyFlag / LastSuccessfulSaveInfo

RuntimeOnly
  ActiveRequests / RequestResults (bounded)
  Reservations / RuntimeTransactionStates
  ReservedByNetworkAndItemKey
  MembershipEpochByNetwork
  ViewSubscriptions
  PlayerSessionId / CurrentConnection
  TemporaryFeatureState (e.g. future chain orders, merchant sessions)
```

`PlayerDirectory` 和各网络成员列表必须相互一致；正常保存得到的是同一状态版本的快照。`Reserved` 是运行期账本，可用量按 `Count - Reserved` 计算，但**不写入库存快照**。`MembershipEpoch` 是**建议增加**的运行期权限代际标记，用于使网络变更前发出的请求和旧客户端视图失效；它不是代替服务端实时检查成员关系的授权凭据。

### 1.3 单机/多人统一调用

```text
玩家操作 / 原版消费事件
          |
          v
Client Request Adapter (远程) / Local Adapter (单机或房主)
          |
          v
Trusted Server Context -> 权限 -> 查询/事务/原版接入
          |
          +--> 网络库存状态变更 + Revision
          +--> 原版状态变更结果
          +--> 响应当前请求 + 推送相关视图增量/失效
```

房主操作也必须经过上面的受信任上下文、权限和交易约束；区别可以只是函数调用而非网络序列化。任何由客户端上报的玩家 ID、角色、库存余额及“原版操作已成功”都不能直接视为可信事实。

## 2. 网络身份、成员和权限契约

### 2.1 标识和初始化

- `NetworkId` 使用 GUID（或等价不可复用标识）；字符串显示名和原版实体 ID 均不参与库存定位。
- `PlayerId` 取自游戏/连接上下文提供的**经实测跨重连稳定**的身份标识；具体属性/字段要等目标版本源码验证。
- 玩家首次被服务端确认为本存档中的有效玩家：若目录不存在，则创建独立网络、将其设为唯一管理员并写入玩家映射。
- 同一存档中不得同时创建两个属于同一稳定 `PlayerId` 的默认网络；重复登录/初始化请求应返回既有映射。
- 不同世界/存档使用各自独立目录，不能把同一玩家在不同存档的网络错误复用。

### 2.2 权限矩阵（已定规则，服务端检查）

| 行为 | 网络成员 | 网络管理员 | 服务器管理员 |
|---|---:|---:|---:|
| 查询及普通存取、制作等物流 | 可 | 可 | 不自动继承其他玩家的网络操作权 |
| 邀请在线玩家（阶段 5） | 可 | 可 | 非必然；按专用维护命令管理 |
| 踢出其他成员（阶段 5） | 不可 | 可 | 非普通成员入口 |
| 主动退出网络（阶段 5） | 可 | 不可通过普通退出 | 非普通成员入口 |
| 修改自动交易规则（后续） | 不可 | 可 | 不自动成为网络管理员 |
| 清空/迁移库存、指定网络管理员 | 不可 | 不可 | 可，经维护命令与鉴权 |
| 查询/强关聚合购买会话（后续） | 不可 | 不可 | 可 |

管理员维护命令的授权由游戏服务器管理权限判断，绝不能靠客户端 UI 隐藏按钮实现。阶段 4 先建立权限/成员服务的稳定接口，阶段 5 才接入正式邀请与成员关系交互。

### 2.3 网络关系发生改变时（为阶段 5 预留）

同一个由服务端接受的成员变更操作，应按稳定顺序完成：

1. 锁定/协调受影响的网络成员状态及必要库存；拒绝新旧并发的不合法操作。
2. 使受影响会话的旧访问权限与视图订阅失效；阻止旧请求继续提交。
3. 取消该玩家使用旧网络的活动功能（链式合成、聚合购买等；未实现前保留取消钩子），释放合法预留。
4. 完成新成员映射及必要的库存迁移，再发布新的网络/权限视图。

**注意**：网络合并不等于管理员“搬库存”。前者移动物品且更改网络归属、注销源网；后者只搬物品，源网及成员保留。阶段 4 不需要提供合并 UI，但存储和事务服务不能把两个概念混为同一操作。

## 3. 统一物品查询与交易协议

### 3.1 物品身份与数量规范

1. 使用完整 `ItemKey` 作为权威存储单元；基础物品 ID、名称、类别只用于粗筛/显示。是否允许忽略品质、耐久或改装件应由原版需求适配器表达，存储层不擅自合并。
2. `Count` 和 `Reserved` 使用 `long`；所有加减计算先做非负与溢出验证；`Available = Count - Reserved`，并要求 `0 <= Reserved <= Count`。
3. 凡游戏 API 只接收 `int` 数量，一次对外交付最多 `int.MaxValue`；对需按堆叠上限展开的结果另行逐堆切分。网络 UI 显示可以保留完整 `long`。
4. 不把所有网络物品转换成玩家背包槽位数组；查询返回精确条件下的数量及来源分配，真正向原版交付物品时才构造必要堆叠。

### 3.2 请求与响应（概念字段）

```text
ResourceRequest {
  RequestId,                // 本次用户意图的唯一标识
  ExpectedNetworkId,        // 客户端当前认知的所属网络；服务端必须再确认
  Operation,                 // Query / Withdraw / Deposit / Consume / Transfer / ...
  Requirements,             // 精确需求及合法匹配规则
  ClientViewRevision?,      // 可用于判断视图过期，不是权限凭据
  FeatureContext?           // 操作来源：制作、维修、载具等
}

TrustedRequestContext {    // 仅由服务器构造
  PlayerId,
  SessionId,
  CurrentNetworkId,
  MembershipEpoch,
  Permissions,
  OriginalGameOperationContext?
}

ResourceResult {
  RequestId,
  Status,                   // Committed / Rejected / Cancelled / Pending 等
  AcceptedAmounts?,         // 实际转移/消耗数量，不能只依据计划数量
  NetworkRevision?,
  ErrorCode?,
  ViewInvalidations?
}
```

`SessionId + PlayerId + RequestId` 可作为**运行期**去重键；若同一请求 ID 的内容不同，应拒绝而非复用旧结果。客户端超时仅可用原 `RequestId` 查询/重试同一请求，不能未经确认产生新的“同一意图”。已处理结果只需保存运行期合理的有界时间/数量；重启不回放未完成请求。

### 3.3 交易状态机

```text
NEW
  -> VALIDATED
  -> RESERVED
  -> APPLYING_ORIGINAL_ACTION
     -> COMMITTED       (原版实际接收/操作确认)
     -> CANCELLED       (执行前取消，释放预留)
     -> FAILED          (失败，释放未交付预留并补偿可回退部分)
```

- `Query` 仅给出当时的可用量；**绝不**把查询或 UI 缓存视作未来消费保证。
- 计划阶段标记每个来源的精确物品/数量；普通消费按**发起玩家个人来源优先、不足才用网络**，后续明确了特殊规则的功能可以选择自己的合法来源优先级。
- 原版个人物品及真实容器的读取/修改需在游戏认可的执行上下文进行，且在原版真正接受时重新验证；不尝试长期把原版背包完全复制成网络索引的一个分支。
- 预留仅代表不可被其他网络请求重复使用；实际物品未交付前不得被错误标记为已完成消耗。
- 提交为单次逻辑完成点：网络数量、预留、修订号、入库事件和结果缓存按有序的服务端提交步骤变化；重复提交不重复改变库存。
- 适配器必须给出**实际接受/消耗结果**，包括部分成功数量；接收能力不足可全部拒绝，或按该操作已确认的原版部分接收语义处理，不能偷偷丢弃剩余物品。
- 如果原版状态不可回退，而网络状态提交又失败，先通过序列化执行、充分预检和受控交付边界来避免正常路径中的此种情况；对确实无法保证正确性的入口禁用相关功能并报告，不假设存在万能回滚。

### 3.4 三类操作模板

**A. 纯网络内部操作**（网络到网络、普通库存增减）：验证 → 预留必要来源 → 在同一个服务端协调区间更新 → 发布一次结果/修订；跨网时对两个网络按稳定 ID 顺序取得协调权限，避免死锁。运行时失败不允许只更改一侧。

**B. 玩家/容器与网络互转**：验证源容器中的实物、目标的实际接收能力 → 得到精确可接收量 → 在可信执行上下文进行交接与网络提交 → 返回实际移动量；若原版容器拒绝则释放对应网络预留。插入后的自动出售等逻辑必须是同一次公共入库处理流程的一部分，不能让第二条独立监听器再次消费入库物品。

**C. 原版消费型操作**（制作、维修、加油、换弹）：先根据原版合法需求查询并建计划 → 保留必要网络数量 → 让原版在受控边界接收/执行 → 根据其真实处理量提交或撤销；**交付给原版后不再由网络重复扣一遍**。实际提交时点由该功能的原版语义决定，不能统一假定为“动画完成”或“队列完成”。

### 3.5 统一公共入库管线（为后续自动出售服务）

所有**最终进入公共库存**的物品必须经过一个入口，例如：

```text
AcceptIntoNetwork(network, exactItems, sourceContext, requestId)
  -> ValidateIdentityAndCounts
  -> ApplyEntryChanges / FutureAutoSellRuleEvaluation
  -> SingleCommittedResultAndRevision
```

规定：

- 普通玩家存入、购买入库、订单完成/取消的剩余物返还等都走这个入口。
- 临时订单空间、预留账本和中间产物的内部移动**不算**公共库存入库。
- 将来实现自动出售时，由入库管线**就本次入库内容**执行出售规则，不需要为每个来源再写事件补丁；自动出售规则新建/变更时的既有库存扫描另有显式入口。
- 自动出售若当笔入库直接消费物品，应体现为同一有序交易效果；不先暴露一份可被其他交易拿走的暂态公共库存。若某入口不能同步完成自动规则，要提供同等的隔离保障。
- 入库后的增量通知以**最终提交后的可见库存变化**为准，避免 UI 短暂显示物品又消失。触发器不可因自身产生的变化反复触发自身。

## 4. 并发模型、请求去重与原版交接

### 4.1 推荐的最低复杂度方案

- 以**网络**为主要资源串行化边界：同一 `NetworkId` 的有冲突库存提交依序执行，多个独立网络可以并行。
- 跨网络迁移/合并按固定网络 ID 顺序协调两个网络；真实商人实体锁是未来商人交易自己的**跨网络共享资源锁**，不能仅锁某一个网络。
- 不强制要求所有操作在同一个全局大锁下执行；不得在持有网络锁时进行无上限等待、网络往返或磁盘完整快照。
- 真实玩家背包/容器、工作方块、载具等原版对象的修改需要遵循它们各自的操作权限和执行线程，并与同一操作的网络提交协调。仅靠网络锁**不能**约束所有原版外部状态。

### 4.2 一致性规则

- 同一 `ItemKey` 的网络可用量扣除全部有效预留后，才可供下一次请求使用。
- 交易只在原版操作的结果与网络修订都达到一致的正常完成状态后报告成功。
- 请求失败、取消或玩家权限失效，释放**尚未实际交付**的预留；已经交给原版的物品按原版语义处理，不无条件复制返还。
- `Revision` 是提交后单调增加的库存版本标识。单个逻辑操作可以导致多个 `ItemKey` 的变化，但给客户端呈现的是有确定操作边界的一组变更。
- 已经过期的请求不能因为客户端刚好显示旧网络 ID 就被批准；成员变更优先使旧身份失效。

### 4.3 失败情形与返回码（推荐最小集合）

| 返回类别 | 示例 | 预期处理 |
|---|---|---|
| `Unauthorized` | 玩家被踢出/目标网络不属于自己 | 拒绝、失效旧视图、停止相关功能 |
| `NotEnoughItems` | 多名玩家竞争后网络不够 | 无超额扣除，提示实际不足 |
| `InvalidItem` | 物品键/原版堆叠规则不匹配 | 不扣料，返回原因 |
| `TargetFull` | 背包/容器无法接收 | 拒绝或按原版允许的部分成功量提交 |
| `BusyOrLocked` | 目标工作方块/容器正被使用 | 不越权绕锁，不消耗尚未交付的材料 |
| `StaleView` | 客户端页面或权限代际已过期 | 服务端重验；必要时让客户端刷新 |
| `DuplicateRequest` | 同请求 ID 重放 | 返回原状态/结果，不重新执行 |
| `UnsupportedIntegration` | 无法可靠钩住原版消费边界 | 禁用该接入功能并记录诊断 |
| `InternalFailure` | 正常执行过程意外失败 | 在允许回退的边界撤销并记录可诊断错误 |

不需要为了这些状态建立复杂的持久化任务系统。`Pending` 操作只能在有效的运行期请求会话中存在。

## 5. 客户端查询视图、缓存与增量同步

### 5.1 基本约定

客户端不获取全量 `ItemKey → Count`。服务端持有完整索引，并针对客户端当前的**查询条件 + 排序 + 页号 + 网络 ID**计算视图；客户端保存当前页和必要的轻量元数据（物品键摘要、显示名、图标引用、可用数量、修订标识等）。

建议将响应分成：

- `NetworkSummary`：所属网络 ID、角色、库存修订号、必要的界面统计和权限表现。
- `InventoryPage`：分页后的稳定轻量 DTO、总结果数/页信息、查询修订号。
- `QueryCounts`：配方/弹药等仅需要的小批量聚合计数，始终由服务端真实计算。
- `InventoryDelta`：小范围可精确更新的已变条目、对应修订号。
- `ViewInvalidated`：改变排序、过滤命中或页边界时，通知客户端重新请求当前受影响视图，而非下发所有变更后让客户端全量重新排序。

### 5.2 首次登录、重连及过期页

1. 登录后先获得当前网络 ID、角色和当前修订号；旧网络缓存必须清空或标记失效。
2. 首次打开存储界面只拉必要页面；制作、补货等功能按需请求所需计数，不借用旧的 UI 页面授权。
3. 在**同一次客户端进程**内断线重连时，可尝试复用经服务端确认一致的轻量缓存；跨进程启动没有有效缓存也完全正常，直接按需重新查询。
4. 不保证服务器保存客户端离线期间所有增量历史。修订连续可补时增量补齐；存在缺口、身份/成员变化或无法判断页是否有效时直接重查当前页/必要视图。
5. 新增/删除变体或排序字段改变，可能改变分页边界：不能只原地修改一条记录而留下错误的页内容；这种情况发 `ViewInvalidated` 更稳妥。

### 5.3 广播范围与节流

- 只给**当前拥有访问权**且订阅相关数据的客户端发送差量或失效提示；不向服务器所有玩家广播全网络物品。
- 普通 UI 更新可以合并同一游戏循环内的多条变更；但操作请求的成功/失败回执不应因合并而消失。
- 搜索输入短防抖；翻页请求可根据查询/排序/修订缓存；图标和 Unity 对象的访问只在已验证安全的执行上下文完成。
- 客户端显式执行变更时，可以暂时显示“处理中”，不可把乐观显示值当成真实扣料结果；服务端拒绝后回滚视觉状态或刷新受影响页面。

## 6. 保存与加载：开发期简化版

### 6.1 持久化数据集合

**保存**：网络 ID、管理员、成员、玩家到网络映射、网络公共库存的精确变体及 `long` 数量、网络修订标识、存档格式版本。后续自动交易规则等真正长期配置会随功能加入持久化字段。

**不保存**：客户端当前页、查询缓存、活动请求去重表、短期预留、补货冷却、工作站占用运行时会话、链式合成订单和隐藏订单空间、聚合购买的实时锁与界面会话。

### 6.2 正常保存流程

```text
启动/加载：读取并校验受支持的当前格式 -> 构建索引与玩家映射
运行中：在服务端内存提交交易 -> 递增 Revision -> MarkDirty
正常自动保存：捕获内部一致的快照 -> 写入临时文件 -> 校验/替换 -> 成功才清除对应脏版本
正常关闭：执行最终保存并记录结果
意外进程崩溃：不提供在途事务/订单恢复承诺
```

- 捕获快照时需要保证**同一逻辑版本**的网络库存和身份映射，不能一半是保存前、一半是保存后。实现可以使用短时一致性快照或合适的不可变视图，具体依现有代码/线程约束选择。
- 保存过程中发生新交易，成功写入旧版本快照后**不能误清除新交易的脏标记**。建议记录 `SnapshotRevision` / `DirtyGeneration` 来判断还有没有未保存的新变更。
- 写盘失败保留上一次有效文件和内存中的脏状态，记录错误；正常情况下继续等待后续保存机会。
- 大库存保存不能在普通拖放路径触发全量写盘；保存耗时/分配纳入阶段 6 基准。

### 6.3 脏数据与异常退出边界

已接受的风险：进程突停后，尚未成功保存的网络变更可能丢失；原版玩家/工作方块保存与模组保存的先后可能导致极端的损失或少量复制，不增加 WAL + 跨原版状态恢复协调器。

**未接受的风险**：正常执行时重复请求双扣/双加、正常保存时混合两个不同状态版本、正常关闭无理由跳过最后保存、读档后玩家串网、`long` 溢出造成负数、失败时仍向客户端宣告成功。

## 7. 阶段 1–3 已验收功能的多人化边界

> 这一章只描述**迁移契约与审查清单**，不推测现有代码具体位置。拿到当前实现后应逐个定位查询口、最终扣料口、原版实际接收时点及 UI 依赖，再决定哪些可复用、哪些必须重构。

| 功能/阶段 | 迁移后必须满足的服务端行为 | 留给源码审查 |
|---|---|---|
| 阶段 1：网络窗口、翻页/搜索/分类 | 当前玩家所属网络，服务端分页查询，客户端轻量展示 | 现有 UI 如何拿列表、缓存和图标 |
| 阶段 1：背包/战利品快捷存入 | 验证发起者和真实来源容器、合法数量；个人/原版来源扣除与公共入库协调 | 当前容器事务边界、战利品访问锁 |
| 阶段 1：拖放、取出、右键半堆 | 原版合法堆叠、背包接收能力、源数量及网络事务一致；保持已验收手势 | 具体 UI 事件和原版堆叠 API |
| 阶段 2：配方材料查询/可制作数 | 个人 + 所属网络的真实可用量，保留精确匹配语义；旧缓存不能授权扣料 | 配方及品质过滤实现 |
| 阶段 2：玩家制作队列 | 发起玩家上下文正确；原版接收材料与网络消费只发生一次 | 入队、取消、退款语义 |
| 阶段 2：工作站输入格供料 | 物品真正转到原版输入格时网络不再继续保有它；后续原版消耗不二次扣料 | 输入格、队列、访问锁与熔炉例外 |
| 阶段 3：装备/工具维修 | 原版队列与玩家加成/收益正确；失败取消不重复扣网络物品 | 修理动作何时实际扣料 |
| 阶段 3：建筑修复/升级 | 使用真实操作玩家和被操作的世界方块；原版确认有效才提交相关消耗 | 权限、工具耐久、替换结果 |
| 阶段 3：载具加油/维修 | 真实载具状态与材料同步变化且恰好一次；遵守原版燃料/维修规则 | 原版操作入口、消耗量和失败返回 |

### 7.1 建议的每个适配点检查表

- 谁是发起玩家？可否可信地取得 `PlayerId`、所属网络和相应原版操作上下文？
- 原版第一次做查询、最终接收物品、取消/失败/返还分别在什么时候？
- 是否存在旧的直接 `Add`/`Remove`、UI 自行修改库存或绕过事务入口的分支？
- 个人背包、快捷栏、战利品容器与网络的来源优先级、变体匹配是否保留？
- 是否重复监听同一原版事件，从而在多人服务端和客户端各扣一次？
- 是否会把网络物品误构造成无限背包格子、每帧批量查询或每次打开全量遍历？
- 如果接入失败，是否安全拒绝并能在开启 `DebugLog` 时定位入口与阶段？

## 8. 后续四组功能应复用的基础能力

本章只定义**接口预留点**，详细功能规则以修订版设计文档为准；不提前实现四个完整功能。

### 8.1 补货（第一项新增功能）

- 根据玩家个人配置与该玩家背包/快捷栏的**真实变化事件**生成小范围补货请求；正常登录/初始化/切网不触发。
- 使用统一资源请求将网络物品转到发起玩家现有堆叠；网络不足时快捷栏优先，再按背包从左到右、从上到下，遵循已经确认的范围与顺序。
- 每名玩家独立监听暂停及 `AutoRestockCooldownMs`（默认 1000 毫秒）；冷却期间忽略事件，不排队、不补扫；手动按钮不受冷却限制。
- 不重新实现扣料，只复用交易协调器和原版堆叠兼容规则。

### 8.2 弹药银行（第二项新增功能）

- 原版支持的手持远程武器（枪、弓弩、火箭发射器等）按原版换弹需求供给，不支持部署设备；第三方武器只有能可靠走同一原版机制时才覆盖。
- 一次换弹可按个人背包/快捷栏优先 + 网络补足；原版真实取走弹药后，网络视为已经完成交付，不额外追踪每一发射击。
- 数量显示使用按需/批量查询及轻量缓存；弹药/补货对同一网络数量的争用仍走统一交易。

### 8.3 链式合成（第三项新增功能）

- 临时订单使用**独立运行期空间**，从发起玩家个人来源和网络预留/转入材料；不要把订单空间作为普通网络可见库存。
- 查询计划与分配可复用 `ItemQueryService`，交接/返还使用 `TransactionCoordinator` 及统一公共入库管线；原版玩家队列/真实工作方块由功能专用适配器验证。
- 运行时订单进度只对当前网络有权成员可见；正常取消、离线、踢出时按确认规则回收；服务器意外崩溃不恢复订单，不在启动时扫描临时订单数据。
- 完成的目标物品优先交付发起玩家；待领取目标物在发起者离线时返还网络；非目标剩余物、材料和副产物返回网络。

### 8.4 商人交易（第四项新增功能）

- 自定义虚空出售允许同时使用发起玩家个人来源和网络物品；收益默认入网络、背包不可完全接收时剩余回网络。
- 手动聚合购买按存档内已发现且当前未被占用的现实商人建来源视图；采购先花发起玩家个人公爵币，不足部分用网络，不改变真实来源商人的库存约束。
- 现实商人锁必须是**跨网络共享**的商人实体级协调；聚合会话无自动超时，但支持服务器管理员查询和强制关闭。
- 自动出售通过公共入库管线检查；自动购买按管理员可调整的从上到下顺序运行，在每条执行时重新核算条件、预算与商人来源。游戏时间错过的计划点不补执行。

## 9. 服务器管理员维护指令设计

阶段 4 的服务端维护能力：

| 操作（示意名称，实际命令名后续定） | 输入 | 约束 |
|---|---|---|
| `network-move-items` | 源 `NetworkId`，目标 `NetworkId` | 源与目标不同；仅搬公共库存；源网络和成员保留；正常执行中的双网一致 |
| `network-clear` | `NetworkId`、显式确认 | 仅清空库存，不删网络/成员；清空后刷新订阅视图 |
| `network-player-info` | `PlayerId` | 返回其当前网络和角色 |
| `network-list-players` | 可选过滤 | 玩家 ID、显示名、在线状态、当前网络 ID、角色 |
| `network-set-admin` | `PlayerId`（不输入网络 ID） | 查玩家现属网络，设置唯一管理员，旧管理员降为成员 |
| `trader-sessions`（商人功能阶段实现） | 无/可选过滤 | 列出活动聚合会话、发起者、持锁商人 |
| `trader-force-close`（商人功能阶段实现） | 会话 ID | 强制关闭/拒绝继续交易并释放来源锁 |

所有输入都在服务端解析和鉴权。打印帮助信息时明确区分“服务器管理员”与“网络管理员”。有破坏性的清空及迁移必须写诊断操作摘要，错误或同源同目标不得静默成功。

## 10. 实施分解与当前阶段验收

### 10.1 推荐工作包

| 顺序 | 工作包 | 完成标志 |
|---|---|---|
| A | 目标版本和阶段 1–3 源码盘点 | 列清单：现有库存真相、查询/写入口、PlayerId 来源、原版执行时点，不提前重写 UI |
| B | `NetworkId`、玩家目录、成员/权限服务 | 单机首次进入创建独立网络，重复进入映射稳定；没有串网 |
| C | 服务端库存索引 + 查询接口 | 精确变体和 `long` 正确；对外 `int` 封顶；按需分页/搜索正常 |
| D | 事务协调器 + 原版交接契约 | 请求幂等、临时预留、实际交付量、正常失败/取消均可验证 |
| E | 正常保存/加载 + 脏版本 + 轻量同步 | 断线重连和正常重启数据正确；旧视图失效，普通变更不全量广播 |
| F | 阶段 1 存储操作多人化 | UI 与已验收手势一致；个人网络取放无双扣/双加 |
| G | 阶段 2–3 各已验收消费入口多人化 | 按源码逐个接入统一交易，真实发起者/原版结果正确 |
| H | 管理员基础维护指令、单机与独立网络多人架构回归 | 维护操作正常；能从专用服务器/远程客户端按各自网络运行基础功能 |
| I | 依次实现补货 → 弹药银行 → 链式合成 → 商人交易 | 各功能沿用统一服务，按修订版设计文档逐项验收；不提前实施插件系统 |

工作包是建议依赖顺序，不要求机械拆成等数量的提交或程序集；遇到现有代码结构不同，以减少重构、保持既有行为为原则。

### 10.2 阶段 4 的最低验收场景

**身份与存储**

- 新玩家首次进档创建一个独立网络；重连仍映射同一网络；不同玩家不串库存。
- 精确物品状态/品质不误合并；数量大于 `int.MaxValue` 时 UI 不溢出，游戏 `int` API 只看到合法封顶值。
- 存取、半堆、背包满、战利品容器已变化等情况，按真实接收量处理，无凭空损失或复制。
- 同一请求重复到达不会重复改变库存；失败或网络变更后不误沿用旧授权。

**正常持久化与同步**

- 游戏自动保存、正常关闭、重新加载后，网络库存及玩家归属正确。
- 保存期间继续有交易时，不误清除未保存变更的脏标记。
- 远程客户端只获取必要视图；新增/删除条目引起页面边界变化时视图可正确刷新；断线重连不会把旧页面当成权威。
- 不要求客户端获得整个网络镜像；不要求崩溃后恢复最后未保存交易或临时合成订单。

**现有功能兼容**

- 制作、维修、建筑、载具、工作站供料保持阶段 1–3 已验收的原版行为，真实发起玩家和材料来源正确。
- 原版拒绝、取消或失败时网络不会重复扣料；同一原版接收动作不会被客户端与服务端重复消费。
- 单机和远程客户端通过同一服务端约束；跨网络无权操作被拒绝。

**验收延后说明**

- 阶段 4 不要求朋友参与共享网络测试、不要求邀请/踢出/合并 UI 完成、不要求共享网络下多人并发全面验收。
- 阶段 5 集中覆盖：共享网络成员关系、权限撤销、合并、跨成员资源争用、操作离线取消、服务器管理员恢复场景。

## 11. 诊断与实施风险提示

### 11.1 必须记录的关键诊断（统一 `DebugLog`）

| 阶段 | 推荐字段 |
|---|---|
| 网络初始化 | 玩家 ID 摘要、网络 ID、初建/复用、结果 |

默认关闭调试日志，不输出逐帧或每次图标读取详情；正常错误有足够可定位信息。不要将不必要的玩家私密标识或完整自定义物品数据大量写入日志。

### 11.2 尚需通过代码/运行时验证的技术问题（不是重新讨论功能需求）

1. 稳定玩家 ID 的准确来源，以及房主/远程客户端/专用服务器的上下文差异。
2. 原版个人背包、快捷栏、战利品容器、制作/维修队列、工作站、建筑、载具的**实际消耗/交付时点**与是否允许可靠撤销。
3. 原版执行线程、游戏对象访问和消息处理的安全边界；必要时把状态修改排入被允许的主执行上下文。
4. 旧代码是否存在客户端直接修改权威库存的路径、重复 Harmony 补丁或者绕过入库入口的调用。
5. 10 万精确变体下索引更新、排序和保存的成本；实际采用何种轻量 DTO 与视图失效策略。
6. 后续特性验证：弹药换弹细节、链式工作方块取消能力、未加载的远距离现实商人及原版商人锁接入。**不因这些未验证的 API 问题修改已确认的功能目标。**

## 12. 最终技术取舍摘要

1. **优先保证正常运行行为**，不追求因七日杀/服务器突然崩溃而发生的所有未保存状态的强恢复。
2. **数据权威始终在服务端**；客户端持有轻量展示视图，库存变化提供局部更新或失效重查。
3. **不同功能共用一套资源语义**：完整 `ItemKey`、查询、预留、实际交付、统一入库、幂等结果和诊断。
4. **原版物品交接必须按实际原版行为处理**；网络负责安全供给，不为已经转交的材料增加第二套原版消费逻辑。
5. **阶段 4 为后续共享网络打好结构基础，但不抢先开发阶段 5 的人际交互与测试工作。**
6. **既有阶段 1–3 依实际源码迁移**；本设计刻意不臆测七日杀具体 API，避免凭假设写出错误改造计划。

> 若实施时发现已验收源码与上述某条技术建议冲突，应优先确保已确认的功能行为和正常运行正确性；技术分层、类名与执行细节可以据实调整。新增的用户可见规则应先反映到《设计与实施计划》，技术文档再同步更新。
