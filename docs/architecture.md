# 超维网络：目标架构与功能范围

## 1. 产品目标

超维网络为玩家提供一个随身携带的大型存储网络。**网络内的物品应像玩家携带的物品一样，可被游戏和已适配的模组查询、匹配、预留及消耗。**例如给载具加油、向工作方块供料、制作物品、维修装备、升级建筑方块时，都能使用网络库存；材料匹配必须遵守游戏规则，包括品质等级、改装件、弹药类型等物品差异。

这是一次新模组重写。旧 `DestroyStorage` 的代码和行为只用于盘点功能、寻找游戏 API 接入点，不作为新架构的约束。没有旧存档迁移要求。新项目仍应有自己的数据格式版本，以便未来升级和修复损坏数据。

## 2. 设计原则

1. **统一物品资源接口**：背包、快捷栏和超维网络通过同一查询/交易入口向游戏功能提供物品。
2. **精确保留物品身份**：库存不能只按物品 ID 合并。品质、改装件、耐久、弹药、染色、自定义数据及游戏认可的其他 `ItemValue` 状态都可能决定物品是否可互换。
3. **先计划、再提交**：物品消耗先建立交易计划并预留来源，游戏操作成功后提交；失败或取消时释放预留。避免界面显示可制作但提交时重复扣除、扣错品质或材料丢失。
4. **服务端权威**：多人游戏由服务端裁决库存查询和交易，客户端呈现授权后的视图。正常增量同步不传输完整库存。
5. **按变更工作**：增删物品产生增量事件和日志；不在拖动物品或打开窗口时全量排序、重建背包、保存并重新读取整个库存。
6. **适配器隔离游戏差异**：游戏/模组 API 接入放在独立适配器中。版本检测失败时记录原因并禁用对应适配能力，不让单个补丁使整个存储系统失效。
7. **缓存轻量、事件驱动**：缓存只保存显示需要的轻量元数据和数量快照。快捷栏或库存变化时增量更新受影响的条目；切换武器不全量扫描库存或重建所有武器缓存。

## 3. 领域模型与核心服务

### 3.1 物品身份和数量

定义规范化的 `ItemKey`，由游戏提供或可稳定序列化的完整物品状态构成。实现时应优先复用游戏的 `ItemValue` 相等性/序列化语义；若这些语义无法涵盖模组扩展，则用版本化键格式补充已知字段，并为未知附加数据保留不丢失的表示。对游戏定义为可堆叠的物品，随机生成的 `Seed` 不应导致同一物品拆成无意义变体；其余品质、改装件和自定义数据仍保留。

数量存储使用 `long`，不能假设所有条目都能放进一个游戏物品堆栈。**所有对外提供给游戏的数量都必须限制在 `int32.MaxValue`**：单种物品即使在网络内累计超过该值，配方/工作站/载具等以 `int32` 表示数量的 API 也只能看到最多 `int32.MaxValue`。显示层同样不得将大于 `int32.MaxValue` 的值强转为负数或溢出。每种物品的当前堆叠上限只在展开为游戏 `ItemStack`、工作站槽位或交互结果时查询。

至少区分以下概念：

- **物品种类**：基础物品定义，用于分类及粗略搜索。
- **精确物品变体**：完整 `ItemKey`，用于品质、配方和消耗匹配。
- **可用数量**：总库存减去其他交易已预留的数量。
- **预留数量**：已被在途交易占用、但还未正式扣除的数量。

六级物品示例：配方要求六级扳手时，查询条件必须明确要求品质 6；其他品质的扳手不能满足此条件。若配方允许任意品质，则由配方适配器明确表达允许规则，而不是存储层擅自把品质忽略。

### 3.2 服务边界

- `StorageNetworkService`：网络生命周期、容量策略、成员和权限。
- `ItemCatalog`：规范化物品身份、可读名称、图标和分类元数据缓存。与 Unity/游戏对象有关的数据只在确认安全的线程上访问。
- `InventoryIndex`：按精确 `ItemKey`、基础物品 ID 和可搜索字段建立数量索引；维护已预排序的浏览投影或增量有序结构。
- `ItemQueryService`：按来源、品质、标签、耐久、弹药等条件查询可用物品；返回数量和来源，不制造虚假背包格子。
- `TransactionCoordinator`：计划、预留、提交、撤销以及重复请求去重。
- `PersistenceService`：版本化快照和追加式变更日志；周期性检查点以缩短恢复时间。
- `NetworkSyncService`：服务端权威修订号、交易 ID 和增量变更；完整快照仅用于首次加入、缺失修订恢复或校验失败后的重同步。
- `NetworkPluginService`：管理网络插件槽、安装状态、功能解锁和管理员权限校验。
- `CompatibilityAdapters`：配方、工作站、维修、载具、建筑升级等游戏消费入口的连接层。
- `DiagnosticsService`：可配置调试日志、适配器状态、查询和交易耗时、同步字节数及失败原因。

核心调用形状（概念接口，实施时按目标游戏运行时调整）：

```text
Query(request) -> matching counts + source breakdown
BeginTransaction(request, exact requirements) -> reservation/plan
Commit(transactionId) -> committed result + revision
Cancel(transactionId) -> release reservation
Subscribe(networkId, changeFilter) -> incremental change events
```

查询和变更必须有明确的网络 ID、玩家/服务端上下文及权限检查。任何 UI 结果都不是消耗授权；最终提交时必须重新验证预留和库存修订。

### 3.3 存储索引和界面投影

库存真相以精确变体为单位保存，避免百万条目时把每个物品都作为一个 `ItemStack` 常驻内存。建议由 `ItemKey -> Entry(count, reservedCount, metadataRef)` 主索引提供精确访问，并维护基础物品 ID、分类及规范化搜索文本的辅助索引。

存储界面按页请求投影数据，只为可见格子构造 UI 所需的 `ItemStack`/图标数据；缓存当前查询条件、排序方式和库存修订号。搜索输入做短暂防抖，翻页不重复扫描全部库存。游戏对象和图标的生成/读取需留在游戏线程；纯字符串和数量索引是否可后台处理，必须先验证目标版本的线程规则。

对 10 万种物品的排序，不应放在拖放事件路径上。使用可维护的有序索引，或基于不可变轻量 DTO 生成、并按修订号缓存浏览顺序。分类/搜索索引的重建在加载或显式恢复期间运行并报告进度。

### 3.4 交易和操作语义

资源来源至少包括玩家背包、快捷栏和超维网络。消费计划应遵守统一、可配置且稳定的来源优先级（初始建议先使用背包/快捷栏，再使用网络），并对每个来源和精确变体记录数量。网络数量在 UI 中扣除预留量，防止并发制作、重复点击和多人请求超额使用。

支持两类适配：

- **可查询型**：游戏只检查是否有材料或展示可用数量。适配器把查询转给 `ItemQueryService`，并保留品质等过滤条件。
- **消耗型**：游戏会实际扣除槽位里的物品。适配器把扣除改为交易计划，待原操作成功后提交。对于会异步完成的工作站任务，预留应在任务开始时建立，并在启动失败、取消或完成时按经验证的游戏语义提交/释放。

如果第三方接口只接受具体槽位数组，而没有可靠查询/消耗钩子，不能把无限虚拟格子塞入普通背包数组。应针对该 API 编写版本化适配器，或者明确标记不支持，并给出诊断信息。

所有会消耗资源的适配器（包括弹药换弹）都复用交易协调器的计划、预留、提交和取消能力。工作台多材料扣料和换弹单弹种扣料可以使用不同的适配器，但不得各自实现绕开服务端原子校验的网络库存扣除流程。

### 3.5 网络身份、成员和权限

- 每个网络有持久、唯一且不会复用的 `NetworkId`。建议使用 GUID 或等价的唯一格式；实际编码格式在实现阶段确定。不同网络的库存只能通过显式事务移动，不按名称、玩家实体 ID 或缓存位置推断网络身份。
- 玩家使用稳定的 `PlayerId` 关联当前网络。每名玩家同时只属于一个网络；首次进入存档时创建个人网络，创建者为唯一网络管理员。
- 每个网络只有一名网络管理员，可有多名成员。管理员和成员都可查看、存入、取出、邀请成员，并使用已支持的“网络物品视同携带”物流操作。管理员另有踢出成员权限；成员可主动离开，管理员不可普通离开或踢出自己。
- 邀请即时发送给在线玩家，被邀请者接受后才加入；不为离线玩家创建待处理邀请。加入者成为成员。
- 管理员可通过明确的“合并加入”加入其他网络：先把自己的网络库存合并进目标网络，再注销来源网络并成为目标网络成员。为避免连带迁移成员，来源网络还有其他成员时必须先由他们离开或被移出。
- 成员离开或被踢后立即失去原网络访问权，并得到一个新的空个人网络，成为新网络管理员。已合并到共享网络的物品继续留在原网络，不按贡献者追踪或返还。
- 服务器管理员权限与网络管理员角色分开。维护命令按玩家 ID 或网络 ID 操作，并在服务端鉴权。`set-network-admin <PlayerId>` 不接受网络 ID：服务端解析玩家当前网络，将其设为管理员，并把同一网络其他管理员降为成员。
- 服务器管理员的库存迁移命令只改变物品归属，不改变网络成员或 ID；玩家接受邀请的网络合并同时改变库存和成员关系。这两种事务必须使用不同操作和日志字段。

### 3.6 持久化和多人同步

建议文件布局为版本化快照 + 追加事务日志。交易先通过服务层验证；落盘成功后发布已提交变更和新修订号。若日志写入失败，交易不得对 UI 或网络宣告成功，并需要恢复预留。快照使用临时文件、校验和及原子替换；恢复时验证快照，再重放不重复的日志事务。

多人模式下，服务端是唯一权威库存。客户端发起带唯一交易 ID 的请求，服务端检查玩家当前网络、网络角色、修订号、可用数量和适配规则后提交，再只向该网络的有权成员广播小型增量。过期客户端收到修订缺口时申请该网络快照。成员退出或被踢后，服务端拒绝旧成员身份发来的后续查询和交易请求。

网络合并要可恢复且幂等：验证两个不同的网络 ID，记录迁移操作 ID，按精确物品变体汇总数量并检查 `long` 溢出；目标网络持久化成功后才注销来源网络并发布成员变更。失败时不能产生半份库存；服务重启后可依据事务记录完成或回滚，不能重复加料。

服务器管理员按网络 ID 迁移物品时，目标写入和来源扣除同样作为一个可恢复事务；成功后来源网络和原成员关系仍存在，只是库存变空。清空库存保留网络 ID 和成员关系。任何维护操作均由服务端校验操作者的服务器管理员权限并返回明确结果。

### 3.7 网络插件与功能解锁

- 插件是网络级功能解锁条件。只有网络安装了对应插件，成员和管理员才能使用该插件解锁的网络功能；插件效果和权限在服务端执行时再次校验，客户端缓存和 UI 显示不能作为授权依据。
- 每个网络有专用插件槽。默认槽位数为 10，并支持配置；多人存档由服务端配置决定可用槽数。
- 只有网络管理员可以通过插件界面安装、移除或替换槽位中的插件。成员可使用网络已解锁的功能，但不能修改插件配置。每次插件槽内容变更作为该网络的一笔服务端事务提交，确保槽位状态与物品库存一致。
- 插件槽与普通网络库存分开建模，并保留完整插件物品身份。插件安装/移除时物品如何在插件槽和普通库存间转移、配置缩减时超出槽位的处理、不同插件的依赖/冲突与叠加规则仍需在对应功能确定前细化。
- 网络合并、成员退出或被踢时，插件状态按网络归属处理，不按原成员追踪插件贡献。管理员合并加入时若两个网络都有插件，目标槽位冲突及来源插件的去向需要单独定义。

## 4. 兼容性边界和必须重建的功能

“视同玩家身上”定义为：所有列入支持矩阵、经过验证的消费入口都使用统一资源接口。对没有稳定接入点的第三方模组，不能宣称自动兼容；提供适配 API 和清晰诊断，使后续可增加专用适配器。

### 4.1 核心游戏入口

| 入口 | 目标行为 | 关键正确性条件 |
|---|---|---|
| 配方列表与可制作数量 | 配方可用性与材料数量合并背包/网络 | 按完整配方要求匹配品质、变体、数量和解锁条件 |
| 制作队列/立即制作 | 预留并准确消耗材料，失败时撤销 | 队列数量、并发请求及取消/完成语义一致 |
| 各类工作方块 | 工作站输入材料可来自网络 | 输入格需要实物时只在适配边界临时构造正确堆栈；不重复消耗 |
| 建筑方块升级/维修 | 维修件、升级材料可从网络取得 | 对品质、材料种类、工具和耐久规则精确匹配 |
| 装备维修 | 维修材料可从网络消费 | 维修失败/取消不丢材料，耐久和材料数量按原游戏规则 |
| 载具加油/燃料 | 燃料查询与扣除包含网络 | 燃料类型兼容规则正确，油量变化和物品扣除恰好一次 |
| 载具维修 | 维修材料可从网络消费 | 只有维修成功才提交消耗，重复交互不会重复扣除 |
| 换弹/弹药银行 | 网络安装弹药插件后，枪械按原版所选弹种从网络查询并在换弹流程中使用弹药 | 弹药轮盘与备弹显示包含网络数量；实际换弹走统一资源事务；多人共享扣料准确 |
| 商人购买/交易 | 交易插件解锁手动虚空出售、聚合现实商人购买及自动规则；购买使用真实商人来源，所有商人锁跨网络共享 | 货币/物品扣除与真实商人库存一致；玩家交易、自动交易和服务端交易锁互斥 |
| 拾取、快捷存入/取出 | 服从过滤规则并通过交易服务增删物品 | 背包优先级、超量、黑名单和丢弃规则一致 |

### 4.2 界面和附加功能

计划重新实现并按阶段验证：分类、搜索、排序、分页、数量显示、超维网络窗口和导航栏快捷打开、同时打开背包、从背包/战利品容器快捷存入、玩家/群组存储权限、群组邀请/接受/离开指令、存储规则（阻止拾取/存入即销毁等）、网络插件槽和插件效果、按键配置、标题/所有者显示、多语言，以及适配器状态页面。插件槽默认 10 个、槽位数可配置，插件只能由网络管理员变更；弹药插件解锁网络弹药银行。

附加功能候选包括：按配方依赖链自动合成并填入产物；以及候选清单中的立即制作、立即拆解、立即维修、三核心插件、拆解材料返还、种植加速和模组内说明页。手动与自动补货规则已经确认，见 4.2.3。自动读书和书籍处理因已有类似模组而不再规划。远程箱子链接也已取消：网络本身提供统一库存，链接箱子的收益有限，却需要额外适配箱子扩容模组、容器锁和区块加载/卸载等行为。商人交易的规则已经确认，见 4.2.2；其他功能仍需逐项讨论。这些功能计划在多人开发第一阶段实现，并按本节后文的多人设计要求明确收益、权限和失败/取消语义。

### 4.2.1 弹药银行行为与轻量缓存

- 弹药银行是网络插件解锁的能力。没有弹药插件的网络不向枪械换弹和弹药数量显示提供网络弹药；背包与快捷栏中的实体弹药继续沿用原版行为。
- 武器的可用弹种和当前请求类型由原版武器数据决定。适配器读取枪械当前选择的弹药类型，不另外建立弹匣兼容表或弹药变体匹配规则。
- 快捷栏内容/当前槽变化时，仅检查发生变化的槽位并增量维护远程武器的轻量弹种引用；没有远程武器时不查询网络弹药。切换武器时使用已有缓存，不全量扫描网络或重建所有武器缓存。
- 背包/快捷栏物品变化以及共享网络修订变化会使相关数量标记为过期。备弹 HUD 和弹药轮盘只刷新当前显示武器需要的弹种；多弹种查询按一批请求处理，不能每帧或每个弹种各发一次远程请求。
- 缓存只服务显示和交互响应。按 R 或选择弹种触发实际换弹时，服务端仍要通过统一资源事务重新校验并预留准确的弹药数量；换弹完成后提交，取消时释放预留。枪械已装填弹药与网络备弹分别计数。
- 弹药扣除优先级服从统一资源服务的来源顺序；默认先扣玩家背包/快捷栏实体弹药，再扣网络库存。切换弹种时已装入枪械的旧弹药遵循原版退回背包/快捷栏或掉落行为。
- 特殊发射器、按整弹匣计量的武器、取消/中断换弹以及插件变更与在途换弹的竞态，需要在适配器兼容测试中单独覆盖。

### 4.2.2 出售、聚合商人购买和自动交易

- 网络安装交易插件后才解锁手动出售、聚合商人购买、自动出售和自动购买。只有网络管理员能管理自动规则；服务端执行规则并校验插件状态。
- 手动出售到虚空商人，收益默认进入网络，界面可切换为进入交易发起者的背包。收益按原版售价公式计算并采用发起者的当前交易加成；无有效正售价或原版不可出售的物品不能出售。自动出售收益进入网络，管理员离线时不应用个人加成。
- 自动出售规则按物品身份及品质匹配：精确匹配指定品质，模糊匹配忽略品质，条件模式按品质比较；所有模式均忽略改装件。新增规则触发一次当前库存扫描，入库时检查新增物品，移除规则不扫描。
- 聚合商人目录实时读取网络成员可交易的真实商人商品。每条商品保留商人来源；同物品同价可合并展示，不同价格分开展示。购买真实扣减来源商人库存；购买物品默认进入网络，可切换进入发起玩家背包，并按玩家持久保存偏好。背包满时沿用原版掉落行为。
- 聚合界面打开时，服务端为所有当前可用来源商人持有独占交易锁直到界面关闭或清理。已被原版交易或其他聚合界面占用的商人从本次扫描跳过；来源跨网络共享锁。其他玩家直接访问被占用的实体商人时应由原版锁拒绝。原版 `LockManager` 单次最多锁 5 个目标，来源更多时需实现与 `EntityTrader` 锁请求集成的服务端商人锁协调器，并保证获取来源集合不存在逐个加锁窗口。
- 自动购买可由游戏内计划时间或管理员手动“立即执行全部规则”触发。普通规则包括目标与品质条件、网络物品数量条件、单次购买数量上限、公爵币条件和单次最高花费；条件须全部满足。批量规则面向所有商品或商品类别，不配置单一物品数量阈值，只使用货币和品质条件；支出仍受单次最高花费限制。
- 数量、货币和品质比较支持 `>`、`>=`、`=`、`<=`、`<`。货币条件是启动门槛，单次花费上限是实际支出限制。批量购买按价格从低到高，价格相同按稳定顺序处理。不同现实商人提供的同物品报价保留各自来源，优先购买低价来源。
- 自动购买按原版商人报价与管理员当前有效加成交易；管理员离线时不应用个人加成。计划时间按游戏内时间计算；每个定时点只检查一次，不做失败重试。商人锁仅在执行期间持有，遇到繁忙来源则跳过，执行时再次校验报价、库存和网络余额。
- 手动交易采用实际发起玩家上下文。网络库存、货币及服务器端规则均服务端权威；自动交易没有在线玩家发起者时按网络管理员的规则执行，但管理员离线不读取/模拟其临时个人 Buff。

### 4.2.3 手动与自动补货

- 手动补货提供一个界面按钮，不需要补货插件。按钮从网络向玩家背包的锁定格子和快捷栏中已有的物品堆叠补充物品，直至堆叠达到原生上限或网络中没有可用库存；不在空格中新建堆叠。
- 网络安装补货插件后解锁自动补货。所有成员可使用该能力；插件槽仍只有网络管理员可以变更。每位玩家可在界面中选择补货范围：背包和快捷栏里的全部现有堆叠，或仅锁定格子和快捷栏里的现有堆叠。
- 自动补货监听玩家自己的背包/快捷栏槽位变化，物品种类或数量发生变化时只检查该玩家的目标槽位，不扫描其他玩家。补货按游戏原生堆叠兼容规则匹配；空槽和已经用空的堆叠跳过，不缓存已消失物品的身份，也不恢复空堆叠。
- 每位玩家独立维护自动补货冷却。自动补货处理期间暂停该玩家的监听，处理完成后按服务端配置 `AutoRestockCooldownMs` 进入冷却，默认值为 `1000` 毫秒；冷却期间发生的变化直接忽略，不排队，冷却结束时不补扫，之后恢复监听。补货系统自身对背包的修改不再次触发自动补货。冷却值以毫秒配置，便于精细调整。
- 网络物品扣除由服务端统一原子化处理，与制作、维修和其他网络消费共享并发安全规则。调试日志受统一调试开关控制。

极限性能测试物品定位为开发期诊断工具，默认不进入正式游戏内容。第一阶段提供两个测试物品：普通模式按各物品运行时堆叠上限加入所有物品变体；极限模式对可堆叠物品的每个变体都加入 `int32.MaxValue` 数量，不可堆叠物品仍按其上限加入。对有品质的物品应加入所有支持品质等级，而不是只选随机等级；读取物品专属品质上限，无法探测时记录回退诊断。测试记录条目数、变体数、构造/持久化耗时和总耗时。调试日志配置默认关闭；本机开发部署配置开启。汇总日志避免逐物品刷屏。

### 4.3 后续功能的多人设计要求

其他功能从多人开发第一阶段起逐项实现。每项功能开始编码前，应先明确：

1. 谁发起操作，以及服务端如何确认发起者和当前网络。
2. 是否读取或消耗共享网络物品；扣除规则和优先级是什么。
3. 产物、货币、阅读/解锁进度等收益属于发起者、网络管理员还是共享网络。
4. 异步、定时或后台操作由谁配置和负责；发起者离线、成员离开/被踢、失败、取消或重试时如何处理。
5. 多人同时操作同一资源时如何预留、排序和避免重复执行。

对没有明确玩家发起者的自动功能，必须先定义规则所有者和收益归属；不得默认为服务器本地玩家或任意在线成员。玩家个人进度必须按实际受益玩家判断，即使使用的物品来自共享网络。

插件解锁的功能还必须验证网络当前插件状态。插件槽内容变更由单一网络管理员发起并由服务端串行提交；功能交易开始后若管理员移除对应插件，应依据该功能定义的预留语义完成或取消，不得让客户端的旧缓存继续授予功能权限。

## 5. 第三方模组兼容策略

1. **公开适配 API**：提供查询请求、精确物品要求、交易生命周期、网络权限和变更订阅的稳定接口；接口有版本号。
2. **适配器能力声明**：每个适配器标记“只查询”“查询+消费”“异步队列”“多人安全”等能力，运行时检测游戏/模组版本和目标方法。
3. **窄范围补丁**：Harmony 补丁只挂接最小消费入口，按目标版本验证签名/返回值。优先在方法边界转换请求，不反复扫描所有 UI/背包对象。
4. **明确降级**：方法缺失或冲突时，禁用该适配器的相关能力并记录版本、类型、方法、失败阶段；不伪造成功结果。
5. **兼容矩阵**：逐一记录游戏版本、模组版本、补丁命中情况、查询、消费、失败回滚及多人行为。不要只用“能加载”作为兼容结论。
6. **扩展样例**：提供第三方模组作者如何查询网络、预留材料、提交或撤销的最小示例和调试说明。

## 6. 可观测性与性能验收

配置至少包含 `DebugLog=false`。开启后使用统一前缀和结构化字段：玩家/网络 ID（可脱敏）、修订号、交易 ID、适配器名、物品键摘要、数量、阶段、耗时和异常。日志不得默认输出每种物品或每帧事件。

性能基准需要覆盖 1 千、3 万和 10 万种精确物品变体，另测同一种物品的大数量堆叠及单变体超过 `int32.MaxValue` 的对外查询。基准项目包括载入、首次打开、搜索/过滤/排序、翻页、拖放、并发消费、保存/恢复以及多人增量同步。记录 P50/P95 耗时和内存分配；阈值应在目标游戏构建和目标机器上测定后固定。

必须满足的架构约束：拖放和普通查询路径不触发完整磁盘保存、完整库存读取或全量 `ItemStack` 构造；单条变更不向所有客户端广播完整快照；查询与消费遵循同一套精确匹配语义。
