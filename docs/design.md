# 超维网络：设计与实施计划

本文记录已确认的阶段安排、功能规则、技术架构和范围决定。尚未确定的内容会标注为待讨论，不视为已承诺实现。

## 路线图与功能设计

### 当前状态

阶段 1、2、3 已验收，下一步进入多人开发第一阶段。所有新增物流功能从设计时考虑多人语义。模组定位为物流，不规划地面物品自动吸附、存储过滤/自动拾取、即时制作/拆解/维修、材料返还或种植加速。UI 随功能逐项设计。插件系统是可选扩展，基础物流不依赖插件。跨版本适配层和公开 API 为低优先级可选方向；当前优先保持关键流程有统一开关控制的诊断日志，未来遇到版本变化时按日志定位问题。

多人开发第二阶段包含成员关系操作和最终多人验收。朋友参与的多人测试统一安排在其他功能完成后，减少反复占用朋友时间。

### 阶段 0：目标版本和接入契约

开发时持续核实目标游戏版本和运行时约束。首期面向当前目标版本直接接入原版 API；通用跨版本适配层和公开 API 不作为近期前置工作，可在未来确有多版本支持需求时评估。旧 `DestroyStorage` 只用于盘点功能与补丁入口，不作为新实现契约。

### 已验收功能

| 阶段 | 已验收范围 |
|---|---|
| 1：存储原型 | 导航栏打开网络、背包/战利品快捷存入、拖放存取、分页/搜索/分类、长数量存储及开发压力测试物品。网络右键取半堆时先按物品堆叠上限封顶；背包 Shift+右键存入半堆，网络 Shift+右键取出半堆。 |

| 3：维修、建筑与载具 | 装备/工具原版维修队列、建筑块修复/升级、载具燃料与维修使用网络材料。 |

### 阶段 4：多人开发第一阶段——服务端基础、既有功能多人化和其他功能

#### 网络与交易核心

- 每个网络具有持久、唯一、不会复用的 `NetworkId`；建议采用 GUID 或等价的全局唯一格式。所有库存操作明确指定网络 ID，不按显示名称或临时实体 ID 混用库存。
- 使用稳定玩家 ID 记录玩家当前所属网络。玩家首次进入存档时得到自己的独立网络，并作为该网络唯一管理员。
- 服务端拥有网络库存、成员关系和交易结果的最终权威。客户端请求查询/变更并显示服务端确认后的状态。
- 交易具备唯一 ID、网络修订号和可恢复的持久化语义，重复请求不能重复扣料或加料；多人同时消费时不能超额使用。
- 插件系统作为可选扩展；不启用插件时基础存储和物流仍可使用。若启用，插件槽默认 10 个且由服务端配置；只有网络管理员可安装、移除或替换插件，成员与管理员均可使用已启用的扩展功能。
- 已验收阶段 1–3 的界面存取、制作、工作站、装备维修、建筑修复/升级、载具燃料/维修都接入服务端请求流程。操作要保留发起玩家上下文，区分共享材料与玩家个人收益/进度。
- 已确认及后续新增的物流功能都在本阶段设计和开发；每项功能都明确操作者、共享库存影响、收益/进度归属及失败、取消、断线和重试语义。

#### 服务器管理员控制台指令

服务器管理员权限与网络内“管理员/成员”角色是两种不同权限。以下维护指令只允许服务器管理员执行，并在服务端检查参数和权限：

1. 按源网络 ID 和目标网络 ID 迁移库存物品。此操作只搬库存，不改变网络成员关系或网络 ID；成功后源网络保留为空。
2. 按网络 ID 清空库存。网络 ID 和成员关系保留；建议要求显式确认参数。
3. 按玩家 ID 查询其当前网络 ID 和网络角色。共享网络中的玩家返回同一个网络 ID。
4. 列出当前存档中已知玩家的玩家 ID、显示名称、在线状态、当前网络 ID 和角色。
5. 按玩家 ID 设置网络管理员，不接收网络 ID 参数。服务端先查该玩家当前所属网络，将其设为管理员，并将同网络其他管理员降为成员；不影响其他网络。

库存迁移和玩家加入网络是不同操作：维护指令只迁移物品；成员加入会改变成员关系，并按第二阶段规则注销来源网络。

#### 本阶段验收边界

开发期间构建并回归已验收的单机流程。最终的多人游玩验收延后到多人开发第二阶段，并等所有新增物流功能完成后集中进行。

### 阶段 5：多人开发第二阶段——成员关系、UI/玩家指令与集中验收

#### 邀请和成员规则

- 邀请即时发送，只能邀请当前在线玩家；不创建面向离线玩家的待处理邀请。
- 网络管理员和成员都能邀请别人；受邀玩家必须接受后才加入，加入者初始为成员。
- 一个玩家同一时刻只属于一个网络。成员要换网时先退出当前网络，再接受目标网络邀请。
- 成员可主动退出；网络管理员不能普通退出，也不能踢出自己。管理员可以踢出成员。
- 网络只有一个管理员。管理员可通过明确的“合并加入”操作加入别人网络，个人网络物品并入目标网络，原网络注销，玩家降为目标网络成员；个人网络还有其他成员时，先由他们离开或被移出。
- 成员退出或被踢后，立即失去原网络访问权并得到一个新的空网络，成为新网络管理员。此前的共享库存留在原网络，不按存入者返还。
- UI 和玩家指令共用服务端成员/权限服务。踢出、退出或加入完成后，旧界面和进行中的请求不能继续操作旧网络。

#### 最终多人验收

朋友参与的多人验收等所有新增物流功能完成后集中进行，覆盖：

- 各玩家私人网络隔离；网络 ID 稳定且不同网络库存不串联。
- 管理员/成员邀请、接受、退出、踢出、网络管理员恢复和合并加入。
- 合并中断、服务器重启、重复请求和存档恢复不会重复加物品或丢物品。
- 多名玩家并发取出或消耗材料时，库存和修订保持一致。
- 阶段 1–3 及新增功能在多人下的发起者、受益玩家、库存扣除和失败回滚正确。
- 离线重连后成员关系与网络 ID 正确；已离线玩家不可接收新邀请。

多人测试的实际执行放在此阶段末尾，不要求朋友参与每个功能的开发迭代。

### 已确认功能设计与范围决定

以下已讨论的物流功能计划放入多人开发第一阶段逐项实现。商人交易不参考旧模组设计。

#### 弹药、换弹和弹药银行

**已确认的行为：**弹药银行作为网络插件，只有安装了弹药插件的网络才能把网络弹药提供给枪械换弹和弹药数量显示。弹种与当前选择由枪械原版数据决定；适配器按枪械请求的弹种处理，不另外实现弹匣或弹药变体兼容匹配。弹药会在换弹请求中通过统一资源事务预留/扣除，不按每发射击单独请求网络库存；已装入枪械的弹药仍由原版枪械弹匣机制消耗。背包/快捷栏实体弹药优先，网络库存作为后续来源。

**显示与缓存：**缓存保持轻量和增量更新。快捷栏变化时只检查变化槽位；切换武器不全量重建缓存。快捷栏中没有远程武器时不查询网络弹药；背包变化和共享网络修订变化时使相关数量缓存过期，HUD/弹药轮盘按当前显示武器刷新。弹种数量可批量查询，但不可逐帧或按每种弹药分别发远程请求。显示缓存不参与扣料授权。

**仍需实现时验证：**按整弹匣计量的武器、发射器、换弹取消/中断、弹种切换时已装弹药退回的原版行为，以及管理员移除弹药插件时在途换弹的处理。

#### 网络插件系统

**已确认的基础规则：**插件系统是可选扩展，基础存储和物流不依赖插件；网络功能可通过独立插件开关解锁，弹药银行由弹药插件解锁。每个网络有专用插件槽，默认 10 个，槽位数量由服务端配置决定。插件槽内容由网络管理员独占变更权限；成员可使用网络已解锁的功能，但不能安装、移除或替换插件。插件状态由服务端权威保存和检查。

插件槽内容变更与库存变化作为网络事务处理，服务端串行提交；管理员唯一写入权限减少多个成员同时改槽冲突，但不会替代服务端校验。具体插件效果、插件之间的依赖/冲突、槽位配置缩减后超出容量的处理，以及网络合并时插件槽物品/状态的迁移规则，在逐项功能设计时确定。

#### 手动与自动补货

- 手动补货提供一个界面按钮，不需要补货插件。点击后，从网络库存向玩家背包的锁定格子和快捷栏中已有的物品堆叠补充物品；只补到游戏允许的堆叠上限，直到目标堆叠满或网络库存不足，不在空格中新建堆叠。
- 网络安装补货插件后，所有成员均可使用自动补货；插件安装、移除和替换仍只有网络管理员可以操作。补货范围由每位玩家在界面中设置：补充背包和快捷栏中的全部现有堆叠，或仅补充锁定格子与快捷栏中的现有堆叠。
- 自动补货只响应发生变化玩家自己的背包/快捷栏格子；物品种类或数量变化时只检查该玩家的目标格子，不扫描其他成员。共享网络扣料由服务端通过统一原子化资源交易处理，确保并发补货不会重复扣料。
- 补货按游戏原生堆叠兼容规则匹配物品。空格以及已经用空的堆叠都跳过；不保存空格的物品记忆，也不尝试恢复已用空的堆叠。
- 自动补货处理期间暂停该玩家的监听，处理完成后进入独立冷却期。`AutoRestockCooldownMs` 为服务端可配置的毫秒数，默认 `1000`。冷却期间忽略该玩家背包/快捷栏变化，不排队，也不在冷却结束时补扫；冷却结束后重新启用监听。补货系统自身对背包的修改不再次触发自动补货。日志遵循统一调试开关。

#### 出售和商人交易

**插件与多人归属**

- 手动出售、聚合购买、自动出售和自动购买均由网络的“交易插件”解锁；未安装插件的网络不能使用这些功能。
- 自动出售/购买规则仅网络管理员可创建、修改和删除。管理员在线时自动交易可应用其当下有效的原版交易加成；管理员离线时不应用个人加成，使用基础价格/商人报价。手动交易使用实际发起玩家的有效加成。
- 服务器是网络库存、货币和自动规则执行的权威方。并发扣除网络货币、物品或交易库存时走统一服务端交易协调；自动操作不归属任意在线玩家。

**手动出售**

- 出售给不对应任何现实 NPC 的虚空商人。支持多人同时出售；所选物品和网络货币变化由统一原子交易处理。
- 售价默认进入共享网络；交易界面允许切换为进入打开该界面的玩家背包。交易按游戏的物品售价和虚空商人默认出售比例计算，并使用发起玩家的原版出售加成；不读取某个现实商人的库存或专属价格覆盖。
- 遵守原版可售条件。物品不可出售标记或基础/最终计算售价不大于 0 时，不能手动出售或被自动出售。品质、耐久状态、经济价值、出售比例、全局交易价格设置和适用的交易加成按游戏售价公式处理。

**自动出售**

- 管理员通过自动出售界面指定要出售的物品与品质规则。匹配方式只判断品质等级，不判断改装件：精确匹配指定品质；模糊匹配忽略品质；条件匹配使用品质比较符 `>`、`>=`、`=`、`<=`、`<`。品质条件不匹配没有品质等级的物品。
- 新增或更改/添加出售标记时，对网络库存做一次全量匹配扫描并出售现存匹配物品。移除规则不触发扫描。
- 新物品进入网络时只检查该物品及受影响规则；符合规则且可售时立即出售，收益进入网络。物品被同一笔存入/出售交易消费，避免存入后重复触发。
- 没有正售价或原版不可出售的物品跳过，不产生出售收益。

**手动聚合购买**

- 网络购买入口实时扫描网络成员可交易的现实商人，并把当前商品聚合到一个与原版购买相同操作习惯的界面。购买仍实际向对应商人交易并减少该商人的真实库存；聚合视图不是虚构商店。购买后商人库存与玩家前往该商人时一致。
- 商品记录始终保留来源商人和报价。同一物品、同一价格可以合并显示并汇总可买数量；同一物品不同价格分开展示。手动购买使用打开界面的玩家作为交易发起者，按该玩家的有效购买加成计算。
- 购买目标默认进入网络；发起者可切换为进入自己的背包，选择按玩家持久保存。背包满时沿用原版行为，将购得物品掉落到地上。
- **商人互斥锁：**聚合购买打开时，服务端扫描并锁定所有当前可用的商人来源，锁在界面关闭、取消、玩家离线或操作失败清理时释放。扫描跳过已被原版交易或其他聚合购买占用的商人；若仍有可用来源则展示这些来源，若没有可用来源则提示所有商人繁忙。
- 锁定按现实商人实体生效、跨网络共享。聚合购买占用期间，其他玩家从普通商人界面发起交易时由原版交易锁拒绝并显示原版拒绝提示。不同网络也共享同一商人锁状态。
- 原版 `LockManager` 单次锁请求最多支持 5 个目标。若可交易商人来源超过此限制，实现时使用服务端商人锁协调器，并让原版 `EntityTrader` 交易锁请求识别该协调器占用、按原版方式拒绝交互；不得逐个加锁形成未锁住全部来源的竞态窗口。

**自动购买**

- 管理员可配置自动购买规则，也可点“立即执行”一次运行全部规则。定时触发与手动执行都立即检查规则；手动执行不等下一个定点。
- 普通规则包含目标物品/品质匹配、当前网络库存数量及比较条件、单次最大购买数量、当前网络公爵币及比较条件、单次最高花费（默认无上限）和计划时间。库存数量条件与公爵币条件均为触发门槛，条件全部满足才执行；单次最高花费单独限制实际支出。
- 品质匹配只判断品质等级，不判断改装件：精确匹配指定品质、模糊匹配忽略品质、条件匹配使用 `>`、`>=`、`=`、`<=`、`<`；设置品质条件时无品质等级物品不匹配。
- 批量规则可购买所有商品、某个商品类别等一组商品，不设置单一商品的库存数量阈值/条件，只检查公爵币条件和品质购买条件。单次最高花费仍适用；预算不足时按报价由低到高购买，价格相同则按稳定顺序处理。
- 自动购买的商品来自网络成员可交易的现实商人，不向虚空商人购买。同物品有多个来源报价时优先购买便宜来源；不同价格作为不同报价保留。交易消耗该现实商人的库存，并按当前商人报价与管理员加成结算。
- 计划时间按游戏内时间计算。时间为每天 5 点、间隔 2 天时，从下一游戏日 5 点开始，之后每隔两个游戏日检查一次。每个定时点只检查一次，不重试；条件不满足、来源繁忙或交易失败后等待下一个定时点或管理员手动执行。
- 每次自动购买只在实际执行期间锁定将交易的商人，完成、失败或取消后释放锁。占用中的来源跳过；手动界面已锁住所有商人时不等待，不重试。执行时重新验证可用库存、报价和网络余额，不能只依赖打开界面或上次扫描时的缓存。

**执行条件比较符**

数量、货币和品质的条件统一支持 `>`、`>=`、`=`、`<=`、`<`。货币条件只判断本次规则是否启动，不代表需要保留的最低余额；实际最高支出由单次最高花费和可用余额共同限制。

#### 自动化链式合成

**目标与计划**

- 玩家从原版追踪的目标配方启动合成链并指定目标数量。网络只负责分析配方依赖、预留/转送材料、安排实际工作方块和追踪订单；不模拟或伪造合成结果。每一份产物都必须由原版玩家制作队列或真实工作方块产出。
- 先使用网络中已有的精确匹配物品。已有数量足够时不再拆解该物品的配方；不足时只递归计划缺少的数量。未解锁的配方不参与候选，视为不可合成资源；如果玩家拥有该资源则可直接使用，否则作为基础材料缺口报告。
- 有多个已解锁配方时，玩家可从可用方案中选择。自动选择时优先选出基础材料可满足、依赖配方可展开且执行条件可满足的方案；仍有多个可用方案时按稳定的配方顺序选择。计划中的替代配方同样遵守解锁和工作方块可用性限制。
- 启动前先完整规划依赖图，核对全部基础材料、配方解锁、执行权限和每一步工作方块条件，并原子预留订单材料。任一环节无法启动就拒绝整张订单，说明缺少的材料或工作方块/设备条件，不留下半启动的订单。

**配方和工作方块可用性**

- 配方选择界面只展示玩家已解锁且存在可用执行路径的方案。工作方块搜索使用固定半径配置 `CraftingWorkstationSearchRange`，默认 `64` 米；只扫描当前已加载区块，不主动加载区块。玩家背包制作作为独立执行路径，仅在原版允许该配方由玩家制作且能够可靠追踪队列时计入。
- 工作方块必须与配方的 `craft_area` 等原版要求兼容，并且玩家拥有原版允许的访问/操作权限。尊重游戏的锁、密码及 BeyondStorage3 同类访问检查；仅位于某个领地范围内不自动代表拥有操作权限。
- 已在制作、被原版交易/访问锁占用、被另一张订单预留、超出搜索范围或位于未加载区块的工作方块不计为可用。服务端为在途订单协调工作方块预留，防止不同玩家或网络同时将同一设备分配给多张订单。
- 范围内的原版玩家制作、工作台、水泥搅拌机、篝火和化学合成站使用各自原生队列与输入/输出行为。具体适配器必须能识别任务归属、取回对应产物，并安全取消该订单的任务；无法做到时不把该工作方块作为可用执行路径。
- 锻造炉按其特殊机制处理：不由网络向熔炉输入槽送料。计划检查炉内配方所需的熔炼资源、可用配件/解锁条件以及是否有足够燃料开火；满足后由原版锻造炉执行配方。其他需要燃料的工作方块沿用其原生送料和燃烧机制，不由链式合成自动补燃料。
- 第三方工作方块以后按适配器逐个支持。适配器必须能安全定位和追踪精确任务；没有可靠任务识别/取消能力时，隐藏相关执行选项并说明不支持，不能用“按配方取消”误取消其他玩家的任务。

**并行、订单隔离与多人语义**

- 一个配方的制作批次可在玩家制作队列及多个当前可用的同类工作方块间并行分配。先排除忙碌和已预留设备，再将整数制作批次尽量平均分配到剩余执行路径；余数按稳定顺序分配。不同配方只在依赖已满足的同一可执行层并行启动。
- 整张订单所需网络物品及已取回的中间产物进入该订单独立的隐藏订单空间，不再被其他网络成员查询、取出或预留。每张订单固定关联发起玩家、所属 `NetworkId` 和唯一订单 ID；工作方块实际执行使用发起玩家上下文，以应用其对应的制作加成。
- 工作方块完成后，只有在网络成功取回真实产物并放入订单空间后，该步骤才算完成；之后才把中间产物发往后续步骤。订单状态展示当前步骤、耗时、绑定的工作方块和异常信息。Shift+左键点击步骤可短暂高亮对应世界中的工作方块。
- 网络成员可查看该网络的订单进度；只有订单发起者或网络管理员可以取消订单。订单及材料预留状态持久化；恢复时不得重复启动已提交的工作任务。发起者离开或被踢时取消其订单，不能把订单转移到其他网络。

**取消、故障和交付**

- 发起玩家离线时取消其订单，不暂停等待重连。玩家手动取消、发起者离线或订单追踪失败时，对每个已登记的真实任务最多尝试取消一次；收回可可靠取回的工作方块材料与产物，再将订单空间内可回收物品退回原网络。
- 区块卸载导致任务无法追踪时按订单失败处理，不等待区块重载后再次取消。若工作方块拒绝取消或仍持有无法取回的物品，不再重试；记录工作方块位置、配方和已知物品并向玩家报告，由玩家自行处置。
- 可检测到的燃料耗尽/停火等情况向订单发起者发出警告，不自动加燃料。锻造炉或其他设备的内部异常导致无法继续时显示设备和已知条件；无法判断或追回的工作方块内部状态不伪装成成功。
- 完成产物默认交给发起玩家。背包空间不足时将剩余产物保留在订单空间并显著标记为待领取，不掉落到地上；领取后才清理已空订单空间。
- 合成链的计划、预留、工作方块分配、开工、取回、取消和异常均记录受统一 `DebugLog` 控制的结构化诊断；常规关闭日志时不向玩家刷屏。

#### 模组范围与后续优先级

- 存储网络是玩家主动管理的物流系统，不设计地面物品自动吸附、自动拾取、入库自动销毁等存储规则。
- 即时制作、即时拆解、即时维修、拆解材料返还和种植加速不属于物流模组范围，不进入功能候选。
- 远程箱子链接、自动读书和书籍处理已从规划中移除。
- UI 随功能逐项设计与实现，不要求在功能开发前统一定稿全部窗口、快捷操作和说明页面。
- 插件系统是可选扩展；基础存储与物流功能在插件系统未启用时仍可使用。若使用插件，现阶段按独立功能开关设计，不预设复杂插件依赖或冲突关系。
- 跨版本适配层、核心逻辑与游戏 API 解耦、存档物品身份迁移和公开 API 属于低优先级可选工作，不阻塞当前功能。开发期为关键流程记录统一开关控制的诊断日志，遇到游戏更新问题后按具体日志和失败阶段修复。

### 阶段 6：性能和发布验证

- 对 1 千、3 万和 10 万精确物品变体做基准，包含单变体超出 `int32.MaxValue` 的数量；记录 P50/P95 和内存分配。
- 完成单机、多人和目标常见模组组合的最终兼容矩阵。多人实测遵循阶段 5 的集中安排。
- 验证持久化恢复、强制退出、重复交易请求、日志开关、补丁缺失、异常物品数据及网络延迟。
- 发布包与开发工作区、缓存和本地测试数据分开。

**发布验收**：核心消费没有误匹配或重复扣除；各适配器能力可诊断；普通查询/拖放不触发全量磁盘读写或全量 `ItemStack` 构造；单条库存变更不向所有客户端广播完整快照。


## 技术架构

### 1. 产品目标

超维网络为玩家提供一个随身携带的大型存储网络。**网络内的物品应像玩家携带的物品一样，可被游戏和已适配的模组查询、匹配、预留及消耗。**例如给载具加油、向工作方块供料、制作物品、维修装备、升级建筑方块时，都能使用网络库存；材料匹配必须遵守游戏规则，包括品质等级、改装件、弹药类型等物品差异。

这是一次新模组重写。旧 `DestroyStorage` 的代码和行为只用于盘点功能、寻找游戏 API 接入点，不作为新架构的约束。没有旧存档迁移要求。新项目仍应有自己的数据格式版本，以便未来升级和修复损坏数据。

### 2. 设计原则

1. **统一物品资源接口**：背包、快捷栏和超维网络通过同一查询/交易入口向游戏功能提供物品。
2. **精确保留物品身份**：库存不能只按物品 ID 合并。品质、改装件、耐久、弹药、染色、自定义数据及游戏认可的其他 `ItemValue` 状态都可能决定物品是否可互换。
3. **先计划、再提交**：物品消耗先建立交易计划并预留来源，游戏操作成功后提交；失败或取消时释放预留。避免界面显示可制作但提交时重复扣除、扣错品质或材料丢失。
4. **服务端权威**：多人游戏由服务端裁决库存查询和交易，客户端呈现授权后的视图。正常增量同步不传输完整库存。
5. **按变更工作**：增删物品产生增量事件和日志；不在拖动物品或打开窗口时全量排序、重建背包、保存并重新读取整个库存。
6. **控制接入边界**：首期按当前目标游戏版本直接接入原版 API，尽量让核心服务职责清晰。完整跨版本适配层/核心解耦是低优先级可选项，不作为近期架构改造前置；游戏更新时优先依靠关键流程诊断日志定位并修复受影响入口。
7. **缓存轻量、事件驱动**：缓存只保存显示需要的轻量元数据和数量快照。快捷栏或库存变化时增量更新受影响的条目；切换武器不全量扫描库存或重建所有武器缓存。

### 3. 领域模型与核心服务

#### 3.1 物品身份和数量

定义规范化的 `ItemKey`，由游戏提供或可稳定序列化的完整物品状态构成。实现时应优先复用游戏的 `ItemValue` 相等性/序列化语义；若这些语义无法涵盖模组扩展，则用版本化键格式补充已知字段，并为未知附加数据保留不丢失的表示。对游戏定义为可堆叠的物品，随机生成的 `Seed` 不应导致同一物品拆成无意义变体；其余品质、改装件和自定义数据仍保留。

数量存储使用 `long`，不能假设所有条目都能放进一个游戏物品堆栈。**所有对外提供给游戏的数量都必须限制在 `int32.MaxValue`**：单种物品即使在网络内累计超过该值，配方/工作站/载具等以 `int32` 表示数量的 API 也只能看到最多 `int32.MaxValue`。显示层同样不得将大于 `int32.MaxValue` 的值强转为负数或溢出。每种物品的当前堆叠上限只在展开为游戏 `ItemStack`、工作站槽位或交互结果时查询。

至少区分以下概念：

- **物品种类**：基础物品定义，用于分类及粗略搜索。
- **精确物品变体**：完整 `ItemKey`，用于品质、配方和消耗匹配。
- **可用数量**：总库存减去其他交易已预留的数量。
- **预留数量**：已被在途交易占用、但还未正式扣除的数量。

六级物品示例：配方要求六级扳手时，查询条件必须明确要求品质 6；其他品质的扳手不能满足此条件。若配方允许任意品质，则由配方适配器明确表达允许规则，而不是存储层擅自把品质忽略。

#### 3.2 服务边界

- `StorageNetworkService`：网络生命周期、容量策略、成员和权限。
- `ItemCatalog`：规范化物品身份、可读名称、图标和分类元数据缓存。与 Unity/游戏对象有关的数据只在确认安全的线程上访问。
- `InventoryIndex`：按精确 `ItemKey`、基础物品 ID 和可搜索字段建立数量索引；维护已预排序的浏览投影或增量有序结构。
- `ItemQueryService`：按来源、品质、标签、耐久、弹药等条件查询可用物品；返回数量和来源，不制造虚假背包格子。
- `TransactionCoordinator`：计划、预留、提交、撤销以及重复请求去重。
- `PersistenceService`：版本化快照和追加式变更日志；周期性检查点以缩短恢复时间。
- `NetworkSyncService`：服务端权威修订号、交易 ID 和增量变更；完整快照仅用于首次加入、缺失修订恢复或校验失败后的重同步。
- `NetworkPluginService`：管理网络插件槽、安装状态、功能解锁和管理员权限校验。
- `GameIntegration`：配方、工作站、维修、载具、建筑升级等游戏消费入口的接入职责。首期可在现有程序集内保持逻辑分层，不要求立即拆分独立适配器程序集。
- `DiagnosticsService`：可配置调试日志、适配器状态、查询和交易耗时、同步字节数及失败原因。

核心调用形状（概念接口，实施时按目标游戏运行时调整）：

```text
Query(request) -> matching counts + source breakdown
BeginTransaction(request, exact requirements) -> reservation/plan
Commit(transactionId) -> committed result + revision
Cancel(transactionId) -> release reservation
Subscribe(networkId, changeFilter) -> incremental change events
```

查询和变更必须有明确的网络 ID、玩家/服务端上下文及权限检查。任何 UI 结果都不是消耗授权；最终提交时必须重新验证预留和库存修订。

#### 3.3 存储索引和界面投影

库存真相以精确变体为单位保存，避免百万条目时把每个物品都作为一个 `ItemStack` 常驻内存。建议由 `ItemKey -> Entry(count, reservedCount, metadataRef)` 主索引提供精确访问，并维护基础物品 ID、分类及规范化搜索文本的辅助索引。

存储界面按页请求投影数据，只为可见格子构造 UI 所需的 `ItemStack`/图标数据；缓存当前查询条件、排序方式和库存修订号。搜索输入做短暂防抖，翻页不重复扫描全部库存。游戏对象和图标的生成/读取需留在游戏线程；纯字符串和数量索引是否可后台处理，必须先验证目标版本的线程规则。

对 10 万种物品的排序，不应放在拖放事件路径上。使用可维护的有序索引，或基于不可变轻量 DTO 生成、并按修订号缓存浏览顺序。分类/搜索索引的重建在加载或显式恢复期间运行并报告进度。

#### 3.4 交易和操作语义

资源来源至少包括玩家背包、快捷栏和超维网络。消费计划应遵守统一、可配置且稳定的来源优先级（初始建议先使用背包/快捷栏，再使用网络），并对每个来源和精确变体记录数量。网络数量在 UI 中扣除预留量，防止并发制作、重复点击和多人请求超额使用。

支持两类适配：

- **可查询型**：游戏只检查是否有材料或展示可用数量。适配器把查询转给 `ItemQueryService`，并保留品质等过滤条件。
- **消耗型**：游戏会实际扣除槽位里的物品。适配器把扣除改为交易计划，待原操作成功后提交。对于会异步完成的工作站任务，预留应在任务开始时建立，并在启动失败、取消或完成时按经验证的游戏语义提交/释放。

如果第三方接口只接受具体槽位数组，而没有可靠查询/消耗钩子，不能把无限虚拟格子塞入普通背包数组。应针对该 API 编写版本化适配器，或者明确标记不支持，并给出诊断信息。

所有会消耗资源的适配器（包括弹药换弹）都复用交易协调器的计划、预留、提交和取消能力。工作台多材料扣料和换弹单弹种扣料可以使用不同的适配器，但不得各自实现绕开服务端原子校验的网络库存扣除流程。

#### 3.5 网络身份、成员和权限

- 每个网络有持久、唯一且不会复用的 `NetworkId`。建议使用 GUID 或等价的唯一格式；实际编码格式在实现阶段确定。不同网络的库存只能通过显式事务移动，不按名称、玩家实体 ID 或缓存位置推断网络身份。
- 玩家使用稳定的 `PlayerId` 关联当前网络。每名玩家同时只属于一个网络；首次进入存档时创建个人网络，创建者为唯一网络管理员。
- 每个网络只有一名网络管理员，可有多名成员。管理员和成员都可查看、存入、取出、邀请成员，并使用已支持的“网络物品视同携带”物流操作。管理员另有踢出成员权限；成员可主动离开，管理员不可普通离开或踢出自己。
- 邀请即时发送给在线玩家，被邀请者接受后才加入；不为离线玩家创建待处理邀请。加入者成为成员。
- 管理员可通过明确的“合并加入”加入其他网络：先把自己的网络库存合并进目标网络，再注销来源网络并成为目标网络成员。为避免连带迁移成员，来源网络还有其他成员时必须先由他们离开或被移出。
- 成员离开或被踢后立即失去原网络访问权，并得到一个新的空个人网络，成为新网络管理员。已合并到共享网络的物品继续留在原网络，不按贡献者追踪或返还。
- 服务器管理员权限与网络管理员角色分开。维护命令按玩家 ID 或网络 ID 操作，并在服务端鉴权。`set-network-admin <PlayerId>` 不接受网络 ID：服务端解析玩家当前网络，将其设为管理员，并把同一网络其他管理员降为成员。
- 服务器管理员的库存迁移命令只改变物品归属，不改变网络成员或 ID；玩家接受邀请的网络合并同时改变库存和成员关系。这两种事务必须使用不同操作和日志字段。

#### 3.6 持久化和多人同步

建议文件布局为版本化快照 + 追加事务日志。交易先通过服务层验证；落盘成功后发布已提交变更和新修订号。若日志写入失败，交易不得对 UI 或网络宣告成功，并需要恢复预留。快照使用临时文件、校验和及原子替换；恢复时验证快照，再重放不重复的日志事务。

多人模式下，服务端是唯一权威库存。客户端发起带唯一交易 ID 的请求，服务端检查玩家当前网络、网络角色、修订号、可用数量和适配规则后提交，再只向该网络的有权成员广播小型增量。过期客户端收到修订缺口时申请该网络快照。成员退出或被踢后，服务端拒绝旧成员身份发来的后续查询和交易请求。

网络合并要可恢复且幂等：验证两个不同的网络 ID，记录迁移操作 ID，按精确物品变体汇总数量并检查 `long` 溢出；目标网络持久化成功后才注销来源网络并发布成员变更。失败时不能产生半份库存；服务重启后可依据事务记录完成或回滚，不能重复加料。

服务器管理员按网络 ID 迁移物品时，目标写入和来源扣除同样作为一个可恢复事务；成功后来源网络和原成员关系仍存在，只是库存变空。清空库存保留网络 ID 和成员关系。任何维护操作均由服务端校验操作者的服务器管理员权限并返回明确结果。

#### 3.7 网络插件与功能解锁

- 插件系统是可选扩展，基础存储与物流在插件系统关闭或未安装插件时仍可运行。只有依赖某个插件的扩展功能才要求网络安装对应插件；成员和管理员的功能权限由服务端再次校验，客户端缓存和 UI 显示不能作为授权依据。
- 每个网络有专用插件槽。默认槽位数为 10，并支持配置；多人存档由服务端配置决定可用槽数。
- 只有网络管理员可以通过插件界面安装、移除或替换槽位中的插件。成员可使用网络已解锁的功能，但不能修改插件配置。每次插件槽内容变更作为该网络的一笔服务端事务提交，确保槽位状态与物品库存一致。
- 插件槽与普通网络库存分开建模，并保留完整插件物品身份。插件安装/移除时物品如何在插件槽和普通库存间转移，以及配置缩减时超出槽位的处理，在插件系统实现前确定。首批插件按独立功能开关设计，不额外引入插件依赖或冲突矩阵。
- 网络合并、成员退出或被踢时，插件状态按网络归属处理，不按原成员追踪插件贡献。管理员合并加入时若两个网络都有插件，目标槽位冲突及来源插件的去向需要单独定义。

### 4. 兼容性边界和必须重建的功能

“视同玩家身上”定义为：所有列入支持矩阵并经过验证的消费入口使用统一资源语义。对第三方模组不承诺自动兼容；确有需求时再增加专用适配，跨版本通用适配仍属低优先级可选项。

#### 4.1 核心游戏入口

| 入口 | 目标行为 | 关键正确性条件 |
|---|---|---|
| 配方列表与可制作数量 | 配方可用性与材料数量合并背包/网络 | 按完整配方要求匹配品质、变体、数量和解锁条件 |
| 制作队列/立即制作 | 预留并准确消耗材料，失败时撤销 | 队列数量、并发请求及取消/完成语义一致 |
| 各类工作方块 | 工作站输入材料可来自网络 | 输入格需要实物时只在适配边界临时构造正确堆栈；不重复消耗 |
| 建筑方块升级/维修 | 维修件、升级材料可从网络取得 | 对品质、材料种类、工具和耐久规则精确匹配 |
| 装备维修 | 维修材料可从网络消费 | 维修失败/取消不丢材料，耐久和材料数量按原游戏规则 |
| 载具加油/燃料 | 燃料查询与扣除包含网络 | 燃料类型兼容规则正确，油量变化和物品扣除恰好一次 |
| 载具维修 | 维修材料可从网络消费 | 只有维修成功才提交消耗，重复交互不会重复扣除 |
| 换弹/弹药银行 | 网络安装弹药插件后，枪械按原版所选弹种从网络查询并在换弹流程中使用弹药 | 弹药轮盘与备弹显示包含网络数量；实际换弹走统一资源事务；多人共享扣料准确 |
| 商人购买/交易 | 交易插件解锁手动虚空出售、聚合现实商人购买及自动规则；购买使用真实商人来源，所有商人锁跨网络共享 | 货币/物品扣除与真实商人库存一致；玩家交易、自动交易和服务端交易锁互斥 |
| 自动化链式合成 | 递归计划配方依赖，将订单材料送入玩家制作队列或真实工作方块 | 只接纳已解锁且有可用执行路径的配方；订单隔离共享库存，真实产物被取回后才完成步骤；支持并行、精确取消和异常回收 |
| 快捷存入/取出 | 玩家主动将背包或战利品物品转入网络，或从网络取出 | 遵守原版堆叠与容器规则；库存变化通过交易服务提交 |

#### 界面和交互

UI 随功能逐项设计；各功能设计文档应同时明确必要的入口、状态反馈和权限表现。


#### 后续功能的多人设计要求

新增物流功能开始实现前，明确发起者及其网络、共享物品扣除、物品/货币/进度收益归属、异步失败/取消/离线语义，以及并发时的预留和重复请求处理。没有在线发起者的自动功能须定义规则所有者和收益归属，不得默认为服务器本地玩家或任意在线成员。

使用可选插件解锁的功能必须在服务端校验当前网络的插件状态。管理员变更插件时，按功能的事务与预留规则处理在途操作；客户端缓存不能继续授权。
### 5. 接入诊断与未来兼容

1. **未来适配层与公开 API（可选）**：近期不要求建立完整跨版本适配体系或公开 API。若后续需要支持多个游戏版本/第三方模组，再设计版本化的统一接口，并评估独立适配实现。
2. **能力诊断**：关键接入点记录目标类型/方法、命中情况、阶段和异常；未来建立适配层时，可按能力标记查询、消费、异步任务和多人安全状态。
3. **窄范围补丁**：Harmony 补丁只挂接最小消费入口，按目标版本验证签名/返回值。优先在方法边界转换请求，不反复扫描所有 UI/背包对象。
4. **安全失败**：当前目标版本的入口缺失或冲突时，安全禁用受影响的功能并记录版本、类型、方法、失败阶段；不伪造成功结果。
5. **兼容矩阵**：逐一记录游戏版本、模组版本、补丁命中情况、查询、消费、失败回滚及多人行为。不要只用“能加载”作为兼容结论。
6. **公开 API 样例**：仅在决定对外支持第三方 API 后提供版本化示例和调试说明。

### 6. 可观测性与性能验收

配置至少包含 `DebugLog=false`；本机开发部署配置开启。核心物流流程和容易出问题的边界应在关键阶段记录统一前缀的结构化诊断字段：玩家/网络 ID（可脱敏）、修订号、交易 ID、功能/入口、物品键摘要、数量、处理阶段、耗时和异常。日志统一受开关控制，不默认输出每种物品或每帧事件。

性能基准需要覆盖 1 千、3 万和 10 万种精确物品变体，另测同一种物品的大数量堆叠及单变体超过 `int32.MaxValue` 的对外查询。基准项目包括载入、首次打开、搜索/过滤/排序、翻页、拖放、并发消费、保存/恢复以及多人增量同步。记录 P50/P95 耗时和内存分配；阈值应在目标游戏构建和目标机器上测定后固定。

极限性能测试物品只用于开发诊断，默认不进入正式内容。普通模式按运行时堆叠上限加入所有物品变体；极限模式对可堆叠物品变体加入 `int32.MaxValue` 数量，不可堆叠物品仍按上限加入。具有品质的物品应覆盖全部支持品质；无法读取物品专属品质上限时记录回退诊断。日志汇总物品条目数、变体数、构造/持久化耗时和总耗时，避免逐物品刷屏。

必须满足的架构约束：拖放和普通查询路径不触发完整磁盘保存、完整库存读取或全量 `ItemStack` 构造；单条变更不向所有客户端广播完整快照；查询与消费遵循同一套精确匹配语义。
