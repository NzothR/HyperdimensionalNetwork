# 超维网络：设计与实施计划

本文记录已确认的阶段安排、功能规则、技术架构和范围决定。尚未确定的内容会标注为待讨论，不视为已承诺实现。

> **2026-10-18 阶段 4 修订：**开发优先级为“多人核心架构 → 阶段 1–3 既有功能多人化 → 补货 → 弹药银行 → 链式合成 → 商人交易”。插件系统暂缓，不作为阶段 4 前置依赖。开发期测试存档可直接丢弃，不做旧格式迁移；正常运行必须保持一致性，意外进程崩溃不做复杂跨系统恢复。链式合成运行中订单和订单空间不持久化。阶段 4 先验证单机及多人架构下的个人网络，完整共享网络验收留到阶段 5。对应技术建议详见同目录《阶段 4 技术设计》。

## 路线图与功能设计

### 当前状态

阶段 1、2、3，以及补货、弹药银行、链式合成的单机功能已由用户完成游戏内验收；这些功能的多人兼容尚未验收，留待阶段 5 集中验证。当前开始第四项物流扩展：商人交易。所有新增物流功能从设计时考虑多人语义。模组定位为物流，不规划地面物品自动吸附、存储过滤/自动拾取、即时制作/拆解/维修、材料返还或种植加速。UI 随功能逐项设计。**插件系统暂缓实现**；补货、弹药银行和商人功能不受插件安装限制，未来再引入插件解锁。跨版本适配层和公开 API 为低优先级可选方向；当前优先保持关键流程有统一开关控制的诊断日志，未来遇到版本变化时按日志定位问题。

多人开发第二阶段包含成员关系操作和最终多人验收。朋友参与的多人测试统一安排在其他功能完成后，减少反复占用朋友时间。

### 阶段 0：目标版本和接入契约

开发时持续核实目标游戏版本和运行时约束。首期面向当前目标版本直接接入原版 API；通用跨版本适配层和公开 API 不作为近期前置工作，可在未来确有多版本支持需求时评估。旧 `DestroyStorage` 只用于盘点功能与补丁入口，不作为新实现契约。

| 阶段 | 已验收范围 |

### 阶段 4：多人开发第一阶段——服务端基础、既有功能多人化和其他功能

#### 网络与交易核心

- 每个网络具有持久、唯一、不会复用的 `NetworkId`；建议采用 GUID 或等价的全局唯一格式。所有库存操作明确指定网络 ID，不按显示名称或临时实体 ID 混用库存。
- 使用稳定玩家 ID 记录玩家当前所属网络。玩家首次进入存档时得到自己的独立网络，并作为该网络唯一管理员。
- 服务端拥有网络库存、成员关系和交易结果的最终权威。客户端请求查询/变更并显示服务端确认后的状态。
- 运行期间交易具备唯一请求 ID、网络修订号和幂等处理；重复请求不能重复扣料或加料；多人并发消费不能超额使用。**不要求因进程突然崩溃而恢复在途请求、临时预留或合成订单**。
- 插件系统本阶段暂缓：不开发插件槽、插件物品、安装/移除、解锁校验；新增物流功能完成后对有权限的网络成员直接可用。未来若启用插件，才实现服务端管理的默认 10 个可配置槽位及管理员独占更改权限。
- 已验收阶段 1–3 的界面存取、制作、工作站、装备维修、建筑修复/升级、载具燃料/维修都接入服务端请求流程。操作要保留发起玩家上下文，区分共享材料与玩家个人收益/进度。
- 已确认及后续新增的物流功能在本阶段按“补货 → 弹药银行 → 链式合成 → 商人交易”依次设计开发；每项功能都明确操作者、共享库存影响、收益/进度归属及失败、取消、断线和重试语义。
- 阶段 4 使用开发期可丢弃的测试存档，不迁移阶段 1–3 旧数据格式；正常游戏保存与正常退出应正确保存网络库存和身份数据，不为进程突然崩溃做复杂恢复。

#### 服务器管理员控制台指令

服务器管理员权限与网络内“管理员/成员”角色是两种不同权限。以下维护指令只允许服务器管理员执行，并在服务端检查参数和权限：

1. 按源网络 ID 和目标网络 ID 迁移库存物品。此操作只搬库存，不改变网络成员关系或网络 ID；成功后源网络保留为空。
2. 按网络 ID 清空库存。网络 ID 和成员关系保留；建议要求显式确认参数。
3. 按玩家 ID 查询其当前网络 ID 和网络角色。共享网络中的玩家返回同一个网络 ID。
4. 列出当前存档中已知玩家的玩家 ID、显示名称、在线状态、当前网络 ID 和角色。
5. 按玩家 ID 设置网络管理员，不接收网络 ID 参数。服务端先查该玩家当前所属网络，将其设为管理员，并将同网络其他管理员降为成员；不影响其他网络。
6. 查询正在进行的聚合购买会话，列出会话标识、发起玩家及其占用的商人来源。
7. 按会话标识强制关闭指定聚合购买界面并释放其商人锁；由服务端执行，不提供自动空闲超时。

库存迁移和玩家加入网络是不同操作：维护指令只迁移物品；成员加入会改变成员关系，并按第二阶段规则注销来源网络。

#### 本阶段验收边界

开发期间构建并回归已验收的单机流程，并验证房主/专用服务器与远程客户端通过多人架构访问**各自独立网络**的基础流程、正常保存及断线重连。共享网络成员操作、跨成员并发及正式多人游玩验收放到阶段 5，等新增功能完成后集中进行；阶段 4 不为测试提前实现正式邀请或临时共享网络入口。

### 阶段 5：多人开发第二阶段——成员关系、UI/玩家指令与集中验收

#### 邀请和成员规则

- 邀请即时发送，只能邀请当前在线玩家；不创建面向离线玩家的待处理邀请。
- 网络管理员和成员都能邀请别人；受邀玩家必须接受后才加入，加入者初始为成员。
- 一个玩家同一时刻只属于一个网络。成员要换网时先退出当前网络，再接受目标网络邀请。
- 成员可主动退出；网络管理员不能普通退出，也不能踢出自己。管理员可以踢出成员。
- 网络只有一个管理员。管理员可通过明确的“合并加入”操作加入别人网络，个人网络物品并入目标网络，原网络注销，玩家降为目标网络成员；个人网络还有其他成员时，先由他们离开或被移出。
- 成员退出或被踢后，立即失去原网络访问权并得到一个新的空网络，成为新网络管理员。此前的共享库存留在原网络，不按存入者返还。
- UI 和玩家指令共用服务端成员/权限服务。踢出、退出或加入完成后，旧界面和进行中的请求不能继续操作旧网络。

#### 最终多人验收

朋友参与的多人验收等所有新增物流功能完成后集中进行，覆盖：

- 各玩家私人网络隔离；网络 ID 稳定且不同网络库存不串联。
- 管理员/成员邀请、接受、退出、踢出、网络管理员恢复和合并加入。
- 网络合并/迁移在**正常运行**中的失败与取消不能产生半份库存；重复请求不能重复执行；正常保存及重启后网络数据一致。不要求意外进程崩溃时跨原版状态进行完整事务恢复。
- 多名玩家并发取出或消耗材料时，库存和修订保持一致。
- 阶段 1–3 及新增功能在多人下的发起者、受益玩家、库存扣除和失败回滚正确。
- 离线重连后成员关系与网络 ID 正确；已离线玩家不可接收新邀请。

多人测试的实际执行放在此阶段末尾，不要求朋友参与每个功能的开发迭代。

### 已确认功能设计与范围决定

以下已讨论的物流功能计划放入多人开发第一阶段，按“补货 → 弹药银行 → 链式合成 → 商人交易”逐项实现。商人交易不参考旧模组设计。插件系统暂缓期间，这些功能不要求插件解锁；正式成员/管理员权限仍保留。

#### 弹药、换弹和弹药银行

**已确认的行为：**阶段 4 不要求弹药插件。弹药银行为玩家手持的**所有远程武器**提供网络弹药，包括枪械、弓、弩、火箭发射器等；不支持部署式设备。第三方新增武器只要使用能被可靠接入的原版换弹机制，便按同一规则支持，不承诺对自定义换弹系统自动兼容。弹种与当前选择由原版武器数据决定；不额外自建弹匣或弹药变体匹配机制。

- 换弹时优先消耗发起玩家背包/快捷栏的实体弹药，不足部分用网络弹药补足，允许一次换弹混合来源；可装入数量和部分换弹行为沿用原版。
- 弹药银行有独立的网络管理员设置“启用弹药银行”，默认开启；关闭后不显示网络备弹且网络弹药不参与换弹，玩家自身弹药仍遵循原版行为。
- 网络只在原版换弹实际请求并接收弹药时负责原子化供给，不按每发射击单独扣除网络库存。已经由原版拿走的弹药交由原版换弹/弹匣机制管理；未被原版拿走的弹药不因换弹中断而凭空扣除。
- 与自动补货同时工作时不加特殊限制；两个入口共享网络资源交易协调，防止同一网络弹药被重复扣除。

**显示与缓存：**缓存保持轻量和增量更新。快捷栏变化时只检查变化槽位；切换武器不全量重建缓存。快捷栏中没有远程武器时不查询网络弹药；背包变化和共享网络修订变化时使相关数量缓存过期，HUD/弹药轮盘按当前显示武器刷新。弹种数量可批量查询，但不可逐帧或按每种弹药分别发远程请求。显示缓存不参与扣料授权。

**实现时验证原版语义：**整弹匣计量武器、发射器、弓弩、换弹取消/中断、弹种切换及退弹。以实际原版请求和接受弹药的时点作为供给边界，不为这些情况另造第二套换弹规则。

#### 网络插件系统（暂缓实现）

插件系统保留为**后续可选扩展**，不进入当前阶段 4 开发范围。暂不实现插件槽、插件物品、安装/移除/替换、插件解锁检查及在途移除插件处理；基础网络和四组新增功能不依赖插件。

未来若启动插件开发，再恢复原先的目标：每个网络独立槽位，默认 10 个且可由服务端配置；仅网络管理员能改变槽内容，普通成员可使用网络已启用的扩展；槽位变更与库存变更由统一事务协调。插件依赖/冲突、缩容及网络合并时的迁移规则留待该阶段单独设计，**当前不把这些约束加入已开发功能**。

#### 手动与自动补货

- 每个网络另有“启用补货功能”开关，默认开启，仅网络管理员可见和修改。关闭后，该网络的自动补货与手动补货都不可用；补货个人设置仍独立保存。网络合并时不复制功能开关，保留主网络原有设置。
- 手动补货提供界面按钮，不依赖插件。点击后，从网络库存补充发起玩家**快捷栏**及**背包锁定格子**中已有的物品堆叠；只补到游戏允许的堆叠上限，不在空格中新建堆叠。手动补货不受自动补货冷却影响。
- 自动补货在个人补货设置中可主动**开启/关闭**；开启时由每名玩家独立选择“仅快捷栏”“仅背包锁定格”或“快捷栏 + 背包锁定格”。不会扫描或补充未锁定的背包格。不依赖插件，所有有网络访问权的成员均可使用。
- 每个设置项必须声明所需权限；当前自动补货设置对网络成员开放。新增管理员专属设置时，界面按权限隐藏条目，服务端在写入时再次校验权限。
- 自动补货持续监测发起玩家快捷栏及整个背包的物品堆叠**数量增加、减少**；任意格子的数量变化都会触发一次扫描，不要求变化发生在补货目标格。扫描范围按个人设置限定为快捷栏、锁定背包格或二者；只补这些目标格中的已有堆叠，不扫描其他成员。新出现且已占据目标格的堆叠也可补货；完全空掉的目标格仍被跳过。
- 网络材料不足以补满全部目标时，先补快捷栏，再补背包目标格子；各区域按稳定的从左到右、从上到下的格子顺序执行，同物品多格按此顺序依次补充。“快捷栏 + 锁定格”模式遵循这一顺序。
- 补货按游戏原生堆叠兼容规则匹配物品。空格以及已经用空的堆叠都跳过；不保存空格的物品记忆，也不尝试恢复已用空的堆叠。
- 玩家登录、初始化背包视图、切换网络及首次同步本身不触发自动补货；玩家后续真实的全库存堆叠数量变化才触发扫描。自动补货自身修改背包不再次触发监听。
- 自动补货处理期间暂停该玩家监听；只有实际补充了物品才启动该玩家独立冷却期，没有可补充容量的事件不会占用冷却。`AutoRestockCooldownMs` 为服务端可配置毫秒数，默认 `1000`。冷却期间的变化直接忽略，不排队，结束时不补扫。多个玩家补货均通过同一服务端资源交易入口协调，不能重复扣料。诊断日志遵循统一开关。

#### 网络功能开关

- 每个网络的功能开关独立保存，当前包括“启用补货功能”和“启用弹药银行”，均默认开启且仅网络管理员可见和修改；服务端对每次配置写入和功能操作分别校验权限/开关。
- 设置以 NetworkId 为键；网络合并时不合并功能设置，继续使用主网络的 NetworkId 及原有设置。

#### 出售和商人交易

**权限与多人归属（插件系统暂缓）**

- 阶段 4 不要求交易插件，所有具备网络访问权的成员均可使用手动交易；自动出售、自动购买规则仍仅由网络管理员管理。未来启用插件系统时再附加解锁条件。
- 自动出售/购买规则仅网络管理员可创建、修改和删除。管理员在线时自动交易可应用其当下有效的原版交易加成；管理员离线时不应用个人加成，使用基础价格/商人报价。手动交易使用实际发起玩家的有效加成。
- 服务器是网络库存、货币和自动规则执行的权威方。并发扣除网络货币、物品或交易库存时走统一服务端交易协调；自动操作不归属任意在线玩家。

**手动出售**

- 出售给不对应任何现实 NPC 的虚空商人。按本轮 UI 约定，从超维网络界面开启出售模式后，为网络库存中每个可售物品格显示独立出售按钮；不增加独立出售入口，也不改动普通点击/拖放。
- 出售收益默认进入共享网络；界面允许切换为优先进入发起玩家背包。背包无法完整容纳本次公爵币收益时，整笔收益转入网络，不掉落地面。按游戏物品售价、虚空商人默认出售比例及发起玩家有效的原版出售加成计算，不读取现实商人库存或专属价格覆盖。
- 遵守原版可售条件。物品不可出售标记或基础/最终计算售价不大于 0 时不能出售；品质、耐久、经济价值、出售比例、全局交易价格设置和适用加成按游戏售价公式处理。带改装件的物品作为完整物品直接出售，不自动拆卸或拆卖。

**自动出售**

- 管理员通过自动出售界面指定要出售的物品与品质规则。匹配方式只判断品质等级，不判断改装件：精确匹配指定品质；模糊匹配忽略品质；条件匹配使用品质比较符 `>`、`>=`、`=`、`<=`、`<`。品质条件不匹配没有品质等级的物品。
- 新增或更改/添加出售标记时，对网络库存做一次全量匹配扫描并出售现存匹配物品。移除规则不触发扫描。
- **所有来源**进入网络公共库存的物品均通过统一入库入口检查自动出售，包括手动存入、自动购买入库、链式合成剩余物/取消返还等；只检查本次进入的物品及受影响规则，符合规则且可售时立即出售、收益进入网络，不能重复触发或重复消费。订单空间内部分配与中间移动不算公共库存入库。
- 没有正售价或原版不可出售的物品跳过，不产生出售收益。

**手动聚合购买**

- 网络购买入口扫描**当前存档中已发现且未被占用的现实商人**，将商品聚合到与原版购买操作习惯一致的界面。不额外按玩家距离、当前在线成员附近范围等条件收缩来源。购买仍向对应真实商人交易并减少其真实库存；聚合视图不是虚构商店。远距离商人的访问方式待实现时参考已有模组方案并验证，不在本轮预设具体 API。
- 商品记录始终保留来源商人和报价。同一物品、同一价格可以合并显示并汇总可买数量；同一物品不同价格分开展示。手动购买使用打开界面的玩家作为交易发起者，按该玩家的有效购买加成计算。
- 手动购买时公爵币优先从发起玩家背包/快捷栏扣除，不足部分从其网络余额补足，可在同一笔购买中混合付款，扣款与收货按一次服务端交易协调。购买目标默认进入网络；发起者可切换为进入自己的背包，按玩家持久保存；背包放不下时整笔商品转入网络，避免掉落。
- **商人互斥锁：**聚合购买打开时，服务端扫描并锁定所有当前可用的商人来源，锁在界面关闭、取消、玩家离线、操作失败或服务器管理员强制关闭时释放。扫描跳过已被原版交易或其他聚合购买占用的商人；仍有可用来源则展示这些来源，否则提示所有商人繁忙。界面**不设置空闲超时**；服务器管理员可查询活跃会话及强制关闭指定会话。
- 锁定按现实商人实体生效、跨网络共享。聚合购买占用期间，其他玩家从普通商人界面发起交易时由原版交易锁拒绝并显示原版拒绝提示。不同网络也共享同一商人锁状态。
- 原版 `LockManager` 单次锁请求最多支持 5 个目标。若可交易商人来源超过此限制，实现时使用服务端商人锁协调器，并让原版 `EntityTrader` 交易锁请求识别该协调器占用、按原版方式拒绝交互；不得逐个加锁形成未锁住全部来源的竞态窗口。

**自动购买**

- 管理员可配置自动购买规则，也可点“立即执行”一次运行全部规则。定时触发与手动执行都立即检查规则；手动执行不等下一个定点。
- 普通规则包含目标物品/品质匹配、当前网络库存数量及比较条件、单次最大购买数量、当前网络公爵币及比较条件、单次最高花费（默认无上限）和计划时间。库存数量条件与公爵币条件均为触发门槛，条件全部满足才执行；单次最高花费单独限制实际支出。
- 品质匹配只判断品质等级，不判断改装件：精确匹配指定品质、模糊匹配忽略品质、条件匹配使用 `>`、`>=`、`=`、`<=`、`<`；设置品质条件时无品质等级物品不匹配。
- 批量规则可购买所有商品、某个商品类别等一组商品，不设置单一商品的库存数量阈值/条件，只检查公爵币条件和品质购买条件。单次最高花费仍适用；预算不足时按报价由低到高购买，价格相同则按稳定顺序处理。
- 自动购买的商品来自当前存档中已发现且可交易、未被占用的现实商人，不向虚空商人购买。同物品多个来源优先较低报价，不同价格各自保留。实际扣减该现实商人的库存；网络管理员在线时使用其当下有效交易加成，离线时使用基础报价。
- 计划时间按游戏内时间计算，自动购买的定时周期不得短于 **1 个游戏日**。时间为每天 5 点、间隔 2 天时，从下一游戏日 5 点开始，之后每隔两个游戏日检查一次。每个定时点只检查一次，不重试；游戏/服务器未运行导致错过的定时点**不补执行**，等待下一个定时点或管理员手动“立即执行”。
- 自动购买规则按界面**从上到下**的顺序依次执行，管理员可以调整顺序；同次触发过程中每条规则在轮到自己时重新判断库存、余额和条件。每次自动购买只在执行期间锁定将交易的商人，完成、失败或取消后释放锁；占用中的来源跳过，不等待、不重试。执行时重新验证库存、报价及余额。自动买入又被自动出售规则立即卖出是允许的配置结果，不特别拦截或提醒。

**执行条件比较符**

数量、货币和品质的条件统一支持 `>`、`>=`、`=`、`<=`、`<`。货币条件只判断本次规则是否启动，不代表需要保留的最低余额；实际最高支出由单次最高花费和可用余额共同限制。

#### 自动化链式合成

**目标与计划**

- 玩家从原版追踪的目标配方启动合成链并指定目标数量。目标数量表示**最低交付量**，原版配方批次导致的超额目标成品也全部交付；启动前正确显示预计实际产出。网络只分析配方依赖、预留/转送材料、安排原版执行路径和追踪订单，不模拟或伪造制作结果。已有库存中的目标成品可直接用于交付，无须强制重新制作；不足部分才真正由原版玩家制作队列或真实工作方块产出。
- 合成普通材料来源仅包括**发起玩家自己的背包/快捷栏**及所属网络公共库存，不使用其他成员个人物品。优先复用这些来源中已有的精确匹配成品/中间材料，已有数量足够时不再递归制作；不足时只规划缺少的数量。具体来源顺序沿用统一资源消费策略。未解锁配方视为不可合成，但已有相应实物仍可直接投入订单；缺少时作为基础材料缺口报告。
- 有多个已解锁配方时，玩家可从可用方案中选择。自动选择时优先选出基础材料可满足、依赖配方可展开且执行条件可满足的方案；仍有多个可用方案时按稳定的配方顺序选择。计划中的替代配方同样遵守解锁和工作方块可用性限制。
- 启动前先完整规划依赖图，核对全部基础材料、配方解锁、执行权限和每一步工作方块条件，并原子预留订单材料。任一环节无法启动就拒绝整张订单，说明缺少的材料或工作方块/设备条件，不留下半启动的订单。

**配方和工作方块可用性**

- 配方选择界面只展示玩家已解锁且存在可用执行路径的方案。工作方块搜索使用固定半径配置 `CraftingWorkstationSearchRange`，默认 `64` 米；只扫描当前已加载区块，不主动加载区块。玩家背包制作作为独立执行路径，仅在原版允许该配方由玩家制作且能够可靠追踪队列时计入。
- 工作方块必须与配方的 `craft_area` 等原版要求兼容，并且玩家拥有原版允许的访问/操作权限。尊重游戏的锁、密码及 BeyondStorage3 同类访问检查；仅位于某个领地范围内不自动代表拥有操作权限。
- 已在制作、被原版交易/访问锁占用、超出搜索范围或位于未加载区块的工作方块不计为可用。订单只在提交自己的队列项时选择可用工作方块，不预先锁定工作方块，也不拦截玩家在制作期间打开或操作它；队列及产物按任务身份持续核对。
- 范围内的原版玩家制作、工作台、水泥搅拌机、篝火和化学合成站使用各自原生队列与输入/输出行为。具体适配器必须能识别任务归属、取回对应产物，并安全取消该订单的任务；无法做到时不把该工作方块作为可用执行路径。
- 锻造炉按其特殊机制处理：不由网络向熔炉输入槽送料。计划检查炉内配方所需的熔炼资源、可用配件/解锁条件以及是否有足够燃料开火；满足后由原版锻造炉执行配方。其他需要燃料的工作方块沿用其原生送料和燃烧机制，不由链式合成自动补燃料。
- 第三方工作方块以后按适配器逐个支持。适配器必须能安全定位和追踪精确任务；没有可靠任务识别/取消能力时，隐藏相关执行选项并说明不支持，不能用“按配方取消”误取消其他玩家的任务。

**并行、订单隔离与多人语义**

- 一个配方的制作批次可在多个当前可用的同类工作方块间并行分配。调度每轮先为依赖已满足的各个独立配方分配一台可用设备，再把剩余设备分给需要多批次的配方；批次均分，余数按稳定顺序分配。工作方块在提交队列时分配，准备计划时的候选不能占住设备。
- 整张订单从发起玩家个人物品及网络公共库存获得的材料、已有成品、已取回中间产物均进入独立隐藏订单空间，不再被普通网络查询、取出或预留。每张订单运行期固定关联发起玩家、所属 `NetworkId` 和唯一订单 ID；任务执行沿用发起玩家的原版制作加成、经验及可可靠归属的原版进度，不按网络成员平均分配。
- 所有进入订单隐藏空间的物品先与所属网络主体完成存入/取出交接；工作方块产物先从原版实体输出格实际扣除，再入网络，最后从网络转入订单空间。若工作方块界面正打开，也同步更新其输出格，避免关闭界面时把旧物品写回。未实际扣除产物时不得给订单计入产物或推进依赖。订单启动后才关注对应成品的网络入账；有足量匹配成品入账时，可从网络取入订单空间、停止追踪该节点队列并继续后续步骤。队列被手动取消、替换或成品被取走时，该节点标红并等待玩家取消订单，或将缺少的成品手动存入网络后继续。订单状态展示当前步骤、耗时、绑定的工作方块和异常信息。Shift+左键点击步骤可短暂高亮对应世界中的工作方块。
- 入账成品若随后被自动出售或其他规则取走，订单不额外追溯；没有足量成品时保持等待，由玩家调整设置、补入成品或取消。为后续商店设计保留网络取出优先级：合成链订单请求高于自动出售，自动出售高于普通手动取出。此顺序是接口约定，商店实现时落实并验收，不在当前合成链中虚构售出交易。
- 网络成员可查看该网络的订单进度；只有订单发起者或网络管理员可以取消订单。**订单、临时订单空间、工作方块追踪和订单临时预留只保存在内存，不持久化**。正常离线、退出网络或被踢时取消其在途订单，不能转移到其他网络；进程突然崩溃后不恢复、重建或继续旧订单。

**取消、故障和交付**

- 发起玩家离线时取消其订单，不暂停等待重连。玩家手动取消、发起者离线或订单追踪失败时，对每个已登记的真实任务最多尝试取消一次；收回可可靠取回的工作方块材料与产物，再将订单空间内可回收物品退回原网络。
- 玩家手动取消订单先经过原版确认对话框；红色错误节点不要求补齐成品才能取消。离开当前世界时尝试撤销在途任务并清理该世界的内存订单；进入新世界时必须拒绝旧世界订单引用。远程网络预留的迟到响应只能通过其原授权向原网络归还，不得把旧订单移到新世界。
- 区块卸载、任务被更改或产物缺失时，将相关节点标为错误并保留订单，等待玩家取消或从网络补入足量成品。若工作方块拒绝取消或仍持有无法取回的物品，记录工作方块位置、配方和已知物品并向玩家报告，由玩家自行处置。
- 可检测到的燃料耗尽/停火等情况向订单发起者发出警告，不自动加燃料。锻造炉或其他设备的内部异常导致无法继续时显示设备和已知条件；无法判断或追回的工作方块内部状态不伪装成成功。
- 完成后的目标成品（含原版批次超额成品）优先交给发起玩家；背包放不下的目标成品暂留运行期订单空间并明显标记**待领取**，不掉地上。玩家离线、退出网络或被踢后，待领取物品转回订单所属网络，不跨登录保留个人追踪。订单剩余原料、中间产物、副产物在订单完成/取消回收时统一送回原网络，不按原来源返还到玩家背包；可直接或最终进入公共库存的物品接受自动出售检查。
- 合成链的计划、预留、工作方块分配、开工、取回、取消和异常均记录受统一 `DebugLog` 控制的结构化诊断；常规关闭日志时不向玩家刷屏。
- **意外进程崩溃策略 A：**不为合成链添加持久状态、启动扫描、跨进程返还或跨原版状态的强恢复；允许在途物品少量丢失，尽量避免复制，但不承诺极端崩溃下绝对一致。正常运行时的扣料、回收、取消和失败处理仍必须正确。原版世界/工作方块自身保存的状态继续由原版管理。

#### 模组范围与后续优先级

- 存储网络是玩家主动管理的物流系统，不设计地面物品自动吸附、自动拾取、入库自动销毁等存储规则。
- 即时制作、即时拆解、即时维修、拆解材料返还和种植加速不属于物流模组范围，不进入功能候选。
- 远程箱子链接、自动读书和书籍处理已从规划中移除。
- UI 随功能逐项设计与实现，不要求在功能开发前统一定稿全部窗口、快捷操作和说明页面。
- 插件系统暂缓；当前新增功能不要求插件物品或解锁，未来启用插件时再另行设计槽位和安装迁移，不阻塞阶段 4。
- 跨版本适配层、完整核心解耦、旧数据迁移和公开 API 均不阻塞当前功能；**开发期旧存档不兼容是允许的**。关键流程保留统一开关诊断日志，更新后按具体失败阶段修复。

### 阶段 6：性能和发布验证

- 对 1 千、3 万和 10 万精确物品变体做基准，包含单变体超出 `int32.MaxValue` 的数量；记录 P50/P95 和内存分配。
- 完成单机、多人和目标常见模组组合的最终兼容矩阵。多人实测遵循阶段 5 的集中安排。
- 验证**正常保存/正常退出/重新加载**、重复请求、日志开关、补丁缺失、异常物品数据及网络延迟；不以意外进程崩溃后恢复在途订单或所有未落盘交易作为发布门槛。
- 发布包与开发工作区、缓存和本地测试数据分开。

**发布验收**：核心消费没有误匹配或重复扣除；各适配器能力可诊断；普通查询/拖放不触发全量磁盘读写或全量 `ItemStack` 构造；单条库存变更不向所有客户端广播完整快照。


## 技术架构

### 1. 产品目标

超维网络为玩家提供一个随身携带的大型存储网络。**网络内的物品应像玩家携带的物品一样，可被游戏和已适配的模组查询、匹配、预留及消耗。**例如给载具加油、向工作方块供料、制作物品、维修装备、升级建筑方块时，都能使用网络库存；材料匹配必须遵守游戏规则，包括品质等级、改装件、弹药类型等物品差异。

这是一次新模组重写。旧 `DestroyStorage` 仅用于盘点功能和补丁入口，不作为新架构约束。**阶段 1–3 开发测试存档同样可以丢弃，不要求向阶段 4 迁移。**新项目仍保留数据格式版本字段，便于明确识别不兼容格式，而不是实现当前阶段的兼容迁移。

### 2. 设计原则

1. **统一物品资源接口**：背包、快捷栏和超维网络通过同一查询/交易入口向游戏功能提供物品。
2. **精确保留物品身份**：库存不能只按物品 ID 合并。品质、改装件、耐久、弹药、染色、自定义数据及游戏认可的其他 `ItemValue` 状态都可能决定物品是否可互换。
3. **先计划、再提交**：物品消耗先建立交易计划并预留来源，在原版真正接收物品的语义时点提交；失败或取消时释放尚未交付的预留。正常运行要防止重复扣除、误匹配和无故丢失；不为进程突然崩溃建立跨系统补偿。
4. **服务端权威**：多人游戏由服务端裁决库存查询和交易，客户端呈现授权后的视图。正常增量同步不传输完整库存。
5. **按变更工作**：增删物品产生增量事件和日志；不在拖动物品或打开窗口时全量排序、重建背包、保存并重新读取整个库存。
6. **控制接入边界**：首期按当前目标游戏版本直接接入原版 API，尽量让核心服务职责清晰。完整跨版本适配层/核心解耦是低优先级可选项，不作为近期架构改造前置；游戏更新时优先依靠关键流程诊断日志定位并修复受影响入口。
7. **缓存轻量、事件驱动**：缓存只保存显示需要的轻量元数据和数量快照。快捷栏或库存变化时增量更新受影响的条目；切换武器不全量扫描库存或重建所有武器缓存。

### 3. 领域模型与核心服务

**阶段 4 共用运行原则：**单机、房主和专用服务器共用同一套服务端逻辑，房主不绕过鉴权和资源交易；玩家身份由可信游戏连接/操作上下文确认；正常运行中的网络变更与原版状态交接不能重扣、漏扣或超额扣除。所有公共库存入库统一经过同一入口，供后续自动出售按入库物品检查。阶段 1–3 已验收实现如何改造，待检查实际代码后逐入口决定；此文不预设补丁/API 细节。

#### 3.1 物品身份和数量

定义规范化的 `ItemKey`，由游戏提供或可稳定序列化的完整物品状态构成。实现时应优先复用游戏的 `ItemValue` 相等性/序列化语义；若这些语义无法涵盖模组扩展，则用版本化键格式补充已知字段，并为未知附加数据保留不丢失的表示。对游戏定义为可堆叠的物品，随机生成的 `Seed` 不应导致同一物品拆成无意义变体；其余品质、改装件和自定义数据仍保留。

数量存储使用 `long`，不能假设所有条目都能放进一个游戏物品堆栈。**所有对外提供给游戏的数量都必须限制在 `int32.MaxValue`**：单种物品即使在网络内累计超过该值，配方/工作站/载具等以 `int32` 表示数量的 API 也只能看到最多 `int32.MaxValue`。显示层同样不得将大于 `int32.MaxValue` 的值强转为负数或溢出。每种物品的当前堆叠上限只在展开为游戏 `ItemStack`、工作站槽位或交互结果时查询。

至少区分以下概念：

- **物品种类**：基础物品定义，用于分类及粗略搜索。
- **精确物品变体**：完整 `ItemKey`，用于品质、配方和消耗匹配。
- **可用数量**：总库存减去其他交易已预留的数量。
- **预留数量**：已被在途交易占用、但还未正式扣除的数量。

六级物品示例：配方要求六级扳手时，查询条件必须明确要求品质 6；其他品质的扳手不能满足此条件。若配方允许任意品质，则由配方适配器明确表达允许规则，而不是存储层擅自把品质忽略。

#### 3.2 服务边界

- `StorageNetworkService`：网络生命周期、容量策略、成员和权限。
- `ItemCatalog`：规范化物品身份、可读名称、图标和分类元数据缓存。与 Unity/游戏对象有关的数据只在确认安全的线程上访问。
- `InventoryIndex`：按精确 `ItemKey`、基础物品 ID 和可搜索字段建立数量索引；维护已预排序的浏览投影或增量有序结构。
- `ItemQueryService`：按来源、品质、标签、耐久、弹药等条件查询可用物品；返回数量和来源，不制造虚假背包格子。
- `TransactionCoordinator`：计划、预留、提交、撤销以及重复请求去重。
- `PersistenceService`：运行期脏标记、正常保存周期/正常退出时的版本化快照；采用临时文件写入与替换等基本安全措施，不把每笔交易持久写日志作为提交前提。
- `NetworkSyncService`：服务端权威修订号、运行期消息去重、按需查询视图与小型增量/视图失效通知；客户端不保存完整库存镜像，重连后校验缓存并在需要时重新请求轻量页面。
- `NetworkPluginService`（未来可选）：插件系统暂缓，不在阶段 4 创建此服务或引入解锁依赖。
- `GameIntegration`：配方、工作站、维修、载具、建筑升级等游戏消费入口的接入职责。首期可在现有程序集内保持逻辑分层，不要求立即拆分独立适配器程序集。
- `DiagnosticsService`：可配置调试日志、适配器状态、查询和交易耗时、同步字节数及失败原因。

核心调用形状（概念接口，实施时按目标游戏运行时调整）：

```text
Query(request) -> matching counts + source breakdown
BeginTransaction(request, exact requirements) -> reservation/plan
Commit(transactionId) -> committed result + revision
Cancel(transactionId) -> release reservation
Subscribe(networkId, viewFilter) -> small change/invalidation events
```

查询和变更必须有明确的网络 ID、玩家/服务端上下文及权限检查；服务端从实际连接/操作上下文确认发起玩家身份，不能相信客户端自填的 PlayerId。任何 UI 缓存结果都不是消耗授权；最终提交时必须重新验证预留和实际可用库存。

#### 3.3 存储索引和界面投影

库存真相以精确变体为单位保存，避免百万条目时把每个物品都作为一个 `ItemStack` 常驻内存。建议由 `ItemKey -> Entry(count, reservedCount, metadataRef)` 主索引提供精确访问，并维护基础物品 ID、分类及规范化搜索文本的辅助索引。

存储界面按页请求投影数据，只为可见格子构造 UI 所需的 `ItemStack`/图标数据；客户端仅缓存必要的查询条件、当前页、轻量物品元数据和修订标记，**不下载整网库存**。变化时应用相关增量或使受影响视图失效并重查；重进游戏时能校验的轻量缓存可复用，无法补齐缺失增量时仅重新请求必要视图。搜索输入防抖，翻页不重复全量扫描。游戏对象与图标访问遵循目标游戏允许的线程规则。

对 10 万种物品的排序，不应放在拖放事件路径上。使用可维护的有序索引，或基于不可变轻量 DTO 生成、并按修订号缓存浏览顺序。分类/搜索索引的重建在加载或显式恢复期间运行并报告进度。

#### 3.4 交易和操作语义

资源来源至少包括**发起玩家自己的**背包、快捷栏和其所属网络。普通消费优先玩家背包/快捷栏，不足使用网络；显式定制的功能按各自规则（如手动购买货币先个人后网络）。对每个来源及精确变体记录数量，网络可用量扣除临时预留，防止多人超额消耗。**网络库存、个人背包和游戏原版状态的正常操作须一致**；各适配点按原版真实接收或扣料时机决定何时提交，不假定所有异步队列流程相同。

支持两类适配：

- **可查询型**：游戏只检查是否有材料或展示可用数量。适配器把查询转给 `ItemQueryService`，并保留品质等过滤条件。
- **消耗型**：游戏会实际扣除槽位里的物品。适配器把扣除改为交易计划，待原操作成功后提交。对于会异步完成的工作站任务，预留应在任务开始时建立，并在启动失败、取消或完成时按经验证的游戏语义提交/释放。

如果第三方接口只接受具体槽位数组，而没有可靠查询/消耗钩子，不能把无限虚拟格子塞入普通背包数组。应针对该 API 编写版本化适配器，或者明确标记不支持，并给出诊断信息。

所有会消耗资源的适配器（包括弹药换弹）都复用交易协调器的计划、预留、提交和取消能力。工作台多材料扣料和换弹单弹种扣料可以使用不同的适配器，但不得各自实现绕开服务端原子校验的网络库存扣除流程。

#### 3.5 网络身份、成员和权限

- 每个网络有持久、唯一且不会复用的 `NetworkId`。建议使用 GUID 或等价的唯一格式；实际编码格式在实现阶段确定。不同网络的库存只能通过显式事务移动，不按名称、玩家实体 ID 或缓存位置推断网络身份。
- 玩家使用稳定的 `PlayerId` 关联当前网络。每名玩家同时只属于一个网络；首次进入存档时创建个人网络，创建者为唯一网络管理员。
- 每个网络只有一名网络管理员，可有多名成员。管理员和成员都可查看、存入、取出、邀请成员，并使用已支持的“网络物品视同携带”物流操作。管理员另有踢出成员权限；成员可主动离开，管理员不可普通离开或踢出自己。
- 邀请即时发送给在线玩家，被邀请者接受后才加入；不为离线玩家创建待处理邀请。加入者成为成员。
- 管理员可通过明确的“合并加入”加入其他网络：先把自己的网络库存合并进目标网络，再注销来源网络并成为目标网络成员。为避免连带迁移成员，来源网络还有其他成员时必须先由他们离开或被移出。
- 成员离开或被踢后立即失去原网络访问权，并得到一个新的空个人网络，成为新网络管理员。已合并到共享网络的物品继续留在原网络，不按贡献者追踪或返还。
- 服务器管理员权限与网络管理员角色分开。维护命令按玩家 ID 或网络 ID 操作，并在服务端鉴权。`set-network-admin <PlayerId>` 不接受网络 ID：服务端解析玩家当前网络，将其设为管理员，并把同一网络其他管理员降为成员。
- 服务器管理员的库存迁移命令只改变物品归属，不改变网络成员或 ID；玩家接受邀请的网络合并同时改变库存和成员关系。这两种事务必须使用不同操作和日志字段。

#### 3.6 持久化和多人同步（开发阶段简化策略）

网络库存与成员关系的**运行期权威状态在服务端内存**。交易在正常运行时完成验证、预留及状态提交后即可确认并更新网络修订号；变更标记为待保存，按游戏正常自动保存周期及正常关闭流程写入版本化快照。普通查询与拖放不触发完整落盘；不实施每笔交易 WAL 强制写盘、复杂崩溃恢复或旧存档迁移。快照写入宜使用临时文件替换及基本有效性校验，正常保存失败必须记录并保留待重试的脏状态，不伪称已保存。

服务端是网络库存与权限唯一权威。客户端请求附唯一运行期请求标识；服务端确定真实玩家身份，检查其当前 `NetworkId`、角色、规则、可用库存及请求去重状态。提交后向有访问权、且订阅相关视图的客户端通知变化条目或视图失效；**客户端无完整库存副本要求**。客户端重新连接时校验网络身份与修订标记：轻量缓存有效则复用，可补增量则补增量，否则只重取必要视图。旧网络权限失效后，服务端拒绝旧请求，客户端清除/失效旧视图。

网络合并及服务器管理员迁移在**单次正常执行过程中**，必须作为包含源和目标的协调操作：检查不同网络、角色及数量溢出，同步更新库存和成员/生命周期，再发布成功结果，运行中失败不可留下半份库存。服务器管理员迁移只移动物品，源网络和成员保留；管理员“合并加入”还改变玩家归属并注销符合条件的来源网络。**不承诺意外进程崩溃时多份原版/模组存档跨文件绝对一致，重启后也不恢复在途任务或重放未完成事务。**

#### 3.7 网络插件与功能解锁（未来阶段）

当前阶段 4 **不实现**插件槽、插件物品、插件安装/拆卸、插件状态存档或功能解锁校验。补货、弹药银行和商人交易按已经定义的普通成员/管理员权限直接使用。保留将来为扩展功能追加解锁策略的设计余地即可，不需预先建立插件服务或空槽数据模型。

未来若确实开发插件系统，再单独确定默认 10 个可配置槽位、管理员更改权限、插件物品迁移、网络合并冲突及在途操作策略；这些均不阻塞当前阶段。

### 4. 兼容性边界和必须重建的功能

“视同玩家身上”定义为：所有列入支持矩阵并经过验证的消费入口使用统一资源语义。对第三方模组不承诺自动兼容；确有需求时再增加专用适配，跨版本通用适配仍属低优先级可选项。

#### 4.1 核心游戏入口

| 入口 | 目标行为 | 关键正确性条件 |
|---|---|---|
| 配方列表与可制作数量 | 配方可用性与材料数量合并背包/网络 | 按完整配方要求匹配品质、变体、数量和解锁条件 |
| 制作队列/立即制作 | 预留并准确消耗材料，失败时撤销 | 队列数量、并发请求及取消/完成语义一致 |
| 各类工作方块 | 工作站输入材料可来自网络 | 输入格需要实物时只在适配边界临时构造正确堆栈；不重复消耗 |
| 建筑方块升级/维修 | 维修件、升级材料可从网络取得 | 对品质、材料种类、工具和耐久规则精确匹配 |
| 装备维修 | 维修材料可从网络消费 | 维修失败/取消不丢材料，耐久和材料数量按原游戏规则 |
| 载具加油/燃料 | 燃料查询与扣除包含网络 | 燃料类型兼容规则正确，油量变化和物品扣除恰好一次 |
| 载具维修 | 维修材料可从网络消费 | 只有维修成功才提交消耗，重复交互不会重复扣除 |
| 换弹/弹药银行 | 所有手持远程武器按原版换弹需求混合使用个人实体弹药及网络弹药；不支持部署设备，无插件门槛 | 弹药轮盘与备弹显示包含网络；原版真正接收时统一扣料，多人不重复扣除 |
| 商人购买/交易 | 无插件门槛；手动可售个人与网络物品，聚合存档内已发现的现实商人，支持自动规则 | 购买公爵币先个人后网络；真实商人库存正确，跨网络锁定与管理员强制关闭会话有效 |
| 自动化链式合成 | 递归计划依赖，以发起玩家背包和网络供料，使用原版队列/真实工作方块 | 运行期订单隔离与真实产物追踪；正常取消回收、待领取离线入网；进程崩溃不恢复订单 |
| 快捷存入/取出 | 玩家主动将背包或战利品物品转入网络，或从网络取出 | 遵守原版堆叠与容器规则；库存变化通过交易服务提交 |

#### 界面和交互

UI 随功能逐项设计；各功能设计文档应同时明确必要的入口、状态反馈和权限表现。


#### 后续功能的多人设计要求

新增物流功能开始实现前，明确发起者及其网络、共享物品扣除、物品/货币/进度收益归属、异步失败/取消/离线语义，以及并发时的预留和重复请求处理。没有在线发起者的自动功能须定义规则所有者和收益归属，不得默认为服务器本地玩家或任意在线成员。

未来若实施插件系统，才额外加入插件解锁鉴权及插件被移除时的在途处理；当前阶段仅依据成员关系、管理员权限、资源及原版操作规则鉴权。
### 5. 接入诊断与未来兼容

1. **未来适配层与公开 API（可选）**：近期不要求建立完整跨版本适配体系或公开 API。若后续需要支持多个游戏版本/第三方模组，再设计版本化的统一接口，并评估独立适配实现。
2. **能力诊断**：关键接入点记录目标类型/方法、命中情况、阶段和异常；未来建立适配层时，可按能力标记查询、消费、异步任务和多人安全状态。
3. **窄范围补丁**：Harmony 补丁只挂接最小消费入口，按目标版本验证签名/返回值。优先在方法边界转换请求，不反复扫描所有 UI/背包对象。
4. **安全失败**：当前目标版本的入口缺失或冲突时，安全禁用受影响的功能并记录版本、类型、方法、失败阶段；不伪造成功结果。
5. **兼容矩阵**：逐一记录游戏版本、模组版本、补丁命中情况、查询、消费、失败回滚及多人行为。不要只用“能加载”作为兼容结论。
6. **公开 API 样例**：仅在决定对外支持第三方 API 后提供版本化示例和调试说明。

### 6. 可观测性与性能验收

配置至少包含 `DebugLog=false`；本机开发部署配置开启。核心物流流程和容易出问题的边界应在关键阶段记录统一前缀的结构化诊断字段：玩家/网络 ID（可脱敏）、修订号、交易 ID、功能/入口、物品键摘要、数量、处理阶段、耗时和异常。日志统一受开关控制，不默认输出每种物品或每帧事件。

性能基准需要覆盖 1 千、3 万和 10 万种精确物品变体，另测同一种物品的大数量堆叠及单变体超过 `int32.MaxValue` 的对外查询。基准项目包括载入、首次打开、搜索/过滤/排序、翻页、拖放、并发消费、**正常保存/加载**及多人增量同步；不加入崩溃恢复订单的性能目标。记录 P50/P95 耗时和内存分配；阈值应在目标游戏构建和目标机器上测定后固定。

极限性能测试物品只用于开发诊断，默认不进入正式内容。普通模式按运行时堆叠上限加入所有物品变体；极限模式对可堆叠物品变体加入 `int32.MaxValue` 数量，不可堆叠物品仍按上限加入。具有品质的物品应覆盖全部支持品质；无法读取物品专属品质上限时记录回退诊断。日志汇总物品条目数、变体数、构造/持久化耗时和总耗时，避免逐物品刷屏。

必须满足的架构约束：拖放和普通查询路径不触发完整磁盘保存、完整库存读取或全量 `ItemStack` 构造；单条变更不向所有客户端广播完整快照；查询与消费遵循同一套精确匹配语义。
