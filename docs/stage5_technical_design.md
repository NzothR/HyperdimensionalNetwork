> 关联资料：[《超维网络：设计与实施计划》](design_revised.md) · [《阶段 4 核心架构与多人化技术设计》](stage4_technical_design.md)  
> 不绑定具体七日杀 API、UI 类名或 Harmony 补丁签名；涉及现有实现的接口、保存入口和原版弹窗行为，以代码检查与实际测试为准。

> **验收状态更新（2026-10-20）：**用户确认现有功能均通过单项测试，包括多人模式下另一名玩家参与的测试。长时间连续游玩稳定性观察仍待完成。本文末尾清单保留为详细回归与稳定性观察范围；当前验收结论以 [`acceptance_status.md`](acceptance_status.md) 为准。清单中未勾选项不表示对应功能单项测试未通过。

## 0. 本阶段的已确认决定

本章属于**必须遵守的产品契约**；后文出现的类名、接口名、消息名和流程拆分属于技术建议，可按已完成的阶段 4 代码调整。

| 事项 | 已确认规则 |
|---|---|
| 加入权限 | 网络管理员和普通成员都可邀请**当前在线**玩家；邀请者必须仍属于其所邀请的目标网络。 |
| 不可邀请对象 | 已在目标网络中的玩家；以及**当前是其他共享网络管理员且其网络仍有其他成员**的玩家。邀请发送时拒绝，接受时再复核一次。 |
| 普通成员换网 | 若受邀者是另一个共享网络的**普通成员**，接受邀请后**直接切换成员关系**，原共享网络库存、配置、规则均不移动，也不先给该玩家创建空个人网络。 |
| 单人网络管理员加入 | 若受邀者是自己网络的管理员且该网络只有自己，接受邀请后把**来源公共库存并入目标公共库存**，注销来源网络，受邀者成为目标普通成员。来源空库存也按同一生命周期处理。 |
| 其他情况 | 已属于目标网络、目标网络失效或共享网络管理员尚有其他成员时，拒绝加入；所有成功加入者初始为目标网络**普通成员**。 |
| 邀请限制 | **每个受邀玩家同时最多一条未处理邀请**，已有邀请时不允许其他人再邀请该玩家；不同受邀玩家可各有一条。邀请仅运行期有效，默认现实时间 **5 分钟**，不为离线玩家留邀请。 |
| 邀请交互 | **复用游戏原版确认弹窗**，显示邀请者、目标网络和加入/合并影响；接受与拒绝两个操作。不另做收到邀请的独立窗口，也不在接受时再要求第二次合并确认。原版弹窗关闭其他窗口只是体验保障，服务端必须额外清理。 |
| 成员退出或被踢 | 普通成员退出或被踢，立刻失去原网络访问权，获得一个**新建的空网络**并成为管理员；原共享库存不返还给个人。网络管理员不能普通退出或踢出自己。可踢出离线成员。 |
| 管理员转让 | 阶段 5 提供**网络管理 UI 内的管理员转让按钮**，仅当前网络管理员可操作；接受转让者须是同一网络的其他现有成员。**管理员转让指令只允许服务器管理员调用**，不向普通玩家提供同等聊天指令。每网始终一名管理员。 |
| 设置归属 | **个人设置跟随 PlayerId**，包括自动补货开关/范围、手动购买的收货位置、手动出售的收益位置与其他玩家独有设置；离开、被踢、直接换网、合并加入均保留。**网络级管理员配置跟随 NetworkId**，如各功能总开关、自动买卖规则；目标网络配置不被来源覆盖。新网络使用网络级默认设置。 |
| 自动交易 | 自动购入物品与自动出售收益仍归**网络**；“流向是个人设置”**只指手动交易界面**的选择，不改变自动交易的网络归属。 |
| 合并入库 | 来源库存经统一公共库存入库接口进入目标网络，**接受目标网络自动出售规则检查**。不合并来源网络的管理员总开关及自动交易规则。 |
| 指令 | 阶段 5 实现完整的玩家成员指令与服务器管理员维护指令；优先完成网络管理 UI，再实现指令，二者复用服务端业务入口。 |
| 验收 | 阶段 5 最后集中进行真正的共享网络多人验收，包括原阶段 1–4 的所有物流功能。 |

### 0.1 对旧设计文档的优先级修正

当前上传的《设计与实施计划》仍写有“成员换网须先退出再接受邀请”“管理员通过单独的明确合并加入操作”等旧表述。**以本章确认的‘受邀者直接接受、按身份直接换网或合并’规则为准**。将来修订主设计文档时应同步替换，避免开发时出现两套加入入口。

当前主设计文档的“当前状态”仍停留在商人交易开发途中；本技术文档按用户本轮确认的**阶段 4 全部完工**作为实施前提。阶段 4 源码若与文档建议的类名/结构不同，优先复用现有实现。

## 1. 目标、非目标与实施边界

### 1.1 阶段 5 交付目标

1. 在线邀请、原版弹窗接受/拒绝、邀请超时及失效。
2. 普通成员直接切网；单人管理员网络合并；普通成员主动退出；管理员踢出成员（含离线成员）。
3. 网络管理 UI：网络摘要、成员列表、邀请入口、踢出、退出、管理员转让与必要反馈。
4. 普通玩家成员指令，以及现有或缺失的服务器管理员维护指令。
5. 成员权限切换时停止旧网络会话/请求，清理在途业务，刷新轻量客户端视图。
6. 在多人共享网络中集中验证存储、补货、弹药银行、链式合成、商人交易与自动规则。

### 1.2 非目标

- 不重做阶段 4 的网络库存主索引、ItemKey、资源事务协调器、商人库存和原版资源交付机制。
- 不重做补货、弹药、合成和商人交易各自的游戏行为；只处理**成员关系变化时**它们的权限、清理与设置归属。
- 不引入离线邀请、邀请申请队列、多个并存邀请、跨存档邀请、网络名称作为权限凭据或共享网络管理员多人制。
- 不实现插件槽或旧存档迁移，也不为意外进程崩溃添加复杂的跨原版状态恢复机制。
- 不强制在阶段 5 补做尚未存在的每一种功能总开关；先按已有设置归属分类，未来增加总开关时沿用统一规则。

## 2. 数据所有权与模型增量

### 2.1 持久化的权威状态

继续使用阶段 4 的 `PlayerId`、`NetworkId`、玩家到网络映射、唯一管理员、网络成员集合、公共库存和网络库存修订号。建议明确区分：

```text
WorldNetworkState                         // 当前游戏存档，服务端权威
  Networks[NetworkId]
    AdminPlayerId                         // 必须属于该网络
    Members[PlayerId]                     // 包含管理员，或沿用现有等价表示
    Inventory / InventoryRevision
    NetworkSettings                       // 管理员可管理的网络级配置
    AutoTradeRules / OtherNetworkRules    // 网络级自动规则
  PlayerDirectory[PlayerId] -> NetworkId
  PlayerPreferences[PlayerId]             // 个人设置，绝不由来源网迁往目标网
  SaveFormatVersion / DirtyGeneration
```

**设置归属是关键，不以“编辑者是谁”判定数据所有权。** 自动交易规则即使只有管理员可以修改，也属于网络而非管理员个人；管理员转让不清空规则。补货个人配置及手动交易目的地即使现在显示在网络界面，也始终属于玩家自己。

来源网络注销时：库存已移入目标；来源网络级设置、自动规则及其他只属于来源网络的配置随来源生命周期删除；原管理员的个人设置仍保留。

成员退出/踢出时新建网络：使用网络级默认配置，不复制原网络的任何网络级设置或自动规则；玩家个人设置完全保留。

### 2.2 仅运行期数据

```text
PendingInviteByRecipient[PlayerId] -> InviteRecord
  InviteId
  InviterPlayerId
  RecipientPlayerId
  TargetNetworkId
  CreatedAt / ExpiresAt          // 现实时间，使用服务端时间

MembershipRevision / PlayerMembershipEpoch
MembershipMutationRequests / ResultCache // 运行期去重
NetworkMutationGate                      // 受影响网络的变更屏障
ActiveFeatureSessions                    // 原有链式合成、聚合购买等
ClientMemberViewSubscriptions
```

每个受邀者以 `PlayerId` 为键，天然限制未处理邀请最多一个。终结状态可以只在有界请求结果缓存中短期保留，不需要永久邀请历史。邀请和处理中请求不持久化，服务器正常重启后全部清空。

`MembershipRevision`（或阶段 4 已有的 `MembershipEpoch`）与**库存修订号分开**：前者表示谁能访问、角色变化和权限撤销，后者表示库存变化。可以使用现有的代际机制，不必为了名称再建一套重复状态。

### 2.3 必须维护的不变量

- 一个 `PlayerId` 始终恰好关联一个**有效** `NetworkId`（操作提交的瞬间不暴露中间空值）。
- 一个有效网络恰好有一个管理员；管理员也必须是该网络成员。
- 同一玩家不会同时列在两个有效网络的成员集合中。
- 合并成功后，来源 `NetworkId` 失效，不能被旧请求、旧邀请或旧缓存继续使用。
- 相同 `InviteId` 或成员变更请求重试不会重复移动库存、重复创建新网或重复执行管理员转让。
- 网络库存/成员关系的正常保存必须来自一个内部一致的状态版本；不要求进程突然崩溃后恢复未保存交易。

## 3. 权限与入口设计

### 3.1 权限矩阵

| 操作 | 普通成员 | 网络管理员 | 服务器管理员维护入口 |
|---|:---:|:---:|:---:|
| 浏览本网络成员/网络信息 | ✓ | ✓ | 可查询任何已知玩家/网络 |
| 邀请合格在线玩家 | ✓ | ✓ | 不自动以某个网络成员身份邀请 |
| 接受/拒绝发给自己的邀请 | ✓ | ✓（仅单人管理员可接受合并） | 不代替玩家接受 |
| 从共享网络直接接受邀请换网 | ✓ | 不适用 | 不代替玩家加入 |
| 主动退出所属网络 | ✓ | ✗ | 不作为普通退出操作 |
| 踢出本网络其他普通成员 | ✗ | ✓ | 按专有维护权限/能力设计 |
| 通过 UI 转让管理员给现有成员 | ✗ | ✓ | 可通过专用管理指令达到同一结果 |
| 用玩家聊天指令转让管理员 | ✗ | **不提供** | 仅服务器管理员管理指令 |
| 修改网络级总开关、自动交易规则 | ✗ | ✓ | 不自动继承网络管理员的普通功能入口 |
| 修改自己的个人设置 | ✓ | ✓ | 不自动更改他人个人设置 |
| `set-network-admin <PlayerId>` 等跨网络维护 | ✗ | ✗ | ✓ |

**服务端判权是最终依据。** UI 仅隐藏/禁用无权限按钮；不能因为 UI 由网络管理员打开就跳过服务端对其当前 `PlayerId`、`NetworkId` 和角色的二次验证。服务器管理员身份与网络管理员身份绝不能混淆。

管理员 UI 转让限制：目标必须是同一网络的**另一名现有普通成员**。目标在线与否不影响数据权限判定；**技术建议**允许选择离线成员以完成管理员交接，实际 UI 如不方便也可先限制为在线成员，但应在开发验收前统一行为。转让前明确提示“你将降为普通成员”。

### 3.2 统一成员变更入口（示意）

```text
InvitePlayer(trustedInvoker, targetPlayerId)
RespondToInvite(trustedRecipient, inviteId, accept: bool)
LeaveNetwork(trustedPlayer, requestId)
KickMember(trustedAdmin, targetPlayerId, requestId)
TransferAdminFromUi(trustedAdmin, targetPlayerId, requestId)
SetAdminFromServerConsole(trustedServerAdmin, targetPlayerId, requestId)
GetNetworkMemberView(trustedPlayer)
```

UI 与玩家指令调用同一业务服务；原版弹窗只传递邀请标识及“接受/拒绝”意图。服务器从真实连接/操作上下文构造 `trustedInvoker`，不相信客户端自报 `PlayerId`、管理员权限或网络 ID。

## 4. 邀请生命周期

### 4.1 发起邀请的校验顺序

1. 根据连接上下文取得真实邀请者，确认其当前所属网络和邀请资格。
2. 解析稳定的目标 `PlayerId`；目标必须是**当前在线**的其他玩家，不能通过显示名歧义定位。
3. 清理已经超时/失效的目标邀请；如果目标仍存在一条有效的未处理邀请，拒绝新邀请，提示“该玩家已有待处理邀请”。
4. 目标已在邀请者网络，拒绝；目标若为**其他共享网络管理员且有其他成员**，拒绝。
5. 为目标创建唯一 `InviteId` 与 5 分钟现实时间到期时间；记录邀请者和当前目标 `NetworkId`。
6. 给受邀者显示原版独立确认弹窗；发送者收到投递成功或失败的反馈。服务端不因客户端声称弹窗显示成功而预先改变成员关系。

同一目标的两个邀请即使同一瞬间抵达，也只允许一条成功创建。不同目标玩家的邀请互不冲突。邀请发起者可同时邀请多个**不同**玩家（若将来希望限制再单独添加规则）。

### 4.2 邀请消失的条件

- 接受成功或受邀玩家明确拒绝；超时满 5 分钟。
- 受邀者离线或服务器会话断开；服务器正常重启。
- 邀请者离开原目标网络，或目标网络注销。
- 接受时发现邀请者已无资格、受邀者已在目标网络或受邀者已变为不可合并的共享网络管理员。
- 一次成功成员变更使此前邀请上下文不再适用时，取消目标玩家的旧邀请。

邀请失效需同步通知弹窗关闭或失效；**即使界面仍显示，也必须由服务端拒绝迟到的“接受”操作**。到期清理可以惰性检查结合低频扫描，不需要逐帧遍历邀请。

### 4.3 接受邀请的事务步骤

```text
原版弹窗点击接受
  -> 服务端依 InviteId 再查邀请 / 真实接收者 / 期限
  -> 重新检查邀请者网络与受邀者当下网络关系
  -> 判定：普通成员直接换网 OR 单人管理员合并
  -> 暂停受影响玩家旧网络新操作 / 清理在途旧会话
  -> 提交成员关系切换（必要时同时合并库存并注销源网）
  -> 使旧授权与视图失效，通知新网络摘要
  -> 标记邀请完成，向双方返回最终结果
```

原版弹窗可能会强制关闭玩家正在打开的其他窗口，但**不能把窗口关闭当成在途商人锁、后台合成订单或待提交网络请求已经取消的证据**。服务端必须明确调用原有功能的清理/取消入口。

接受操作完成后不再增加第二次合并确认；对于单人管理员，弹窗内容应在点击接受前写明来源网络物品将合并、来源网络注销、来源网络管理员配置不继承等后果。

请求失败时：玩家仍属于原网络，来源库存与管理员身份保持不变；向玩家提供可读失败原因。邀请是否仍可重试取决于它是否过期/失效；**建议仅对暂时忙碌且邀请仍有效的失败保留重试资格**，其余终结失败销毁邀请。

## 5. 成员变更与合并的执行协议

### 5.1 状态分支表

| 原有身份 | 网络状态 | 操作结果 | 来源网络处理 |
|---|---|---|---|
| 普通成员 | 属于其他共享网络 | **直接换网**，新角色普通成员 | 原网保留，库存/规则/总开关不变；从成员集合移除此人 |
| 管理员 | 来源网只有本人 | **合并加入**，新角色普通成员 | 全部公共库存入目标；注销来源网与来源网络级设置/规则 |
| 管理员 | 来源网仍有其他成员 | **拒绝** | 无变化；邀请发起时也应禁止邀请此人 |
| 任意 | 已经在目标网 | **拒绝/已加入** | 无变化 |
| 任意 | 邀请过期、邀请者已离开、目标网不存在 | **拒绝** | 无变化 |

合并按**目标现有网络**为主网络；保留目标 `NetworkId`、当前管理员、自动交易规则及网络级总开关。来源玩家的个人设置与其 `PlayerId` 继续保留。成功加入的玩家变成目标普通成员，即使原来是个人网络管理员。

### 5.2 普通成员直接换网

正常运行中建议把成员关系变更视为一个逻辑提交：

1. 对受邀者和源、目标网络的成员变更取得排他协调权，阻止旧请求在提交后继续成功。
2. 关闭/拒绝该玩家的新旧网络敏感会话，并按照第 6 章完成其运行中的旧网操作清理。
3. 从源成员列表移除该玩家，将其加入目标成员列表；将 `PlayerDirectory` 映射改为目标网络，并将其角色设为普通成员。
4. 保留**源网络原封不动的公共库存、规则、总开关**；不创建临时空网，也不转移原成员个人背包物品。
5. 递增受影响成员/权限版本，使旧查询视图、旧操作请求、弹药/补货缓存失效；标脏以供正常保存。
6. 同步双方网络成员列表及该玩家的新网络摘要；被移动玩家以后按目标网络重新查询必要轻量视图。

**不得**先完成来源身份删除、随后异步创建目标身份，使其他功能能观察到“无所属网络”的中间状态。

### 5.3 单人管理员合并网络

建议分为 **预检查 → 静默/清理 → 预计算 → 逻辑提交 → 后续入库规则处理 → 通知**：

1. 检查邀请、来源/目标不同、来源管理员确实是受邀者，且来源成员集合仅此一人；目标网络有效。
2. 按稳定 `NetworkId` 顺序协调来源和目标网络；将来源网络标记为合并中，拒绝新入库、扣料、自动购买、自动出售以及新的依赖来源网络的操作。
3. 结束来源管理员的聚合购买会话、链式合成订单及其他运行期个人会话；停止来源网络的自动交易执行/待执行提交，释放原版商人锁和可释放的预留。**先回收能够回收的来源物品，再计算最终待合并库存**。
4. 汇总来源精确 `ItemKey` 数量，检查目标对应条目 `long` 加法是否溢出；检查当前两网修订与角色未变化。
5. 在单次受协调的逻辑提交中，将来源物品转入目标**统一公共入库路径**，更新受邀者 `PlayerDirectory` 与成员角色，删除来源网络及其网络级设置、自动交易规则，增量更新目标库存和相关修订/成员版本。
6. 在合并逻辑已经成功且目标网络仍受有序提交协调的前提下，处理本次目标入库应触发的自动出售检查。**出售执行失败不得把已成功的合并伪装成未发生**；未售出的物品仍归目标网络，记录错误。实现时应避免其他操作抢先消费刚入库、还待出售规则检查的相同物品。
7. 清理来源邀请/旧缓存/订阅，通知参与成员与受邀者。结果去重，重发同一接受请求只返回既有成功结果。

若**合并核心逻辑尚未提交**时出现普通失败（条件变化、数据溢出、取消清理无法安全完成等），不得只搬一半库存或注销一半成员数据；按失败返回并保持原有效网络。取消过程若出现无法取回的原版工作方块物品，按既有合成链异常语义报告，不凭空补偿；如果其在途任务仍可能继续写回已注销的网络，应阻止合并，直到能够安全停止这一写回路径。

**注意**：合并库存与来源网络注销属于同一正常执行的成员/库存协调操作；自动出售属于合并成功后对新入库物品的后续业务效果。这既符合“统一入库监督”，也避免下游商人计算错误导致已提交合并被倒扣回去。

### 5.4 普通成员主动退出

- 仅允许普通成员；管理员请求普通退出时返回明确拒绝。
- 撤销该玩家旧网操作权限并完成个人在途业务清理。
- 服务端新建唯一 `NetworkId`、创建**空库存**、配置网络级默认设置，把退出者设为唯一管理员。
- 同一逻辑提交中从原网络成员集合移除玩家、更新 `PlayerDirectory`，不搬走原网库存、自动规则或其他网络配置。
- 个人设置保留；注销/失效旧网个人视图，加载新个人网络视图；正常保存时持久化新网络与身份。

### 5.5 管理员踢出成员

- 当前管理员可踢出自己网络的其他**普通成员**，不可踢自己；被踢玩家可以离线。
- 服务端即刻使该成员对原网络的访问失效，取消其在途请求、合成订单和聚合会话；创建新空个人网络，原网物品不按贡献返还。
- 玩家在线时关闭旧管理/库存/交易窗口、使缓存失效并通知新网络；离线时服务端直接完成身份/网络创建，下次登录读取新网络。
- **权限撤销不能依赖被踢玩家确认弹窗、在线接收消息或客户端主动退出。** 某个原版任务无法完整回收时按原有异常处理，不应因此允许其继续使用旧网络。

### 5.6 管理员转让

```text
旧管理员 A + 同网普通成员 B
  -> A 在管理 UI 选择“转让管理员”并确认
  -> 服务端验证 A 当前仍为管理员，B 当前仍属于同网且非 A
  -> 同一逻辑提交：AdminPlayerId = B，A 降为成员，B 升为管理员
  -> 递增成员权限版本 / 广播成员角色变化 / 标脏
```

网络 ID、库存、管理员总开关、自动交易规则及所有成员个人设置保持不变。自动交易下一次执行使用**当前新管理员**的在线加成；旧管理员不再具有修改网络级设置、规则或踢出成员的权限。已开始执行的管理员专属请求必须在提交时重新校验权限，不能依赖过期 UI。

服务器管理员的 `set-network-admin <PlayerId>` 使用同一个“单网仅一管理员”的角色变更核心步骤，但入口鉴权来自服务器管理员权限，**不提供网络管理员可直接调用的玩家转让指令**。

## 6. 在途功能清理与身份切换屏障

### 6.1 统一清理接口（建议）

不建议让邀请、退出、踢出、管理员转让各自遍历 UI 对象。可由成员服务调用一个集中分发的运行期清理协调器，适配阶段 4 已实现功能：

```text
PrepareMembershipChange(playerId, sourceNetworkId, changeKind)
  -> FreezeOrRejectNewOperationsForAffectedScope
  -> CancelUserPendingResourceRequests
  -> RestockAdapter.StopOldNetworkListenerAndCooldown
  -> AmmoBankAdapter.InvalidateOldNetworkSupplyAndHudCache
  -> CraftChainAdapter.CancelOrdersOwnedByPlayerAndReturnToSource
  -> TraderAdapter.CloseAggregatePurchaseSessionAndReleaseTraderLocks
  -> ManualTradeAdapter.CancelUncommittedActions
  -> SettingsAndInventoryViews.InvalidateOldSubscriptions
  -> Quiesced / FailureWithDiagnostics
```

具体 API 名以现有代码为准。成员离开时，**只清理该玩家的运行期操作**，不能误停止原网络中其他成员发起的合成链、补货和正常交易。来源网络注销的单人管理员合并是例外：还需停止来源网络自身的无人值守自动交易与网络级运行期任务。

### 6.2 权限生效时点

- 接受、退出、踢出等操作一旦进入受协调的身份切换阶段，旧网络针对该玩家的新请求不能再开始。
- 正在执行的操作可按照原版已真实交付的时点完成已有不可逆部分；**已成功交付的物品不反向追缴**。尚未实际提交的旧网请求取消/拒绝。
- 在玩家新网络身份生效之后，迟到的旧 `NetworkId`、旧角色、旧 `MembershipEpoch` 请求必须被服务端拒绝；重复请求也不能绕过撤销权限。
- 网络变更中清理完毕前，不能让迟到的取消/回收回调向**错误的新网络**返还材料。所有回收继续指向操作绑定的**原 `NetworkId`**，只有明确的合并核心步骤会再迁移来源库存。
- 客户端显示刷新是结果而非权限前提：哪怕网络通知尚未送达，服务端也已经拒绝旧身份操作。

### 6.3 功能级处理矩阵

| 功能 | 网络身份变更时的处理 |
|---|---|
| 存储/搜索/拖放 UI | 关闭或重置旧窗口，撤销旧订阅；依据新网按需重查页面，不下载整网快照。 |
| 手动/自动补货 | 取消尚未交付的请求；停止旧网络自动监听与冷却，切到新网络后依据玩家个人开关与**新网络的功能总开关**重新挂接。切网初次同步不触发补货。 |
| 弹药银行 | 使旧网络弹药数量缓存失效，停止旧网供给；原版已经接收的弹药不追缴。新网按其弹药总开关重新查询。 |
| 链式合成 | 取消此玩家发起的旧网订单，依既有规则尽力从原版任务及订单空间回收**到旧网络**；已完成但待领取的物品也回旧网。其他玩家订单不受影响。 |
| 手动虚空出售/手动购买 | 拒绝未提交的旧网络交易；已成功提交结果不因换网撤销。个人选择的收益/收货位置不清空。 |
| 聚合购买会话 | 立即结束受影响玩家会话并释放它持有的真实商人锁；原版已完成的购买不反向执行。 |
| 自动购买/自动出售 | 普通成员离开不影响原网络的网络级规则；**来源网络注销合并**时停止该来源网络自动任务、丢弃其规则；目标规则继续使用。管理员转让后自动交易使用新管理员身份决定加成。 |
| 网络设置与规则编辑 | 关闭旧网管理员设置页，拒绝旧版本/旧权限的保存；玩家个人设置保留。 |
| 邀请弹窗 | 身份改变后清除该玩家失效邀请；目标网注销后清除相关邀请；过期响应被拒绝。 |

如果未来增加新功能，必须声明：其活跃会话是否绑定玩家还是网络、成员变化时如何停止、已交付物品怎样处理、旧网回收去向以及如何取消可能迟到的回调。

## 7. UI 方案（网络管理面板 + 原版邀请弹窗）

### 7.1 管理面板布局草案

建议在现有超维网络界面增加“网络管理”入口，复用已完成的 UI 资源、风格和导航。**下列为信息层级草案，不要求按字符画机械还原像素布局。**

```text
┌────────────────────────── 超维网络 · 网络管理 ──────────────────────────┐
│ 当前网络：<显示名称/网络摘要>    NetworkId：<缩写> [复制完整 ID]         │
│ 我的身份：管理员 / 成员          网络管理员：<玩家显示名>               │
├───────────────────────────────────────────────────────────────────────┤
│ 网络成员（在线 / 总数）                        [邀请在线玩家]          │
│   ● 玩家 A       管理员      在线     （自己的条目）                   │
│   ● 玩家 B       成员        在线     [踢出] [转让管理员]（仅管理员）  │
│   ○ 玩家 C       成员        离线     [踢出] [转让管理员]（仅管理员）  │
├───────────────────────────────────────────────────────────────────────┤
│ 普通成员： [退出网络]                                              │
│ 管理员：   不显示普通退出按钮，显示管理员专属操作                   │
│ 提示：退出/被踢后获得新空网络；旧共享物品留在原网络                 │
└───────────────────────────────────────────────────────────────────────┘
```

要点：

- 在线与离线状态来自服务端；成员列表包含离线成员，稳定 `PlayerId` 是操作目标，显示名仅供阅读。
- 不必新增“邀请收件箱”页面：每名玩家最多一个待处理邀请，**接受/拒绝直接复用原版弹窗**。管理 UI 可以显示“邀请已发出/对方已有邀请/目标不可邀请”的反馈。
- 踢出、主动退出、管理员转让均应有原版确认弹窗或同等清楚的确认交互；邀请的**接受**已经是加入/合并确认，不追加二次确认。
- 管理员专属按钮对成员隐藏，同时服务端鉴权；离线成员也可以被踢出。
- `NetworkId` 完整复制值来自服务端；显示名称不能用于请求定位。
- 成员变更后只刷新**成员/角色与必要当前视图**，不广播整份网络库存。

### 7.2 受邀者原版弹窗文案示意

**普通成员收到邀请：**

> **超维网络邀请**  
> `<邀请者显示名>` 邀请你加入其所在的超维网络。接受后，你会直接退出当前共享网络，成为目标网络的普通成员；你在原共享网络中存放的物品仍属于原网络。个人设置保留。  
> **[拒绝] [接受]**

**单人管理员收到邀请：**

> **超维网络邀请**  
> `<邀请者显示名>` 邀请你加入其所在的超维网络。接受后，你的个人网络库存将并入目标网络，原网络注销，你成为目标网络普通成员。原网络的管理员配置和自动交易规则不会继承；入库物品受目标网络自动出售规则影响。个人设置保留。  
> **[拒绝] [接受并合并]**

按钮标签与字数应根据原版弹窗可容纳空间调整；不改变只有**一个独立原版弹窗**、两个操作的原则。邀请发出后若玩家角色改变，点击接受时仍由服务端重校验，并可拒绝已经不适用的邀请。

### 7.3 转让管理员确认文案

> 将网络管理员转让给 `<目标成员>`？转让后你将变为普通成员，不能再编辑网络级设置、自动交易规则或踢出成员。网络库存、NetworkId 和所有网络规则保持不变。

完成后成员 UI 立即更新权限，旧管理员界面的写入请求也必须被服务端拒绝。

## 8. 玩家指令与服务器管理员指令

### 8.1 两套权限，不是两套业务逻辑

- **玩家指令**使用真实玩家会话身份，根据其当前网络角色执行邀请、退出、踢出等日常操作。
- **服务器管理员指令**使用七日杀现有服务器管理权限体系鉴权，可执行跨网络维护操作；不能把网络管理员权限等同于服务器管理员。
- UI、原版邀请弹窗和玩家指令最终请求同一个成员服务；服务器管理员指令可以在通过单独的管理员鉴权后复用对应的角色变更核心步骤。
- 命令字符串为**建议名称/语法**。是否使用 `/sn`、原版聊天命令还是控制台命令，等检查现有模组命令注册方式后决定。

### 8.2 玩家成员指令（示意）

| 命令示例 | 效果 | 权限与备注 |
|---|---|---|
| `/sn info` | 查看本人所属网络、角色和管理员 | 本网络成员 |
| `/sn members` | 查看成员名单、角色、在线状态 | 本网络成员 |
| `/sn invite <PlayerId>` | 邀请一名当前在线且符合资格的玩家 | 本网络成员/管理员；目标只能有一条待处理邀请 |
| `/sn accept <InviteId>` | 接受自己的未过期邀请，按身份自动换网或合并 | 受邀者本人；仍要重做服务端资格检查 |
| `/sn decline <InviteId>` | 拒绝自己的邀请 | 受邀者本人 |
| `/sn invite-status` | 查询自己是否有一条待处理邀请 | 可选便民指令；不增加邀请收件箱系统 |
| `/sn leave` | 退出当前共享网络并获新空网络 | 普通成员，管理员拒绝 |
| `/sn kick <PlayerId>` | 踢出同网其他成员 | 当前网络管理员；允许离线目标 |
| `/sn help` | 按身份展示合法玩家指令和说明 | 所有玩家 |

即使存在 `/sn accept`，收到邀请的**默认交互依然是游戏原版弹窗**。文本入口主要作为阶段 5“完整指令系统”的补充，不意味着重新制作邀请 UI。**不提供网络管理员聊天指令转让管理员**。

### 8.3 服务器管理员指令（沿用阶段 4 约定并验收）

| 操作（示意命令） | 权限 | 主要约束 |
|---|---|---|
| `network-move-items <SourceNetworkId> <TargetNetworkId>` | 服务器管理员 | 只移动库存；**不**改变成员与网络生命周期；源网仍存在且库存变空。 |
| `network-clear <NetworkId> --confirm` | 服务器管理员 | 清空库存，保留网络 ID 与成员；必须明确确认。 |
| `network-player-info <PlayerId>` | 服务器管理员 | 查询当前网、角色及必要玩家信息。 |
| `network-list-players` | 服务器管理员 | 列已知玩家 ID、显示名、在线状态、所属网和角色。 |
| `network-set-admin <PlayerId>` | **仅服务器管理员** | 从玩家当前网络解析目标网，唯一管理员切换，不接受 NetworkId 参数。 |
| `trader-sessions` | 服务器管理员 | 查询活跃聚合购买会话、持有者及商人来源。 |
| `trader-force-close <SessionId>` | 服务器管理员 | 强制结束指定会话并释放锁；不改已完成的真实交易。 |

阶段 4 已存在的命令不必重复造轮子；阶段 5 的“完整指令系统”重点是**检查缺项、统一解析/权限/帮助/返回码，并覆盖新的成员操作**。UI 管理员转让与 `network-set-admin` 共享单网唯一管理员约束，但授权来源不同。

本仓库采用游戏 F1 控制台命令（输入时不加 `/`）：玩家入口为 `hdn-network`（别名 `sn`），支持上表中的全部玩家成员操作；`accept`/`decline` 使用 `invite-status` 返回的运行期 `InviteId`，原版确认弹窗也携带同一 ID。服务器维护入口为 `hdn-network-admin`，子命令为 `move-items`、`clear`、`player-info`、`list-players`、`set-admin`、`trader-sessions` 和 `trader-force-close`。`list-players` 支持偏移量与每页数量，`clear` 必须带 `--confirm`。原 `hdn-trader-market list|close <sessionId>` 命令仍保留兼容。

### 8.4 参数解析与失败反馈

- 需要稳定 `PlayerId` 的操作优先接受完整标识；如支持按显示名查找，重名时明确提示歧义，不默选第一个。
- 缺参数、目标离线、邀请已占用、邀请超时、目标不可邀请、非管理员、目标非本网络成员、同源同目标、库存数量溢出等均提供可理解的失败原因。
- 管理员破坏性命令提供记录与明确结果；玩家指令避免打印大量物品/完整库存。
- 文本指令同样需要请求去重与权限检查，不能因未走 UI 而绕过成员切换屏障。

## 9. 客户端同步、权限缓存与正常保存

### 9.1 成员变更事件（建议 DTO）

```text
MemberViewChanged {
  NetworkId,
  MembershipRevision,
  AdminPlayerId,
  MemberSummary[],             // 成员少时可整表；不是库存快照
  Cause                     // Join / Leave / Kick / TransferAdmin / Merge
}

OwnNetworkChanged {
  PlayerId?                  // 可由受信任会话隐含，不信客户端字段
  OldNetworkId,
  NewNetworkId,
  NewRole,
  MembershipRevision,
  NetworkSettingsSummary,
  InventoryRevision
}

InvitationNotice / InvitationWithdrawn / InvitationResult
```

网络成员列表通常远小于 10 万种库存变体，因此可以按网络发送精简成员列表；**库存仍然坚持阶段 4 的分页、轻量视图及变更/失效通知，不因阶段 5 加入共享网络而恢复全量快照广播**。

### 9.2 同步时机

- 邀请创建/失效：只同步邀请当事人所需的通知。
- 加入/退出/踢出：新旧网络有权成员收到成员列表变更；身份改变的玩家收到自己新网络摘要，清理旧网查询订阅/补货/弹药缓存。
- 管理员转让：该网络成员收到管理员角色更新；旧管理员 UI 立即切为成员态或关闭管理员设置；新管理员获得可操作入口。
- 合并：向目标网络的有权订阅者发送本次库存变更或相关视图失效；来源客户端必须废弃失效的来源网络缓存。
- 断线与重连：重新从服务端取得所属 `NetworkId`、身份和成员修订信息；客户端旧缓存绝不授权访问旧网络。

### 9.3 保存策略

沿用阶段 4 的正常自动保存和正常关闭快照：成员映射、唯一管理员、网络身份、网络级设置/自动规则、个人设置及库存同属正常持久化范围。邀请、弹窗状态、在途事务、商人锁和链式合成订单仍只存在运行期。

不引入针对突然进程崩溃的跨原版状态强恢复。**但正常运行的合并/换网/退出/踢出必须逻辑完整，正常保存不能把“源网已删除、成员仍指向源网”等中间状态写进去。**

## 10. 并发、幂等与异常场景

### 10.1 最小协调要求

- 每个成员变更操作有运行期唯一 `RequestId`；同一个请求成功后重放只返回原结果。
- 邀请的接受以 `InviteId + 受邀者` 严格绑定；不能代替其他玩家接受。
- 修改两个网络关系/库存时，按固定网络 ID 顺序进入协调区间，避免不同操作互相死锁。
- 不在持有全局成员锁时等待玩家交互、磁盘全量保存或网络往返；取消原版操作的等待必须有可控结束条件和失败结果。
- 合并或直接换网正在进行时，其他请求的最终提交必须检查受影响玩家当前的成员版本及实际 `NetworkId`，避免基于旧权限跨网写入。
- 服务器只公布**最终提交后**的角色、成员和库存视图，不对客户端发送可被误认为已成功的中间状态。

### 10.2 典型竞态及预期结果

| 竞态 | 必须保证的行为 |
|---|---|
| 两名邀请者同时邀请同一目标 | 只有一条待处理邀请成功，另一个明确失败。 |
| 邀请时目标是单人管理员，接受前邀请了别人加入自己的网络 | 接受时重新检查，发现来源网已有其他成员则拒绝合并。 |
| 邀请者发送后离开其目标网络 | 该邀请失效；迟到接受拒绝。 |
| 普通成员接受邀请的同时被旧管理员踢出 | 两操作由身份变更协调器定序；不能创建两个新网络、不能同时留在两网。 |
| 同一个接受请求重复到达 | 不重复合并来源库存或重复注销来源网。 |
| 合并时来源自动交易正要扣款 | 冻结来源新操作，先停止/完成可确认的在途动作，清理后再计算库存；不能出现注销后仍向来源提交。 |
| 合并入库碰到目标自动出售 | 仍按目标规则检查；自动出售异常不使已成功合并逆转或复制物品。 |
| 链式订单取消时成员已换网 | 可回收材料仍进入订单绑定的**旧网络**；不能进入新网。 |
| 管理员转让与管理员规则编辑同时发生 | 按提交顺序与当时有效角色鉴权；旧管理员转让后不能继续提交新管理员专属修改。 |
| 踢出离线成员，玩家之后上线 | 直接读取新空网络及管理员角色，不重新获得旧共享网的缓存访问权。 |
| 被踢成员旧客户端仍打开库存/商人页 | 服务端拒绝任何旧授权新操作；相关界面/锁和订阅清理。 |
| 正常保存恰好遇到合并 | 捕获一致逻辑状态快照；不能保存半成品。 |

## 11. 推荐开发顺序与交付分段

| 顺序 | 工作包 | 完成标志 |
|---|---|---|
| A | 检查阶段 4 已完成的成员目录、网络生命周期、交易协调、商人会话、订单取消及设置保存接口 | 明确复用点；不重新设计已经工作的库存核心。 |
| B | 成员变更协调器、角色/身份代际、运行期清理接口 | 可通过内部测试安全完成直接换网、退出、踢出、管理员转让；旧请求无权限。 |
| C | 单人管理员网络合并与目标入库规则 | 正常成功/失败无半份库存；来源网注销、规则不迁移；自动出售正确触发。 |
| D | 单邀请服务 + 5 分钟有效期 + 原版确认弹窗 | 一目标最多一邀请；接受自动选择换网/合并；弹窗关闭后服务端仍兜底清理。 |
| E | 网络管理 UI（成员表、邀请、退出、踢出、管理员转让） | 权限按钮准确、信息同步、离线成员可管理；复用既有 UI 风格。 |
| F | 玩家指令与服务器管理员完整维护指令 | 已实现并构建；静态审查确认复用成员服务、服务端鉴权与稳定目标标识。游戏内多人命令回归仍待验收。 |
| G | 共享网络集中回归与性能/日志验证 | 多名玩家真实共同游玩，各物流功能正确且无串网/越权/重复扣料。 |

顺序允许按现有代码的依赖小幅调整；**管理 UI 优先于正式玩家指令**是本阶段明确偏好。不会为了“先有指令”而额外写两套操作实现。

## 12. 阶段 5 验收清单

### 12.1 邀请、加入与网络身份

- [ ] 任意网络成员能邀请在线且有资格的玩家；离线玩家、同网玩家、仍有其他成员的共享网络管理员均不可邀请。
- [ ] 单个受邀玩家同时最多一个有效邀请；不同受邀玩家可以分别收邀请；邀请 5 分钟超时并可在终结后重新邀请。
- [ ] 原版弹窗显示真实邀请者及正确加入影响；拒绝无副作用，迟到接受失败。
- [ ] 普通成员在有邀请时能直接从共享网络 X 加入 Y；X 库存、规则和总开关不变，不创建临时个人网络。
- [ ] 单人管理员加入 Y 时，X 库存全部进入 Y、X 注销、角色变成员；X 的网络级配置及自动规则不继承，个人设置保留。
- [ ] 目标网络自动出售对合并进来的物品起作用，且失败不会让来源物品被错误复制。
- [ ] 加入失败时成员、库存、规则保持合法原状态；重复接受不重复合并。

### 12.2 退出、踢出、管理员转让

- [ ] 普通成员主动退出获得新空网络并成为管理员；个人设置不变，新网络管理员设置全部为默认。
- [ ] 普通成员被踢（在线或离线）得到新空网络；旧共享库存不返还；不能继续访问旧网。
- [ ] 网络管理员不能普通退出、踢出自己或踢出其他网络玩家。
- [ ] 当前管理员可在 UI 转让给同网其他成员；原管理员降为普通成员，网络级设置和自动规则仍在原网络。
- [ ] 网络管理员没有玩家聊天转让指令；服务器管理员 `set-network-admin <PlayerId>` 可以安全完成唯一管理员切换。
- [ ] 管理员转让后，自动交易加成读取新管理员的实际在线状态和有效加成。

### 12.3 设置与业务会话

- [ ] 自动补货个人开关/范围、手动买入收货方向及手动卖出收益方向，在所有成员身份变化后仍跟随原玩家。
- [ ] 目标网络的管理员总开关与自动交易规则不被来源网络覆盖；退出/踢出得到的新网络应用默认网络设置。
- [ ] 普通成员换网不停止旧网络其他玩家的合成链或网络自动交易。
- [ ] 换网/踢出/合并会取消受影响玩家旧网合成订单，按既有规则回收到旧网；旧网库存迁移则在取消回收后执行。
- [ ] 聚合购买会话在相关玩家切网时关闭并释放真实商人锁；已完成的原版交易不撤销。
- [ ] 已真正被原版接收的弹药、工作站材料和已完成交易不反向追缴；未提交的旧网操作不能迟到扣料。
- [ ] 网络窗口、查询缓存、弹药 HUD/自动补货监听和网络设置 UI 在身份变更后按新网络刷新。

### 12.4 多人并发及持久化

- [ ] 房主、远程客户端、专用服务器均通过同一服务端成员/库存权限校验。
- [ ] 多人共享网络同时取出、存入、制作、维修、加油、换弹和自动补货，不会超额使用或重复扣料。
- [ ] 多人共享链式合成、商人交易、自动售卖/购买、聚合商人锁与角色切换交互正确。
- [ ] 邀请、加入、踢出、转让、合并碰到网络延迟、重复请求、失败与取消时不产生中间非法成员关系。
- [ ] 正常保存、正常关闭、重进存档后网络 ID、唯一管理员、成员映射、库存、网络配置和个人设置一致；邀请不会跨重启恢复。
- [ ] 客户端按需拉取轻量视图，成员变化只广播必要成员信息；不为共享网络广播整个库存。
- [ ] `DebugLog` 可定位成员变更请求、合并阶段、被清理会话、失败原因、相关网络/玩家摘要及耗时。

### 12.5 指令系统

- [ ] `hdn-network info|members|invite-status` 在主机与远程客户端返回当前服务端视图；成员超过一页时列表完整且不混合成员变更前后的结果。
- [ ] 玩家成员及网络管理员均可邀请合格在线玩家；同网、离线、待处理邀请和不合格管理员会得到明确错误。
- [ ] `accept`/`decline` 仅能处理自己的有效邀请；过期或旧 `InviteId` 不能作用于后来收到的新邀请；原版弹窗仍可正常接受/拒绝。
- [ ] 普通成员可退出及邀请换网；管理员不能普通退出；仅网络管理员能踢出同网普通成员，离线踢出后玩家上线获得新空个人网络。
- [ ] 非服务器管理员无法运行 `hdn-network-admin`；管理员的库存迁移只搬库存，清空必须确认，管理员重设按目标玩家当前网络执行。
- [ ] 维护命令遇到成员切换/合并时安全拒绝；执行期间同网库存操作不能并发穿过维护屏障。
- [ ] 库存迁移/清空/管理员重设遇到聚合商人会话或自动交易规则执行时拒绝，避免交易流程在维护后继续使用过期库存视图。
- [ ] 管理员列表和查询命令能显示离线玩家；聚合商人会话维护命令仍可用。

## 13. 诊断与源码落地注意事项

### 13.1 建议诊断字段

`DebugLog` 统一记录：`RequestId`、`InviteId`、`PlayerId` 摘要、`SourceNetworkId`、`TargetNetworkId`、操作类型（Invite/Accept/DirectSwitch/Merge/Leave/Kick/TransferAdmin）、旧/新角色、成员版本、受影响库存修订号、取消会话数、合并精确变体数、入库自动出售结果、阶段耗时与错误码。默认关闭详细日志，不打印逐物品大列表。

### 13.2 源码对接时核对，而不是先假设

1. 阶段 4 的网络目录是否把管理员保存在成员集合内，角色变更怎样标脏并正常保存。
2. 运行期请求如何携带真实玩家身份、操作所属网络及身份代际；有无迟到请求或重试路径。
3. 链式合成取消是否可按**发起人 + 原 NetworkId**查询并回收；已完成但待领取的订单如何处理。
4. 商人聚合购买关闭窗口与实际释放商人锁是否分离；服务器端能否按玩家会话强制清理。
5. 自动交易正在执行时，能否使将注销的来源网络停止新批次且可靠处理已提交批次。
6. 现有玩家个人设置与网络级设置实际存储位置、默认值、序列化入口及缓存刷新方式。
7. 原版确认弹窗能否在邀请到达时独立呈现、可靠触发接受/拒绝并自然关闭背包等窗口；**业务安全不能依赖弹窗必然关闭窗口**。
8. 服务器管理员指令与普通玩家聊天命令的注册/权限检查路径，是否已有阶段 4 的七项维护能力。

### 13.3 允许的实现变体

可以沿用阶段 4 现有 `MembershipEpoch` 而不是新增 `MembershipRevision`；可以把邀请、成员和网络生命周期写在同一服务内而不增加新程序集；可以复用已有管理员命令解析器。只要满足**单一服务端权威、单人唯一管理员、正常运行原子切网/合并、旧权限失效、个人设置保留、网络级设置不迁移、统一入库检查**这些行为契约，具体类名并不重要。

> **最终实施原则：**阶段 5 是把阶段 4 已完成的个人网络基础扩展成真实共享网络。新增的是成员生命周期和交互入口，不是第二套库存或交易系统。先保证服务端身份变化与在途功能清理，再上网络管理 UI、完整指令及最终多人验收。
